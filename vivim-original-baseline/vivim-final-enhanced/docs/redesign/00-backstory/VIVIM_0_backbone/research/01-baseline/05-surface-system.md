**Critical finding:** The `surfaces/web/src/canvas/` module does NOT import or reference `reprogrammability/` at all. The canvas has its own node/edge type system (`NodeType`, `EdgeKind`), its own store, its own command layer, and its own config. It is a **closed, independent system** at the frontend level. Reprogrammability exists separately on the backend.

---

## What the code does

The canvas is the **infinite-canvas frontend surface** — a pan/zoom workspace with nodes and edges. It is a self-contained subsystem in `surfaces/web/src/canvas/`.

**Five modules, each with one job:**

1. **`types.ts`** — core data types.
   - `NodeType = 'package' | 'note' | 'code' | 'image' | 'link' | 'group' | 'marker'` (line 4-11). 7 node types. **This is canvas-specific**, not the `SurfaceKind` enum from reprogrammability.
   - `EdgeKind = 'depends-on' | 'conflicts' | 'relates' | 'references'` (line 13-18). 4 edge types.
   - `CanvasNode { id, type, position, size?, data, color?, label?, parentId?, revision }` (line 31-47). Each node has a `type` from NodeType, free-form `data`, optional visual overrides, optional group parenting, and a CRDT-style `revision` counter.
   - `CanvasEdge { id, from, to, kind, label?, bends?, revision }`. 1-to-1 from-to with optional curved control points.
   - `CanvasBookmark { id, name, hotkey?, viewport }`. Saved viewports.
   - `CanvasState { schema: 'vivim.canvas/v1', id, nodes, edges, bookmarks, viewport, configOverrides?, updatedAt }`. The complete document.

2. **`config.ts`** — user-configurable canvas configuration.
   - `CanvasConfig` is "the single source of truth for every visual + behavioral dimension of the canvas."
   - Typed (`so the config panel can render a schema-driven UI`).
   - **Hot-reloadable** (file watcher re-reads `config/canvas.toml` on save).
   - Overridable per-canvas (each canvas has `configOverrides`).
   - Resettable (panel has "Reset to defaults" button).
   - Load order: defaults → global config (`config/canvas.toml`) → per-canvas overrides → runtime overrides from the config panel.
   - 249 lines covering theme, palette, grid, snap, zoom, persistence, keyboard bindings, etc. The file is a *configuration schema* — every field is a tunable, and the config panel reads from this shape to render a UI.

3. **`store.ts`** — Zustand store. Single source of truth at runtime.
   - `useCanvasStore` (line 65) — a Zustand store with state + actions. State: `state` (the document), `config`, `selectedNodeIds`, `selectedEdgeIds`, `mode`, `history` (for undo), `future` (for redo).
   - **Mode is canvas-specific**: `'normal' | 'insert' | 'visual' | 'command'` (line 16). Vim-style modes.
   - Actions: viewport (setViewport, panBy, zoomBy, fitToContent), nodes (addNode, updateNode, removeNode, moveNode), edges (addEdge, removeEdge), selection (select, selectAll, clearSelection), bookmarks (addBookmark, gotoBookmark), history (undo, redo, commit), mode (setMode), config (setConfig, resetConfig), bulk (loadState).
   - History is bounded by `config.persistence.versionHistory` (line 259). Older history states are dropped.
   - Node ids are generated by `nextId('n')` (line 137) — `${prefix}_${Date.now().toString(36)}_${counter}`.

4. **`commands.ts`** — Vim-style modal command layer.
   - Pure function `handleKey(key, mode, pendingKeys, config, selection)` (line 59). Takes keys + state, returns `CommandResult` with `action` (e.g. `{ kind: 'pan', dx, dy }`, `{ kind: 'zoom', factor }`, `{ kind: 'node-delete', ids }`, `{ kind: 'insert-note', at? }`) and `newMode`.
   - **Bindings come from `config.keyboard.bindings`** (line 51). The `CanvasConfig` defines which keys do what; this file inverts the map to look up by key.
   - 17 action kinds defined. Leader-key sequences (e.g. `d` then `d` to delete) are supported via `pendingKeys`.
   - "This module is pure: it takes (keys, state) and returns (action, newMode). The React layer wires it to actual store dispatches." (line 12-13)

5. **`live-config.ts`** — server-side patch tool for canvas definitions.
   - **`patchDefinition(id, partial, deps)`** (line 50) — P8-enforced live edit of a `CanvasDefinition`. Validates: no inline `<script>`, sandbox.allowInlineScript must be `false`. Bumps version, emits `canvas:def:updated` on the event bus so mounted nodes re-render without page reload.
   - **`reresolve(ctx, deps)`** (line 85) — re-runs `routeSync` against the current store with a new `traceId`. Returns a fresh `ResolvedSurface`.
   - **`observeContext(cb, deps)`** (line 99) — subscribes to four event types: `account:plan_tier_changed`, `provider:added`, `workspace:switched`, `canvas:def:updated`. Returns a disposer.

**The P8 invariant** (P8 = "no inline script" — see line 56-64): `inline <script>` tags are forbidden in `CanvasDefinition.html`, and `sandbox.allowInlineScript` is a literal-`false` type. This is the **trust boundary for the canvas's HTML surface**. It is the only place where the canvas "renders user-provided code" — and it is locked down.

## Key observations

- **The canvas is closed at the data level.** `NodeType` is 7 hard-coded values. `EdgeKind` is 4. There is no way for a user (or a plugin) to add a new `NodeType` without modifying the source. The `data: Record<string, unknown>` field is the only escape hatch — and it is type-erased at the schema level.

- **The canvas is configuration-extensible, not code-extensible.** `CanvasConfig` is a deep, typed object with many tunables. The config file `config/canvas.toml` is hot-reloaded. But this is *user configuration* of an existing system, not *user code that extends the system*. A user cannot make a new node type. They can change colors, snap behavior, keybindings, theme.

- **Two parallel "extensibility" models coexist in this codebase:**
  - Canvas: `NodeType` + `data` bag + `config.ts` + command bindings. Closed at the type level; open at the data and config level.
  - Reprogrammability: `SurfaceKind` + `SurfaceSpec` discriminated union + mutation ops. Open at the type level (modulo `custom` flagging) but requires backend wiring (Prisma / SurfaceRegistry).

- **The canvas's `commands.ts` IS the closest thing to a user-extensible command system in the canvas layer.** The bindings are loaded from `config.keyboard.bindings` (config-driven). The action kinds (17 of them, line 26-46) are hard-coded in TypeScript. So you can rebind a key to a different action, but you can't add a new action kind without editing the source.

- **History is a closed stack with bounded depth.** `commit()` (line 257) keeps only the last `versionHistory` states. Undo/redo is canvas-only, in-memory. There is no cross-session history and no version persistence (that would be the version-store in engines/reprogrammability/).

- **The canvas is CRDT-aware but not yet CRDT-implemented.** Each node/edge has a `revision` counter (line 46, 56). The `collaboration.ts` file is in the same directory and presumably implements the CRDT merge. The data model anticipates multi-user editing, but the basic store actions just bump `revision` without doing anything with it. (Need to read `collaboration.ts` to confirm.)

- **The live-config toolkit is the only "user edits the live canvas" path.** It is server-side, called via the API. It validates P8 invariants strictly. It emits events for re-render. It does NOT call any user-defined code — it calls `canvasDefinitionStore.update(id, patch)`. So it is a *safe* extensibility point.

- **`loadState` overwrites the entire canvas.** Line 269. No conflict resolution. This is a power-user / migration tool, not a normal user flow.

- **Snap-to-grid is per-canvas.** Line 169-186. `moveNode` snaps to `snap.gridSize` if `snap.enabled`. The grid size is itself configurable. This is a config-driven behavior, not a code-driven one.

- **There are 7 node types but 1 of them is `'group'`** (line 10) — frames that contain other nodes. Nodes can have `parentId` (line 44). The canvas is a tree-of-graphs. `removeNode` cascades to remove all edges pointing to/from the node (line 162-166) but does NOT cascade to children — a group is just a node, and removing it leaves its children orphaned. (Possibly a bug; possibly intentional.)

- **P8 is a hard invariant.** Inline scripts are forbidden at the type level (literal `false`). This is the *only* place the system loads user HTML, and the loader is forced to be sandboxed. This is a real security boundary.

- **The "leader key" pattern in `commands.ts` (line 10, 88-90) is multi-key sequence handling.** `pendingKeys` accumulates; if the current sequence is a prefix of any binding, we wait. This is exactly how Vim's `dd`, `gg`, `gg` work. It is a small, focused command-bar model.

- **Mode is canvas-scoped, not app-scoped.** The canvas has its own `'normal' | 'insert' | 'visual' | 'command'` modes. These are unrelated to any "app mode" or "LLM agent mode." They are the canvas's local interaction model. Plugins cannot change them (the mode is internal state in the store).

## Key questions raised

1. **Is `config/canvas.toml` a user-edited file?** The comment says it's hot-reloaded. Is the user expected to write TOML? Or is the config panel the only way to set it? If the former, this is a textual extension surface (user writes a file, system re-reads it).

2. **How does a node get rendered?** `CanvasNode` has `type: NodeType` and `data: Record<string, unknown>`. Somewhere there's a renderer that maps `type` → React component. Is that hard-coded, or registered? (Likely hard-coded, given `NodeType` is a 7-value literal — but need to confirm.)

3. **Is the `data` field the extension point for nodes?** A user can't add a new `NodeType`, but they can put anything in `data`. The renderer for that type is then responsible for using `data` correctly. This is data-driven extensibility, not code-driven.

4. **Where does `collaboration.ts` fit?** It exists in the same dir. CRDT is mentioned in the `revision` field. The store doesn't do CRDT merge. So `collaboration.ts` must wrap the store with a CRDT layer. (Will read in a follow-up if needed.)

5. **What is `RouteContext` and `ResolvedSurface`?** Line 17, 88-90. These are imported from `shared/route-context`. They are not the `ReprogrammableSurface` from reprogrammability — they are routing concepts. The naming overlap is a hazard.

6. **What is `CanvasDefinition` vs `CanvasState`?** `CanvasState` is the live document (in the Zustand store). `CanvasDefinition` (referenced in `live-config.ts:16`) is presumably a server-side stored template. The two have related shapes but different lifecycles.

7. **Can a user create a new `NodeType` via the `reprogrammability` system?** The canvas is closed. Reprogrammability is open. Is there a bridge where a `ReprogrammableSurface` of kind `'custom'` can host a canvas node? Or are they parallel worlds that never meet?

8. **What does the "live-config" model give us for an extension system?** It is a safe, validated, event-emitting patch path. A user can edit a `CanvasDefinition` (a server-side template), and mounted instances re-render. This is *almost* a "user extension" — except the schema is fixed (`html`, `css`, `bindings`, `layout`, `sandbox`, `status`, `tags`, `name`, `description`). The `scriptUrl` field hints that users can point to an external script — but P8 forbids inline.

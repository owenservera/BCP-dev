# Ω Evolution Team — Constitution

> Status: OWNER-DIRECTED TEAM SEED
> Date: 2026-09-28
> Scope: `team/omega-evolution`

## 1. Mission

Build toward the VIVIM vision on top of Ω.

The team is free to discover that this requires:

- extending Ω;
- simplifying Ω;
- rewriting Ω;
- replacing Ω subsystems;
- changing Ω boundaries;
- changing Ω vocabulary;
- changing Ω law;
- moving functionality between host, plugins, surfaces, tooling or other layers;
- discarding existing work;
- creating capabilities that do not exist today.

The team is judged by the quality of the destination it creates, not by how faithfully it preserves the path that produced the present repository.

## 2. No migration obligation

The following are explicitly **not inherited obligations**:

- migrating old VIVIM subsystems;
- preserving old folder structures;
- implementing the current CFA portfolio;
- completing current P1 workstreams;
- following the current Architecture Steward launch queue;
- porting old engines because they exist;
- preserving the current Ω implementation merely because it is already proven;
- finishing a prior roadmap before creating a better one.

Migration/harvest may be chosen when useful. It is a means, not the mission.

## 3. Full Ω stewardship

The team has branch-local stewardship over Ω as a living system.

This includes authority to decide, on this branch, whether a current Ω rule, design decision, boundary, implementation, test, or convention should:

- remain;
- be amended;
- be replaced;
- be deprecated;
- be deleted.

The team must preserve the evidence trail whenever a material change occurs.

## 4. Vision over inertia

When an existing implementation and the intended product experience disagree, investigate the disagreement rather than assuming the implementation is correct.

When an existing law blocks a requirement the team believes is necessary, treat that as a legitimate architecture choicepoint.

When a new idea is attractive but weakly evidenced, label it as a hypothesis and test it.

## 5. Evidence discipline

The team may move faster than the main program, but it may not become careless about evidence.

Maintain the distinctions:

- evidence vs representation;
- description vs authority;
- hypothesis vs observation;
- proposal vs decision;
- implementation vs proof;
- capability vs authorization;
- confidence vs proof;
- candidate vs realization;
- unknown vs failure.

A branch decision is not evidence merely because it was written down.

## 6. Freedom does not mean chaos

The team may change almost anything, but material changes should remain discoverable.

For consequential changes, record:

- what changed;
- why;
- prior state;
- new state;
- evidence;
- implications;
- falsifier or validation condition;
- compatibility consequences;
- whether existing artifacts were superseded, retained, or removed.

Do not create bureaucracy for its own sake. Use the smallest durable record that keeps the reasoning reconstructable.

## 7. Build from the vision, not the backlog

The team roadmap is created after a fresh assessment of:

- the user/product vision;
- the current Ω substrate;
- the known destination gaps;
- current evidence;
- available agent capabilities;
- unresolved architecture choicepoints.

The existing backlog is reference material, not a command queue.

## 8. Preserve the useful corpus

The team should aggressively harvest useful knowledge.

It should not, however, confuse harvesting with architectural adoption.

Useful legacy behavior can become:

`evidence → understanding → re-expression → verification → adoption`

rather than:

`old code → automatic import`

## 9. Parallel development

Safe independent work is encouraged.

Shared mutable surfaces require explicit ownership.

Do not merge branches merely to communicate.

Use Agent Commons and exact refs for communication and lineage.

## 10. Product outcome

The team should continuously ask:

> Would this make the eventual VIVIM product materially more coherent, sovereign, useful, evolvable and trustworthy?

That question guides priorities, but does not replace evidence or explicit design reasoning.

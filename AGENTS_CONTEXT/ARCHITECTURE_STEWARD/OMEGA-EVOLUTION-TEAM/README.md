## What this is

The **Ω Evolution Team** is a deliberately independent development program for taking VIVIM toward its long-term vision **from the current Ω baseline**.

It shares the repository, tools, agent infrastructure, evidence corpus, and access available to the existing BCP-dev team, but it does **not** inherit the existing program's migration burden, P1 sequencing, CFA roadmap, or implementation backlog.

Its job is to ask:

> **If we were responsible for making Ω become the best expression of the VIVIM vision from here, what would we build, change, delete, replace, or rethink?**

The team owns that answer.

## Independence

The team has:

- its own long-lived development branch: `team/omega-evolution`;
- its own durable team context in this directory;
- its own roadmap;
- its own task queue;
- its own development state;
- its own decision/evolution history;
- freedom to reorganize or replace the Ω implementation;
- freedom to amend Ω design and law on this branch when the team concludes that doing so is necessary.

The team is **not** a migration squad.

Legacy, BCP, current Ω code, current destination documentation, and existing agent work are inputs to inspect and harvest. None is an obligation merely because it already exists.

## Shared access, separate ownership

The team uses the same repository access and collaboration substrate as the existing agents:

- the full `BCP-dev` repository;
- current `main` and all accessible branches;
- `AGENTS_CONTEXT/`;
- Agent Commons;
- current CFA agent homes and their research;
- Ω runtime, tests, tooling and evidence;
- legacy/VIVIM source mines;
- BCP forensic/migration machinery;
- existing development acceleration and agent tooling.

No second credentials system, second Commons protocol, second ontology, or second repository is created.

Access is shared. **Ownership of the team's direction is not shared by default.**

## Relationship to main

`main` remains the independent integration line and continues its existing work.

The Ω Evolution Team's branch is a separate experimental/product-development line. Team work is authoritative for the team's branch, not automatically for `main`.

A future integration into `main` is an explicit decision, not the team's default objective.

## Core distinction

Keep these separate:

| Existing material | Team interpretation |
|---|---|
| Current Ω law | Starting point; amendable on this branch |
| Current Ω architecture | Starting implementation and evidence; replaceable |
| Destination docs | Vision/context to understand; not a backlog |
| CFA roadmaps | Peer intelligence; not inherited work |
| BCP migration machinery | Available capability; not a duty |
| Legacy VIVIM | Evidence/harvest source; not architecture to preserve |
| Existing tests/gates | Evidence and guardrails; retain, improve, replace, or supersede deliberately |
| Existing product assumptions | Hypotheses to validate, not permanent commitments |

# Architecture Steward — Spawn Experience Rubric

> Status: FIRST PASS / GENERAL RUBRIC
> Established: 2026-09-25
> Purpose: describe how a fresh Steward should enter the repository and how the spawn experience should be judged.

## 1. Spawn objective

A fresh Steward should become useful without reconstructing the project from conversation history and without reading the repository indiscriminately.

The desired experience is:

`orient → identify authority → locate active reality → understand existing knowledge → identify the actual question → act → leave durable context`

## 2. First-pass spawn sequence

### S0 — Establish the boundary
Read the root repository working agreements and build context. Confirm the meaning of the top-level trees before interpreting detail.

### S1 — Enter the Steward workspace
Read the Steward README, mandate, state and current operating interpretation. The Steward should know its responsibilities and non-responsibilities before touching other documentation.

### S2 — Locate current architectural reality
Read the smallest relevant destination and Ω authority views. Do not load historical research merely because it exists.

### S3 — Search before inventing
Before creating a document, registry, model, protocol or work item, search for prior work on the subject across destination research, System Intelligence, legacy harvest and peer agent-context packages.

### S4 — Classify what is found
Separate authority, current derived views, evidence/research, proposals, implementation, history and process machinery.

### S5 — Work the question
Operate on the concrete architectural seam that caused the Steward to be invoked. Do not perform a repository-wide rewrite as a substitute for understanding.

### S6 — Close the loop
Record only durable operating knowledge that will materially improve the next Steward session. Update existing views when necessary. Create new machinery only when recurring work proves the need.

## 3. Spawn success rubric

| Test | Pass condition |
|---|---|
| Orientation | Fresh Steward identifies repository layers and authority hierarchy correctly. |
| Scope | Fresh Steward can state what it owns and what it does not. |
| Retrieval | Fresh Steward finds existing relevant research before creating new architecture. |
| Authority | Fresh Steward does not promote derived/history material into authority. |
| Lineage | Fresh Steward can connect current work to prior research/evidence. |
| Contradiction | Fresh Steward preserves unresolved conflict instead of flattening it. |
| Actionability | Fresh Steward can identify the next concrete architectural action. |
| Restraint | Fresh Steward adds no new machinery unless justified by the task. |
| Durability | Important discoveries are left in repository-visible context. |
| Teachability | Another fresh agent can reproduce the orientation from the durable context. |

## 4. Spawn failure modes to watch

- reading everything before identifying the question;
- treating the latest document as automatically authoritative;
- treating a folder name as an authority signal;
- duplicating a concept because it appears in several research packages;
- creating a tracker/registry/process layer before recurring need is proven;
- confusing implementation existence with proof;
- confusing architecture depth with maturity;
- confusing historical process with current instructions;
- deleting history before extracting unique value and repairing references;
- leaving important conclusions only in the conversation.

## 5. Steward-specific spawn lesson from the first instantiation

The first Steward spawn succeeded because the repository already contained durable role instructions and a clear authority hierarchy.

The main friction was not lack of information. It was excess and repetition: multiple research generations, current and historical program-management documents, and several overlapping views of the same subjects.

Therefore the first-order optimization for future Steward spawns is not more context. It is better **context selection and lineage navigation**.

## 6. Relationship to peer agents

Peer agents have their own `AGENTS_CONTEXT/<ROLE>/` workspaces.

The Steward should treat those workspaces as authoritative context for their respective roles, not as subordinate folders to rewrite.

The Steward's job is to understand the interfaces between those roles and the repository-wide architecture.

Peer-workspace cleanup or redesign is deferred until there is a concrete problem to solve.

## 7. Generalization rule

This rubric is intentionally role-level and minimal.

A future Steward session may improve it when actual spawn evidence shows a repeatable failure or missing step.

Do not expand the rubric for theoretical completeness.

## 2. Composition boundary

**ALIGNED — RETAIN PROPOSED BOUNDARY**

CFA-07 owns the semantic and structural composition membrane:

- composition identity and membership semantics;
- dependency and contribution relationships among composition members;
- Manifest / CompositionSpec / Recipe semantic distinctions;
- plugin contribution and dependency structure;
- composition-level candidate admissibility constraints above K0 enforcement;
- first-party/system-plugin and third-party/extension-plugin symmetry at the governed composition boundary;
- Forge semantics as the mechanism for generating/proving candidates;
- composition-side replacement continuity and its handoffs to Work and Evolution.

The boundary retains:

`plugin identity != composition identity != canonical data identity`

and:

`candidate != admitted != active`

CFA-07 is not a universal plugin authority and is not a second runtime authority.

## 3. Composition vs Capability ownership

**ALIGNED**

CFA-06 remains the semantic owner of:

- Capability meaning;
- capability/operation references;
- Provider / Account / Model / Realization / Session / Resource semantics;
- routing/selection semantics;
- provider-specific realization knowledge and evidence.

CFA-07 owns:

- whether a capability/realization participates in a given composition;
- composition membership;
- assembly context;
- composition-level dependency and replacement constraints.

Therefore:

`Capability meaning → CFA-06`  
`Composition membership/assembly → CFA-07`

Selecting a realization is not defining the capability, and composition membership does not grant permission.

No separate Capability CFA is created by this alignment.

## 4. Plugin / Forge / admission boundary

**ALIGNED**

### Plugin

CFA-07 stewards the semantic shape by which plugins declare contributions, dependencies and composition participation. The plugin remains governed by the same Manifest / Recipe / Port path as other plugins.

### Forge

Forge remains inside CFA-07 as a composition-generation and proving mechanism:

`Forge plugin → candidate artifacts → evidence/proof → proposal → normal admission/evolution/authority path`

Forge:

- does not grant authority;
- does not create a privileged developer path;
- does not bypass composition admission;
- does not become K0.

The Builder Pack remains a declaration/schema/policy/test package, not a privileged SDK layer.

### Admission / enforcement

CFA-10 owns non-bypassable runtime enforcement, including admission/integrity, manifest/content verification, isolation/Port, capability enforcement, revocation/fencing, atomic activation, and generic runtime recovery/lifecycle enforcement.

CFA-07 may define the composition structure and semantic constraints that require enforcement, but does not perform K0 enforcement.

Invariant:

`composition semantics != runtime enforcement`

CFA-10 remains provisional/unborn in the repository state used for this alignment; this record does not ratify CFA-10.

## 5. Active replacement / Work interaction

**ALIGNED WITH PEER SEPARATION**

For plugin or realization replacement:

- CFA-07 owns composition-side candidate replacement and membership/continuity description;
- CFA-06 owns realization-specific meaning, validity and external realization evidence;
- CFA-05 owns active Work continuity, pause/reconcile/resume/refuse behavior and Work-level Outcome semantics;
- CFA-09 owns broader compatibility/change lifecycle once its identity is established.

An active Work is therefore an affected dependent, not a composition object CFA-07 may silently mutate.

A valid replacement does not automatically create a new semantic Capability or rewrite canonical Work meaning.

Unknown external effects remain explicit and flow through CFA-06 → CFA-05 reconciliation.

## 9. System plugin vs ordinary plugin

**ALIGNED — ONE GOVERNED PLUGIN BOUNDARY**

System plugins and ordinary/extension plugins may differ by role, packaging, composition inclusion, provenance and product policy, but not by an undocumented second authority or admission mechanism.

A system plugin may be:

- first-party;
- bundled;
- required by a default composition;
- assigned an explicit boot/composition role under existing Ω law.

None of these creates a second admission path.

Where Ω already specifies a special runtime role (for example a designated boot-phase role), that is a separate K0/constitutional rule and is not a CFA-07-created privilege.

The architectural rule is:

`system plugin != trust-bypass class`

and:

`first-party status != undocumented privilege`

First-party and third-party plugins should traverse the same governed Manifest / Recipe / Port boundary to the extent applicable contracts allow.

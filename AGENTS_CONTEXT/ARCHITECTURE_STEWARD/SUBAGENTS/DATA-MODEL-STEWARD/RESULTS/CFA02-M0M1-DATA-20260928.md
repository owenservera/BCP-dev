## Lineage-metadata rule (how MODE/SURFACE/WORK_ID+lineage attach without a second task system)

1. All M1 additions are **optional metadata keys on the existing receipt** (`RESULTS/<SESSION_ID>.md`) and, where useful, an **opaque lineage pointer line on the existing `TASKS.md` entry** (e.g. `Lineage: work_id/attempt/handoff/session`). No new file, table, registry, or store.
2. Key spelling follows v1.1 `UPPER_SNAKE` style. Values are **citations/identifiers**, never semantic re-definitions: CFA-02 carries `MODE`/`SURFACE`/`WORK_ID`/`goal_id`/`attempt_id`/`handoff_id` opaquely; their meaning is owned by the Steward envelope (mode), CFA-08 (surface), CFA-05 (work/attempt), and Commons (handoff/session).
3. Fixed mappings (no parallel truth): `session_id` ≡ `SESSION_ID`; `source_sha` ≡ `BASE_MAIN_SHA` (+ `PREDECESSOR_VERIFIED` detail); `result_sha` ≡ `COMMIT_SHA`; `handoff_id` ≡ pointer into `COMMONS`; `RESOLVED_AGENT` ≡ `CFA / AGENT` + `AGENT_ID` + `IDENTITY` triple; `ACTUAL_CHANGED_PATHS` ≡ `FILES_CHANGED`.
4. Commons remains the communication transport; the receipt remains its durable projection at HANDOFF REPORTED (contract §Commons convergence). A surface switch (LOCAL ⇄ CHATGPT-WEBAPP) writes **one continuing receipt chain** (same `WORK_ID`/`goal_id`, new `SESSION_ID`/`attempt_id`/`source_sha`) — never a forked task, never a competing authority chain.
5. EXECUTION-only keys (`REQUESTED_AGENT`, `ALLOWED_PATHS`, `REQUIRED_TESTS`, `TEST_RESULTS`) are **absent, not empty**, on DELIBERATE receipts. Validators must not demand them unless an `IMPLEMENTED` claim is made.
6. Per `STATE.md` Q2: this key list is a **bounded candidate set for M0/M1**, not a universal schema. New keys beyond it require corridor evidence + Steward amendment.

## No-rewrite rule (backward compatibility: v1.1 receipts remain valid)

1. Every M1 key is OPTIONAL. A receipt with only the 22 v1.1 fields validates as **pre-M1/unspecified**, never as failed.
2. Absent `MODE`/`SURFACE`/`WORK_ID`/lineage ⇒ "unspecified (pre-M1)". Absent `RESULT_CLASS` ⇒ interpret `RESULT` text + `SESSION_STATUS` as today. Absent execution keys on a non-`IMPLEMENTED` receipt ⇒ legitimate, not a gap.
3. The `IMPLEMENTED` evidence gate (commit exists, path containment, required tests passing, STATE fresh, delivery-ref re-read) fires **only** when `IMPLEMENTED` is claimed (`RESULT_CLASS=IMPLEMENTED` or `IMPLEMENTATION_STARTED: yes` with code delta). `INVESTIGATED`/`FALSIFIED`/`BLOCKED`/`SUPERSEDED`/`PARKED` never retroactively require execution keys.
4. No backfill: existing receipts (including all six in this home's `RESULTS/`) are never rewritten to add M1 keys. Cross-referencing (e.g. a later receipt citing an earlier `SESSION_ID` as predecessor) is the only permitted linkage.
5. Alias discipline: `RESOLVED_AGENT`/`ACTUAL_CHANGED_PATHS`/`handoff_id`-as-key, where used, MUST equal their canonical source triple/field; a mismatch is a validation failure, not a second opinion.

## Canonical data-owner vetos (forbidden second store / ontology)

- **V1 — no work/task database.** Tripwire: any proposal with its own work lifecycle (create/assign/transition/close) competing with `TASKS.md` entries + the Commons HANDOFF state machine (`OFFERED→…→REPORTED→CLOSED`). Lineage tuple travels *on* those two surfaces or the proposal STOPS as BLOCKED.
- **V2 — no identity registry.** Tripwire: any receipt-owned agent roster, key registry, or session directory competing with `OWNER-DELEGATION.md` + `PEER-ROSTER.md` + Commons `agent_id`/`session_id`/`key_id`. Receipts cite identities; they never mint them.
- **V3 — no authority/enforcement store.** Tripwire: `ENFORCEMENT_LEVEL` (or any permission/capability verdict) authored by the receipt, evaluated from the receipt, or treated as proof of mechanical enforcement — especially while `WORKER-CATALOG-2026-09-28.md` records name-scoped gating as unavailable on this runtime. Enforcement semantics belong to CFA-04/CFA-10 + the validator; the receipt carries at most their opaque citation.
- **V4 — no evidence/test/command store.** Tripwire: embedding test-run histories, command logs, or path registries in receipts beyond outcome citations + refs. Canonical evidence lives where produced (test output, commits, vault); the receipt points.
- **V5 — no competing receipt system.** Tripwire: any M1 artifact that replaces rather than extends `SESSION-RESULT-CONTRACT.md`, or any completion claim advanced without the Durable Completion Gate transaction (receipt + TASKS.md closure + recorded ref + delivery-ref re-read). Chat/Commons assertions stay REPORTED-UNVERIFIED until then.
- **V6 — no universal schema by fiat.** Tripwire: making any M1 key mandatory repository-wide, or extending the key set, without corridor evidence and a Steward amendment. Per operating-model §13 and delegation limits: add machinery only when recurring real work proves a current layer cannot express the requirement.

On any tripwire: STOP, record `BLOCKED` + cursor in this home's `STATE.md`/`TASKS.md` lane, send Commons REQUEST/HANDOFF to the owning CFA via the Steward — do not wait synchronously, do not implement around the owner.

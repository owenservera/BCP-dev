## Rationale (why this ranking, from the CFA-02 lens)

1. **Verifiability before velocity.** Ranks 1–2 come first because every other
   tool's output is worthless if the team cannot pin what it read (exact SHAs,
   no merge-to-read) and cannot prove what it concluded (receipt + TASKS closure
   on the delivery ref). CFA-02's invariant is about reconstructability; the
   team's own workflow must satisfy it before the product can.
2. **Canonical-vs-derived is the load-bearing distinction.** Ranks 3, 4, 7, 10
   operationalize it: export-verify proves projections are disposable; scoped
   query keeps the Lens a composer of authorities rather than a new store;
   freshness checking stops stale views from posing as truth; dossiers make the
   distinction portable across sessions.
3. **Change is the invariant's subject.** Ranks 5, 6, 8, 9 address the clause
   "merely because its representation, storage implementation, provider
   realization, surface, or surrounding system changes": migration diffing,
   parser replay, correspondence audit, and checkpoint discipline each cover one
   change class with a falsifiable check.
4. **Deliberately excluded** (non-goals for this toolset): installing anything
   (characterization only); a universal graph database / universal Event-State
   schema (roadmap deferred list); multi-device sync substrate (not yet needed);
   live provider/Chrome execution tooling (M2 live corridor is BLOCKED and
   owned through CFA-06/CFA-04 gates); any second identity/authority/ontology
   registry.

## 2. Design decisions the Steward should know

1. **Two rooms, not one.** §8.11's ATTENTION message lives in a dedicated
   `s3-attention-<run>` room so §8.6 keeps its exact length-2 shape
   (observation + reply) for a clean F4. Both rooms name the run; procB finds
   both by fold and asserts membership ⊇ {S3-ALPHA, S3-BETA}.
2. **Sender-side inbox visibility.** A raw DM is NOT in the sender's inbox
   under current `inbox()` semantics (recipients=[B], no membership), so §8.11
   uses a ROOM message mentioning B: visible in A's inbox (member,
   outbox-side view) and B's inbox (member + mention). B's ack reply is likewise
   room-visible both ways post-sync. F11 is closed across three checkpoints:
   A-init inbox (attention present), B inbox (attention + reply present),
   A-verify inbox post-resync (both present).
3. **Deliberate fold asymmetry.** procA/init exits BEFORE procB runs, so A's
   fold ⊂ B's fold by construction. Step (4a) `compareEvidence` asserts
   SUPERSET (B misses zero A keys — F3/F6), never equality; equality is asserted
   only by step (4b) `procA --phase verify` after re-sync. The compare also
   asserts A's init inbox correctly PREDATES B's reply (ordering check), so a
   forged equality cannot pass silently.
4. **No settle window.** Execution is strictly sequential (A completes, then B),
   and local git push-then-fetch is synchronous — no sleeps/polls exist in the
   harness (anti-hang). F11's "settle window" is satisfied by ordering, noted here.
5. **Identity fork guard.** Both procs call `loadOrCreateIdentity` with
   `{repoRoot, remote: s3remote, branch}` so a re-run against a non-fresh bare
   remote fails closed (`COMMONS_IDENTITY_ALREADY_PUBLISHED`) instead of
   forking. S.3b must use a FRESH `$S3\remote.git` (step 1 creates it).

## 3. Confirmed K0 duty set

### K0-1 — Admission and integrity
Only an explicitly admitted, verifiable composition may enter execution.

The constitutional mechanism covers the minimum verification needed for signed Recipe admission, manifest/content integrity, trusted identity/signature checks and fail-closed refusal of unverifiable composition.

Composition authoring and compilation remain outside K0.

### K0-2 — Compartment and transport boundary
Every admitted guest executes through the governed compartment/Port boundary appropriate to its runtime tier.

Worker/Port isolation is the established current mechanism. It does not by itself prove process-level or OS-level hostile-code containment.

### K0-3 — Capability egress and runtime fencing
The runtime independently enforces that a guest may exercise only capabilities structurally granted to it.

This includes token validity, token ownership, scope matching, revocation and generation/lifetime fencing where required.

Capability meaning, provider meaning and routing remain outside K0.

### K0-4 — Generic authority-gate enforcement
Where a consequential effect is required to pass a configured Authority gate, the runtime enforces that mechanical gate so guest code cannot bypass the policy boundary.

CFA-04 owns permission meaning, consent, standing, delegation, scope, duration, revocation semantics and policy/risk interpretation.

### K0-5 — Atomic activation and fail-closed recovery
Partially verified state cannot become active; activation crosses the defined atomic durability boundary; invalid incoming state falls back to known-good or refuses; replacement/recovery cannot bypass admission and fencing.

Compatibility and change meaning remain with CFA-09 and the owning domains.

### K0-6 — Generic lifecycle containment
The runtime enforces the minimum create/start/ready/stop/crash/recover lifecycle necessary to keep admitted execution inside the governed boundary.

Scheduling economics, queue policy and product orchestration are not K0 by default.

### K0-7 — Minimum integrity/platform primitives
Only generic crypto, canonicalization, hashing, atomicity and owner-scoped platform primitives proven necessary to support the constitutional duties remain K0 candidates.

Vault format, credentials UX and product storage/key-file policy are not constitutional merely because the current host implements them.

## 5. State / Graph / Grant / Generation minimums

These are **reduction experiments, not settled K0 subsystems**.

### State
Target minimum: a generic compare/fence/lease-style primitive sufficient to prevent a universal unsafe concurrent transition.

### Graph
Target minimum: the smallest host-owned lookup required to resolve a uniquely admitted implementation. Broader graph analytics remain outside K0.

### Grant
Target minimum: independently verifiable grant integrity/provenance sufficient to prevent a fabricated capability edge from entering trusted runtime state. The full history store is not thereby promoted.

### Generation
Target minimum: a call-lifetime target pin that keeps an in-flight invocation bound to the already authorized implementation generation. The full registry/range-resolution system remains experimental.

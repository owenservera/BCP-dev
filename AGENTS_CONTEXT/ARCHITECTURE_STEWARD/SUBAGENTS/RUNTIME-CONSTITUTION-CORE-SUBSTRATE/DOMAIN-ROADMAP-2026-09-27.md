# CFA-10 — Strategic Domain Roadmap
## Strategic Objective

Make VIVIM's runtime constitution a small, domain-neutral, independently enforceable safety boundary through which every admitted composition must pass, while preserving product meaning, canonical data, authority semantics, realization semantics, Work semantics, composition semantics, experience and evolution governance in their owning CFAs.

The destination is not “finish the host.” It is:

\`verify/admit → isolate/transport → enforce egress/authority fence → invoke → contain lifecycle → atomically activate/replace → recover/fail closed\`

with every K0 claim backed by an explicit invariant, named bypass, minimum enforcement mechanism, reproducible falsifier and clear K0/K1/plugin/tooling placement.

## Responsibility Frontier

### K0 owned by CFA-10

1. Admission and integrity.
2. Compartment and Port transport.
3. Capability egress, revocation and runtime fencing.
4. Mechanical enforcement of required Authority gates.
5. Atomic activation and fail-closed recovery.
6. Generic lifecycle containment.
7. Only crypto, canonicalization and platform primitives proven necessary to support the above.

### Explicit non-scope

CFA-01 owns World/Ontology/Context meaning.
CFA-02 owns canonical Data/Identity/Persistence and remains PROVISIONAL.
CFA-03 owns Semantic Continuity, language, grounding and Intent/Plan meaning.
CFA-04 owns Authority, permission, consent, standing and delegation semantics.
CFA-05 owns Work, Attempts, scheduling/background continuity, Outcome and execution reconciliation.
CFA-06 owns Capability, Provider, Account, Model, Session, Realization and Routing semantics.
CFA-07 owns Composition, Plugin and Forge semantics, candidate generation and promotion meaning.
CFA-08 owns Experience, Interaction, Surface and presentation/projection.
CFA-09 owns Change, Compatibility, Migration, Rollback and Self-Maintenance governance.

CFA-10 does not equate K0 with \`host/src\`, and does not create a second authority, data, provenance, ontology, identity or communication system.

## Current Evidence / Maturity

### OBSERVED / CURRENT

- B1 requires signed Recipe admission and hash-covered content before execution.
- B2 provides Worker-thread/V8-isolate compartments and Port transport, while explicitly not proving process/resource-exhaustion containment on Bun.
- B3 verifies capability tokens host-side, including ownership/scope/revocation; revocation is generation-based.
- B4 verifies incoming state, pins only after verification, preserves a known-good pinned recipe and fails closed when pinned state is corrupt.
- B5 caps \`host/src\` at 1,500 LOC with zero headroom; future host growth requires removal.
- \`bootPhase 0\` remains assigned to \`vivim.law\`.
- D-456 makes Chrome master/slave the shippable-v1 substrate and removes AI-API/local-model sequencing from the live product plan.
- Current host still mixes constitutional mechanisms with responsibilities that are not proven irreducible K0.
- B1 executable-entry confinement remains underproven.
- Zero-plugin/diagnostic boot remains a target rather than a proven current mode.
- State/Graph/Grant/Generation remain reduction experiments.
- First-party/extension symmetry remains underproven.
- Active Work replacement remains underproven.
- A stronger OS/process containment claim is not established.

### DERIVED / CURRENT

- K0 membership follows universal non-bypassability and domain-neutrality, not implementation location or product importance.
- B5 is a strategic reduction constraint.
- Zero-plugin boot tests whether product semantics have leaked into the substrate.
- The runtime may pin the implementation being executed without owning Work, Provider, Composition or Evolution semantics.
- The roadmap should seek the minimum viable constitutional kernel, not a complete runtime framework.

### UNKNOWN / CURRENT

- Exact B1 entry-confinement primitive.
- Minimum State primitive.
- Minimum Graph/Grant representation.
- Minimum Generation split between admission-time and call-lifetime state.
- Generic bootstrap-role shape compatible with current law.
- Owner-scoped platform/secret seam.
- Required security tier for hostile extension/resource-exhaustion containment.
- Live active-Work replacement contract.
- Exact CFA-02 atomicity/integrity join.
- Final K0 size after safe extraction.

### CONFLICTED / CURRENT

No direct peer ownership contradiction is established. There is one explicit constitutional design tension: a generic signed bootstrap role may be attractive for reduction, while current Ω law still assigns bootPhase 0 to \`vivim.law\`. That tension is a reconciliation question, not permission to change law.

## Conceptual Roadmap

### M1 — Executable Constitutional Boundary & Evidence Closure

**Conceptual outcome**

Every K0 duty has a traceable invariant, bypass, minimum mechanism and falsifier; the highest-risk admission gap, B1 executable-entry confinement, is either proven or reduced to a precisely bounded unknown.

**Why it matters**

Later reduction cannot be trusted if the thing being reduced is not defined at the executable-entry and admission boundary.

**Evidence basis**

Current B1–B5 law; Recipe/boot/recovery/token/lifecycle implementation; hermetic bootstrap verifier; Core-vs-Plugin Pass-3 evidence.

**Current maturity**

PARTIAL — admission, egress, activation/recovery and lifecycle have strong evidence; B1 and final host reduction are incomplete.

**Design choices**

- Exact relation between Recipe entry, manifest entry, source-tree containment and executed bytes.
- Required refusal behavior for traversal, absolute, out-of-tree and hash-mismatch entries.
- Which checks are K0 versus gate/tooling-only.
- Proof threshold for calling a runtime invariant universal.

**Success criteria**

Design validity: every retained K0 duty maps to a universal invariant and concrete bypass.

Implementation validity: adversarial B1 cases refuse; successful execution is traceably tied to integrity-covered bytes; B5 remains satisfiable.

Integration: runtime handoffs remain generic and semantic meaning stays in owning CFAs.

Proof validity: the corpus replays from a clean checkout and preserves UNKNOWN instead of upgrading absence of evidence to proof.

**Falsifiers / failure conditions**

- Any out-of-tree or hash-mismatched entry executes.
- Executed bytes cannot be tied to the admitted integrity boundary.
- A K0 check requires product semantics.
- Host growth occurs without equal-or-greater removal.

**Prerequisites**

Current Ω B1–B5 and existing runtime evidence.

**Dependencies**

Composition/Recipe semantics from CFA-07; capability egress from CFA-06; Authority gate contract from CFA-04; Work invocation boundary from CFA-05; change/evidence semantics from CFA-09; CFA-02 only for any claimed canonical-persistence atomicity.

**Candidate implementation later**

A deterministic B1 adversarial fixture/gate and compact K0 invariant/falsifier matrix.

**Remain unresolved**

Generic bootstrap role, OS containment, minimum State/Graph/Grant/Generation and active Work replacement.

### M3 — Governed Lifecycle, Atomic Replacement & Recovery

**Conceptual outcome**

Admitted implementations can be started, contained, fenced, replaced and recovered without K0 acquiring Work, Provider, Composition or Evolution meaning. Active Work receives explicit runtime termination/replacement facts rather than a fabricated semantic Outcome.

**Why it matters**

Safety must hold across time, not only at boot. Replacement is where generation, authority, capability and Work semantics most often collapse.

**Evidence basis**

B4 recovery/pinning, Worker lifecycle, generation fencing, current Evolution/Work contracts.

**Current maturity**

PARTIAL — boot/recovery evidence is strong; active Work replacement remains unproven.

**Design choices**

- Runtime lifecycle state machine.
- In-flight generation pin.
- Fence ordering relative to activation.
- Runtime→Work termination/replacement handoff.
- Runtime→Evolution compatibility/recovery handoff.

**Success criteria**

The old generation is fenced before the new active generation can perform governed effects.

Corrupt/unverified replacements never become active.

An interrupted attempt is not silently converted into Work completion.

Runtime recovery exposes facts needed by Work/Evolution without deciding their semantics.

**Falsifiers / failure conditions**

- Old and new generations can both act past the fencing point.
- Runtime invents a semantic Outcome.
- Replacement requires understanding provider or Work meaning.
- Corrupt replacement becomes active.

**Prerequisites**

M1 and M2.

**Dependencies**

CFA-05 is primary; CFA-09 is primary for compatibility/rollback; CFA-04 and CFA-06 provide live authority/capability constraints.

**Candidate implementation later**

Fault-injection lifecycle/replacement harness.

**Remain unresolved**

External-effect reconciliation is Work-owned; semantic rollback is Evolution-owned.

Three tests are coupled here:

1. valid empty/diagnostic state;
2. first-party/extension symmetry;
3. truthful isolation/resource-exhaustion tier.

**Why it matters**

These distinguish a genuinely generic K0 from a product shell disguised as K0.

**Evidence basis**

Everything-is-a-Plugin constitution; current Worker/Port claim; composition symmetry research; current \`vivim.law\` rule; D-456 product substrate context.

**Current maturity**

UNDERPROVEN / PARTIAL.

- Generic signed bootstrap role compatibility.
- Explicitly justified trust-tier differences, if any.
- Required process/OS containment under the actual extension threat model.
- Meaning of “same governed path.”

An empty diagnostic state exists without product-domain capability requirements.

System and extension plugins use the same admission, egress, Authority-gate and lifecycle barriers unless an explicit trust-tier rule says otherwise.

- First-party code bypasses a gate without an explicit, machine-visible trust rule.

## Product / Strategic Consequences

A successful CFA-10 destination provides the stable constitutional floor underneath VIVIM:

- new capabilities, providers and plugins can evolve without enlarging trusted runtime by default;
- provider/account/model selection remains product/domain semantics rather than kernel policy;
- Work can survive replaceable workers and generations without runtime becoming the Work store;
- Forge can generate candidates without a privileged runtime admission path;
- first-party VIVIM behavior can demonstrate the same governed membrane expected of extensions;
- surfaces can show runtime state without becoming canonical truth;
- self-maintenance can activate only verified/fenced replacements;
- Chrome-only v1 remains a product realization constraint, not a hardcoded provider meaning in K0.

Failure to reach this state leaves every future extension exposed to undocumented host assumptions.

## Owner goal (quoted verbatim)

> Our local machine agent team just transitioned from webapp-only commit/push to
> FULL LOCAL MACHINE ACCESS. Identify the TOP 10 TOOLS we must set up to become
> a fully efficient, state-of-the-art, autonomous goal-execution team.

Semantics: per-domain tool substrate for full-machine access; the authority
surface is radically expanded versus webapp-only commit/push.

## Why full machine access changes the authority problem

Webapp-only commit/push confined consequential effects to one narrow,
human-observed channel (repository writes). Full local machine access adds, at
minimum: arbitrary process execution, filesystem-wide read/write, OS/shell
integration, credential and secret stores, network egress beyond the previous
allowlist, background/daemon persistence, and cross-application actuation. Each
is a new effect class requiring its own authority basis, scope, expiry, and
revocation path. Under CFA-04 invariants: capability ≠ authority —
the fact that the team *can* now touch the machine says nothing about what it
*may* do, for whom, under what live basis. Every tool below is ranked by how
much it shrinks the gap between "can" and "provably may, with live,
revocable, reconstructable permission."

## Rationale (why this ranking, from the CFA-04 lens)

1. **Enforcement first, semantics second, convenience last.** Rank 1 is the only
   item that can convert the other nine from advice into guarantees; hence it
   leads despite being the most CFA-10-dependent.
2. **Time is the new threat.** Webapp sessions were short; autonomous machine
   agents persist, retry, resume, and work in the background. Ranks 2, 3, 7, 9
   all answer one fact: authority decays with time, and only live re-resolution
   detects the decay.
3. **No second stores.** Ranks 2, 4, 5, 9 deliberately reuse existing homes
   (Commons streams, Work/Attempt records, vault resolution) as citation
   carriers rather than building a permissions database, a security store, or
   an authority graph — all explicitly unjustified by the CFA-04 roadmap.
4. **Custody before scale.** Rank 6 (identity/rotation) gates safe scaling: ten
   autonomous agents with unrotatable keys multiply the blast radius of any
   compromise across every other tool.
5. **Verification closes the loop.** Ranks 4, 8, 10 convert autonomous activity
   into inspectable, verifiable, human-governed behavior — the product promise
   of trustworthy automation.

  spawn nothing. OWNER-DELEGATION.md is active and names exactly the ten CFAs.
- **DERIVED:** the ten tool classes above follow from mapping the roadmap's M1–M5
  contract needs against the expanded machine effect surface; ranking follows
  the enforcement → liveness → custody → verification logic in Rationale.
- **PROPOSAL:** every ranked row's setup note; none is authorized work until
  gated (CFA-04 authority gate + CFA-09 safe envelope) and, where mechanical,
  CFA-10-verified.
- **UNKNOWN:** which OS-native sandbox mechanism the owner will accept; exact
  secret-store and vault choices (not CFA-04's to make); per-tool allowlist
  contents; autonomy-radius defaults (owner policy); whether the ten-name spawn
  restriction ever becomes mechanical (pending opencode version support).

today. They are documented, prompted, receipt-checked procedural controls.

enforcement requires CFA-10 verification against the installed runtime plus a
wired name-scoped permission mechanism, evidenced by exact commit/ref — never
by prompt text alone.

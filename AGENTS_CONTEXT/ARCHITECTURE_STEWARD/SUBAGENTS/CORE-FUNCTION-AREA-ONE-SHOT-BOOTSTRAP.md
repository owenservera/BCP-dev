# CFA-05–10 — One-Shot Core Function Area Bootstrap

> Status: DERIVED / PROPOSED from completed CFA-01–04 Round-2 cycle
> Date: 2026-09-27
> Scope: birth/bootstrap procedure only
> Authority: process contract; not Ω law and not CFA authority

## Prime rule

One-shot means **one launched prompt carries the full bootstrap lifecycle**.

It does **not** mean one stage.

`FULL CONTEXT → SELF-DESIGN → OWNER DIALOGUE → ALIGNMENT → CORE AGENT IDENTITY → COMMONS TEST → EXECUTION`

Do not skip the Owner Dialogue / Alignment gate merely because the prompt is launched once.

## Inputs

Before design, read:

1. `/AGENTS.md`
2. `/BUILD_CONTEXT.md`
3. `/AGENTS_CONTEXT/README.md`
4. Architecture Steward foundation, README, STATE, operating model and relevant canonical/ownership artifacts
5. `AGENTS_CONTEXT/ARCHITECTURE_STEWARD/SUBAGENTS/README.md`
6. `AGENTS_CONTEXT/ARCHITECTURE_STEWARD/SUBAGENTS/CORE-FUNCTION-AREA-REGISTER.md`
7. all CFA-01–04 durable identity/state/boundary artifacts
8. all CFA-01–04 Round-2 addenda
9. `AGENTS_CONTEXT/ARCHITECTURE_STEWARD/BOUNDARY-DESIGN-SYSTEM/ROUND-2-COMPLETION-AUDIT-2026-09-27.md`
10. relevant destination/Ω evidence
11. `AGENTS_CONTEXT/AGENT-COMMONS/` constitution, transport and bootstrap guidance
12. the current CFA-specific `LAUNCH-PROMPT.md` as **domain seed, not proof of identity**

Classify substantive claims as:
`OBSERVED | DERIVED | PROPOSED | UNKNOWN | CONFLICTED`

Preserve freshness separately:
`CURRENT | STALE | UNRESOLVABLE`

## Phase 1 — Self-design

Produce an evidence-backed candidate design containing:

- candidate CFA name and machine-safe slug;
- central architectural question;
- smallest coherent mission;
- scope;
- explicit non-scope;
- responsibilities;
- inputs;
- outputs;
- peer interfaces;
- decision rights;
- durable workspace;
- alternatives considered;
- major unknowns;
- why this deserves a standing agent.

Do not treat folder name, register label, seed prompt or historical implementation as proof.

## Phase 2 — Owner Dialogue / Alignment gate

Present the self-design to the human owner.

Explicitly challenge:

- identity/name;
- scope and non-scope;
- neighboring ownership;
- decision rights;
- possible split/merge/move;
- questions requiring owner intent rather than archaeology.

**STOP before creating `CORE-AGENT.md` until alignment is supplied.**

An identity may remain provisional when the owner has not aligned it.

## Phase 3 — Durable identity

After alignment, create/update as appropriate:

- `CORE-AGENT.md`
- `README.md`
- `STATE.md`
- identity history/change record
- launch wrapper only if the birth protocol itself needs correction

`CORE-AGENT.md` is a responsibility contract, not Ω law.

## Phase 4 — Commons birth test

After identity creation:

1. read local `COMMUNICATION-HOW-TO.md`;
2. read `AGENTS_CONTEXT/AGENT-COMMONS/SESSION-CAPABILITY-AND-TRANSPORT.md`;
3. determine the real transport available;
4. publish one self-authored PUBLIC introduction;
5. read it back by message ID;
6. verify stable attribution and recoverability;
7. verify replay/projection preserves epistemic status;
8. record message ID and verification result.

Never mint a replacement identity to make the test pass.

Commons is communication infrastructure, not authority.

## Phase 5 — Domain execution

Only after identity alignment/creation:

- execute the CFA-specific mission;
- preserve peer ownership;
- keep evidence and freshness explicit;
- record unknowns/conflicts rather than normalizing them away;
- do not activate shared boundaries;
- do not rewrite Ω law;
- do not create a second ontology, authority store, universal identity registry or architecture graph.

## Completion gate

Persist a bootstrap report containing:

- final/provisional CFA name;
- agent identity status;
- workspace;
- aligned scope/non-scope;
- peer interfaces;
- remaining UNKNOWN / CONFLICTED / DEFERRED items;
- evidence index;
- Commons message ID + verification;
- durable identity commit SHA;
- substantive artifacts produced;
- what was not activated/ratified.

Do not say COMPLETE merely because files exist.

## Process-resolution hierarchy

When the protocol itself leaves a procedural question unclear, resolve in order:

1. direct repository evidence;
2. completed CFA-01–04 precedent;
3. CFA Register;
4. narrowest defensible interpretation;
5. human-owner escalation.

Record which level was used.

## Process anti-faking rule

Never claim an operation succeeded without observed evidence.

If transport, signing, tooling, runtime, permissions or network access are unavailable, record the limitation explicitly and continue only where the remaining work is honest.

## Resume rule

If a session ends unexpectedly, resume from durable repository state rather than restarting blindly.

At minimum inspect:

- existing bootstrap artifacts;
- latest commit;
- current identity status;
- last completed phase;
- remaining phase;
- owner-alignment state;
- Commons verification state.

Do not overwrite historical evidence merely to make the bootstrap look continuous.

## Completion vocabulary

Use only these implementation/bootstrap states where applicable:

- DESIGNED ONLY
- IMPLEMENTED + UNVERIFIED
- IMPLEMENTED + PARTIALLY VERIFIED
- IMPLEMENTED + VERIFIED
- BLOCKED
- UNKNOWN

## Change rule

If a problem is domain-specific, change the CFA parameter/seed.

If it recurs across multiple CFA births, propose a protocol change.

If it is a peer-boundary problem, route a bounded reconciliation.

If it is owner intent, return to Owner Dialogue.

Do not modify this shared protocol merely to accommodate local implementation convenience.

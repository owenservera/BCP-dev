# CFA-05–10 — One-Shot Core Function Area Bootstrap Protocol Design

> Date: 2026-09-27
> Status: DERIVED / PROPOSED — produced only after CFA-01–04 Round-2 completion audit
> Scope: reusable birth protocol for CFA-05 through CFA-10
> Authority: not Ω law, not a CFA identity, not an activation mechanism

## 1. Purpose

The repository now contains enough evidence to replace repeated bespoke bootstrap instructions with one reusable self-contained birth protocol, parameterized by CFA identity, workspace, domain seed and peer seams.

**One-shot does not mean one-stage.** One launched prompt must carry the full bootstrap lifecycle, while preserving the hard stops that proved useful in CFA-01–04:

FULL CONTEXT → SELF-DESIGN → OWNER DIALOGUE → ALIGNMENT → CORE AGENT IDENTITY → EXECUTION

The prompt may therefore be launched once, but it must not silently skip the owner-alignment gate or self-ratify an identity.

## 2. Round-2 lessons incorporated

### Proven by CFA-01–04 experience

1. Repository state is the durable cross-session memory; later agents should read completed peer addenda rather than inherit summaries.
2. Peer claims remain peer claims until the other side explicitly answers the same bounded question.
3. Ownership is multidimensional: meaning, durable representation, authority, execution and realization can belong to different CFAs.
4. Evidence state and freshness are orthogonal and must remain explicit.
5. Minimum handoff contracts are more reusable than prescribing internal implementations.
6. A seam can be reconciled while implementation or policy remains unknown/deferred.
7. Shared-boundary activation is a separate Steward decision; bootstrap agents do not activate their own cross-CFA boundaries.
8. Durable citations and live decisions must remain distinct where time, expiry or revocation matter.

### Rejected or premature

- automatic identity ratification;
- automatic boundary activation;
- universal identity/Event/State registries created from terminology overlap;
- numeric quality scores or rankings for CFAs;
- turning a reusable bootstrap into a second architecture authority;
- implementation-first work used to conceal unresolved ownership.

## 3. One-shot prompt structure

Every CFA-05–10 launch should contain these sections in this order.

### A. Mission envelope

- exact CFA ID and candidate name;
- exact candidate workspace;
- current launch-prompt path used as domain seed;
- explicit statement that the named identity/scope is provisional;
- repository and date;
- direct-main delivery rule for durable bootstrap artifacts.

### B. Prime directive

The first task is to discover the smallest enduring architectural responsibility that deserves a standing CFA agent, including what it owns, what it does not own, and how it interfaces with peer areas.

The prompt must explicitly state:

Do not treat the folder name, candidate mission or previous artifacts as proof of final identity.

### C. Full-context recovery

The single prompt must require reading, as applicable:

- AGENTS.md;
- BUILD_CONTEXT.md;
- AGENTS_CONTEXT/README.md;
- Architecture Steward foundation, state and operating model;
- SUBAGENTS/README.md;
- CORE-FUNCTION-AREA-REGISTER.md;
- all existing CFA-01 through CFA-04 durable identity/state/boundary artifacts;
- CFA-01 through CFA-04 Round-2 addenda;
- ROUND-2-COMPLETION-AUDIT-2026-09-27.md;
- relevant destination documentation;
- relevant Ω contracts and implementation evidence;
- relevant historical/legacy evidence;
- Agent Commons constitution, protocol, identity/trust and bootstrap guidance;
- the current domain-specific launch prompt as a seed, not an anchor.

The agent must classify what it finds as OBSERVED, DERIVED, PROPOSED, UNKNOWN or CONFLICTED and preserve CURRENT, STALE or UNRESOLVABLE freshness where relevant.

### D. Self-design

Before durable identity creation, the agent must produce an evidence-backed candidate design covering:

- candidate identity and machine-safe slug;
- central architectural question;
- smallest coherent mission;
- scope;
- explicit non-scope;
- responsibilities;
- inputs and outputs;
- peer interfaces;
- decision rights;
- durable workspace;
- alternatives considered;
- major unknowns;
- why this deserves a standing agent rather than only an investigation instrument.

### E. Owner dialogue gate

The prompt must instruct the agent to stop for substantive owner alignment before creating CORE-AGENT.md.

Owner dialogue should challenge:
- name and identity;
- scope/non-scope;
- neighboring ownership;
- decision rights;
- whether the responsibility should split, merge or move;
- which repository uncertainties require owner intent rather than further archaeology.

The owner dialogue is architecture work, not a ceremonial sign-off.

### F. Durable identity gate

Only after alignment may the agent create/update:
- CORE-AGENT.md;
- README.md;
- STATE.md where warranted;
- identity history/change record;
- launch prompt only when the birth protocol itself needs correction.

CORE-AGENT.md must remain a responsibility contract, not Ω law.

### G. Commons birth test

After identity alignment and creation, the agent must perform the existing Commons bootstrap test:

1. read the local communication guide and shared transport contract;
2. publish one self-authored PUBLIC introduction;
3. read it back by message ID;
4. verify stable attribution and recoverability;
5. verify replay/projection preserves epistemic status;
6. record the message ID and verification in the bootstrap report.

Never mint a replacement identity merely to make the communication test pass.

### H. Function-area execution

Only after identity creation may the agent execute its substantive domain mission.

Execution must continue to use the common evidence vocabulary and must preserve peer ownership. The agent may investigate, characterize, recommend, challenge and reconcile within scope, but must not silently acquire another CFA’s semantic, authority, canonical-data or runtime responsibility.

### I. Completion gate

The one-shot prompt must end with a machine-checkable report containing:

- final CFA name and agent identity;
- workspace path;
- aligned scope and non-scope;
- peer interfaces;
- remaining UNKNOWN / CONFLICTED / DEFERRED items;
- evidence index;
- Commons introduction message ID and verification result;
- durable identity commit SHA;
- implementation or mission artifacts produced;
- explicit statement of what was not activated or ratified.

Do not report “complete” merely because files exist.

## 4. Boundary-control rules embedded in every launch

- Do not activate shared boundaries.
- Do not rewrite Ω law.
- Do not self-ratify a provisional/proposed identity.
- Do not turn evidence into authority merely because it is durable or signed.
- Do not turn representation into canonical meaning merely because it is persistent.
- Do not turn capability into permission.
- Do not turn visibility/accessibility into existence or authorization.
- Do not normalize UNKNOWN or CONFLICTED into agreement.
- Do not create a second ontology, authority store, universal identity registry, or architecture graph.
- Do not create implementation merely to close a bootstrap checkbox.

## 5. Peer-context rule for CFA-05–10

Every one-shot launch reads the current CFA-01–04 Round-2 completion audit before domain design.

The agent should inherit **context, not conclusions**:

- reconciled seam facts may be used as current peer evidence;
- remaining UNKNOWN items stay unknown until the new CFA has evidence to resolve them;
- DEFERRED items remain deferred until the named later dependency exists;
- the agent must not silently reopen completed CFA-01–04 work unless new evidence creates a concrete boundary challenge.

## 7. Parameter rules

The reusable prompt should substitute only:

- CFA_ID;
- CANDIDATE_AREA;
- AGENT_SLUG;
- WORKSPACE;
- DOMAIN_SEED;
- PRIMARY_PEERS;
- DOMAIN_SPECIFIC_READ_SET;
- DOMAIN_SPECIFIC_COMPLETION_TESTS.

Everything else should remain structurally identical across CFA-05–10 so the birth process is comparable and auditable.

## 8. Sequencing rule

The one-shot protocol itself is reusable and independent, but execution remains owner-routed.

Recommended operational sequence remains the existing register order:

CFA-05 → CFA-06 → CFA-07 → CFA-08 → CFA-09 → CFA-10

This is sequencing for context accumulation, not authority ordering. The owner may launch independent sessions in parallel when the required peer context has already been made durable.

## 9. Output architecture

The next implementation of this design should consist of:

1. one canonical reusable protocol document;
2. six thin parameterized launch prompts or wrappers, one per CFA;
3. a router table containing exact prompt paths and required predecessor artifacts;
4. no duplicated bespoke lifecycle logic across the six prompts.

The existing domain launch prompts remain valuable domain evidence and should be preserved. The one-shot layer should wrap or supersede only the **birth-procedure duplication**, not erase domain-specific research content.

## 11. Safety against process drift

When a CFA-05–10 launch produces a novel problem, classify the failure before modifying the shared protocol:

- domain-specific issue → fix the CFA-specific parameter/seed;
- repeated birth-process issue → propose a protocol change;
- peer boundary issue → create a bounded reconciliation question;
- owner-intent issue → route to owner dialogue;
- implementation issue → do not rewrite the birth protocol merely to accommodate local code.

The reusable protocol is therefore a birth contract with controlled evolution, not a universal architecture script.

## Core model already settled

### VIVIM is a compositional factory, not one fixed application

- **Ω is the current best realization of the Lego factory.**
- Earlier VIVIM variants are **proven prototypes**: imperfect and often not composable, but containing mature behavioral, UX, provider, and product intelligence.
- The destination is an **ecosystem/composition model** through which each person can create a unique VIVIM instance.
- User environments are intentionally variable.

“Lego” is a conceptual metaphor for composability, reusable pieces, interoperability, composition/sets, authorship, and evolution. It is **not canonical ontology**.

Canonical architecture language remains:

\`Capability / Plugin / Contract / Composition / Object / Surface / Realization / Authority / Work / Evidence / Forge / Evolution / Product Instance\`

### Factory UX versus instance UX

Do **not** anchor the product to one fixed dashboard, workspace, or feature bundle.

Stable UX belongs primarily to the **factory**:

- discovery;
- addressing;
- understanding;
- composition;
- configuration;
- governance;
- inspection;
- creation;
- replacement;
- evolution;
- removal.

A user's workspace, surfaces, compositions and workflows are instance-level outcomes.

The product-building sequence is:

\`Ω factory → building language/interoperability → compelling first-party pieces → compositions → user-created pieces/sets → user-specific VIVIM instance\`

### User as ordinary creator/composer

There is no privileged developer mode.

The ordinary user should ultimately be able to create and evolve both:
- individual pieces/capabilities;
- compositions/sets of pieces.

The Personal Agent makes construction intelligible but does not gain special authority because the user is creating/modifying the environment.

### K0 is deliberately narrow

- **K0** = irreducible, domain-neutral, genuinely non-bypassable constitutional runtime mechanisms.
- **K1** = shared contracts / interoperability vocabulary / boundary protocol.
- **System plugins** = first-party VIVIM capabilities/semantics.
- **Extension plugins** = third-party and user capabilities.
- **Tooling** = out-of-tree development machinery.

Importance does not justify K0 promotion.

Current major Core obligations are:

1. executable-entry confinement;
2. generic empty-composition / bootstrap-role semantics;
3. minimal State / Graph / Grant / Generation mechanisms;
4. first-party / third-party runtime symmetry;
5. active Work continuation across replacement.

Use the invariant / bypass / minimality test.

# Coding-start cut line

A credible GO should trace a coherent path approximately like:

\`user → factory affordance/composition → address/intent → capability → realization → authority → durable Work where consequential → execution → evidence → canonical World update → persisted Product Instance → close/reopen continuity\`

The exact first composition may exercise a smaller subset, but it must demonstrate the **compositional factory principle**.

GO does not require all product domains, all providers, all Legacy harvest, all vertical slices, full autonomous evolution, or complete native Windows shell.

It does require that the first build not rest on an unresolved assumption likely to force redesign of the factory's fundamental boundary.

# Stop condition

Stop preparing when:

- factory boundary is sufficiently clear;
- building language is concrete enough;
- reference pieces are identified;
- first composition is traceable;
- factory UX invariants are clear;
- dangerous unknowns are resolved or explicitly bounded;
- E2E path is credible.

Then **coding is the experiment**.

Use:

\`FIND → SYNTHESIZE → DECIDE → BUILD → LEARN\`

not:

\`RESEARCH → DOCUMENT → RESEARCH → DOCUMENT\`

Do not start a third archaeology pass unless a concrete implementation finding proves an existing conclusion materially wrong.

### The Vivim System Vision: The Sovereign AI Substrate

Vivim is not a chat wrapper, nor a simple aggregator; it is architecturally defined as a **local-first AI conversation operating system**. It serves as a programmable substrate on which intelligent, composable, and privacy-preserving workflows execute entirely on the user’s machine (via a Tauri desktop shell and Bun runtime), requiring no central cloud account.

The philosophical core of the system is the concept of the **"Sovereign Mirror."** Vivim rejects the extractive, attention-harvesting models of hyperscalers, positioning itself as a tool for digital self-determination. It connects to external intelligence (ChatGPT, Claude, Gemini, DeepSeek, Qwen, Grok) while ensuring that the user retains absolute ownership of their data, memory, and execution environment.

---

### Core Concepts

The architecture is built upon several high-concept pillars that separate Vivim from standard AI applications:

*   **The Capability System:** This is the fundamental atom of the system. Every interaction—whether `send_message`, `select_model`, or `create_chat`—is defined as an atomic, typed operation called a **UnifiedCapability** (e.g., `cap:chat:send_message`). These capabilities are not hardcoded UI actions; they are abstract entities bound simultaneously to the CLI, API, UI, and MCP (Model Context Protocol).
*   **Atomic Cognitive Unit (ACU) & The Knowledge Graph:** Vivim models all domain objects (conversations, memories, agents) as **Nodes** within a graph. These nodes possess cryptographic provenance (`contentHash`), version chains, and weighted edges, forming a "cap-store" that natively captures the lineage and evolution of human-AI interactions.
*   **Natural Language Command Language (NLCL) & Reprogrammability:** The system is inherently mutable. It features a "closed mutation grammar" that allows users and agents to reshape the product’s interface and kernel behaviors at runtime using near-natural language. Every mutation is logged, versioned, and cryptographically verifiable.
*   **The Execution Kernel & Chrome Governor:** To interact with closed web-based providers, Vivim employs a specialized execution environment. The **Chrome Governor** manages the Chrome DevTools Protocol (CDP), acting as a secure, resilient bridge that "harvests" and "injects" data into provider interfaces when official APIs are unavailable or restrictive.
*   **Dual-DB Architecture:** A strict, forensic-level boundary exists between the **System Database** (configuration, provider seeds, capability registries) and the **User Database** (private conversations, semantic memory). This ensures that platform updates never compromise private user states.

---

### The Core Capability Vision

The vision for Vivim's capabilities is centered on **Unified Intent, Agentic Autonomy, and Surface Parity.**

1.  **Unified Intelligence & Resolution:**
    The user should never need to know *which* provider is handling a task or *how* the protocol works. The **Capability Resolution Engine** takes a natural language intent, translates it into a resolved capability with a confidence score, and routes it to the appropriate provider. Vivim includes specialized parsers for every major streaming format (SSE, `batchexecute`, reasoning deltas), making the underlying provider invisible to the user.

2.  **Agentic Autonomy (ActionPlan IR):**
    Vivim is designed to be an "Agentic Backbone." It utilizes an **ActionPlan Intermediate Representation (IR)** and a **Fleet Supervisor** to orchestrate multi-step, autonomous workflows. It can break down high-level goals, manage "slave" execution threads, handle circuit-breakers, and even "heal" broken selectors in browser automation without human intervention.

3.  **Surface Parity:**
    A defining capability of Vivim is that the "Surface" (where the user interacts) and the "Kernel" (where the logic lives) are perfectly synchronized. Any capability available to the AI agent is equally available to the user via the CLI or UI. This parity ensures that automation is transparent and controllable.

4.  **Self-Referential Knowledge (The Auto-Librarian):**
    The system is self-describing. Through a massive internal "Source Atlas" and "Librarian" engines, Vivim automatically generates and maintains its own documentation. It can answer "What am I?" and "Why was this decision made?" by querying its own architectural forensics, enabling a level of autonomous debugging and self-improvement rarely seen in desktop software.

In summary, Vivim’s vision is to provide a **hot-swappable, privacy-sovereign microkernel** where the user commands a fleet of AI capabilities through a unified, natural-language interface, all while maintaining a complete, cryptographic history of their digital thought process.

# Ω-9 · PROGRESSIVE ADAPTIVE DISCLOSURE — *The Aperture*

> **Decision record:** `D-433` *(next free ID; the content is what lands, not the number).*
> **Type:** Adaptation-Tier addition — **core, not plugin.**
> **Precedence:** extends the ratified stack. Where this conflicts with the gate, the gate wins.
> **Requires:** Ω-2 (`D-426`) green — disclosure spends budget. Ω-3 (`D-427`) green — disclosure emits sealed contexts. Ω-5 (`D-429`) green — efficiency is a measured fold.
> **Completes:** the Mind Spine's evolution from *assembler* to *aperture* — the "honest mirror" pointed at context flow.
>
> **The one invariant this upgrade exists to protect:**
> **The realization never reads the vault; it *requests*, and core *discloses*. Prediction may be probabilistic — disclosure is deterministic, gated, budgeted, and receipted.**

---

## 0 · The one sentence

> **Context is not poured; it is disclosed — progressively, adaptively, under the law, against the budget — so the model always has what it needs and never more than it's owed, and every byte it saw is a receipt.**

Ω-3 answered *"what did the model know when it said that?"* by sealing the context. Ω-9 answers the sharper version: *"what did it **ask for**, what were we **willing to give**, and what did it **actually use**?"* The context window stops being a bucket you fill and becomes a lens you open.

---

## 1 · What dies without this — and why it dies quietly

Ω-3 assembles context **in one shot, up front, under a static policy.** That single fact kills three properties the moment a task gets long or a window gets small:

1. **Efficiency dies.** Batch assembly faces a forced choice: *under-feed* (the model lacks what it needs → hallucinates) or *over-feed* (dilute attention, burn budget on rows the model never cites). Both are waste; one is dangerous.
2. **Adaptation dies.** A multi-turn agent's needs *evolve* across the turn. A static seed can't know at turn 1 what turn 7 will require. The policy is frozen; the task is alive.
3. **Honesty thins.** Ω-3 records what was *given*. But if the model *needed more and wasn't given it*, the hallucination that follows looks like a model failure when it was a **disclosure failure**. Without a disclosure trail, you can't tell the two apart.

**The silent failure mode:** the model answers confidently from a starved context, the user trusts it, and the receipt shows a full context that was never actually *used*. The glass house gets its curtained room back — this time the curtain is "we dumped everything and assumed it read it."

---

## 2 · Why this is core, and why a plugin can never do it

Ω-3's sovereignty argument generalizes into its sharpest form here:

> *A Forge can build a **recommender** — a relevance model, a prefetch heuristic, a compression style. It can never build the **aperture**.*

If a plugin controlled progressive disclosure, it would control **what the model learns next** — not just what it knows now. That is control of the system's *attention over time*, which is control of its reasoning trajectory. The layout engine (Ω-6) was core because it controls what the *user* sees first; the aperture is core because it controls what the *model* sees next. **Both are microphones no guest is allowed to hold.**

**The constitutional split — this is the whole design:**

| | Nature | Owner |
|---|---|---|
| Predicting what the model will need | **probabilistic** (ML), badged, sealed | a realization (a recommender) |
| Deciding to disclose it | **deterministic**, law-gated, budgeted | **core** (the aperture) |
| Recording what was disclosed | **deterministic**, ledgered | core |

The recommender *proposes*; the aperture *disposes*. Exactly the Ω-2 doctrine — *"the governor never outsources the decision"* — now applied to cognition. **Probabilistic prediction at the boundary; deterministic disclosure at the center.**

---

## 3 · The mechanism — how the aperture breathes

### 3.1 The seed + the disclosure manifest
Instead of filling the window, core assembles a **minimal seed** — the highest-relevance atoms — plus a **disclosure manifest**: a compressed map of what is *available but not yet revealed*.

```
SEED            (the few atoms the model starts with)
DISCLOSURE MANIFEST  (a table of contents for what it *could* ask for)
  ├─ [Ω-3 full decision doc]     relevance 0.92 · ~2.1k tokens
  ├─ [5 dissent rows]            relevance 0.88 · ~400 tokens
  ├─ [related Ω-2 budget ctx]    relevance 0.61 · ~800 tokens
  └─ [D-427 signature chain]     relevance 0.55 · ~120 tokens
```

The manifest is the decisive idea: **it lets the model know what it doesn't know — without consuming it.** The model sees pointers, relevance scores, and byte-cost estimates. Sensitive namespaces appear as *existence-only* entries ("a namespace here is sealed; request to learn if you may see it"), so the manifest never leaks structure it isn't allowed to.

### 3.2 Pull — the disclosure protocol
The model requests more through gated capability calls. Every request is law-gated, budget-claimed (Ω-2), sealed, badged, and ledgered — *then* disclosed.

- `ctx.drill@1` — deepen resolution on an atom already cited (zoom in).
- `ctx.expand@1` — broaden to related context (zoom out).
- `ctx.fetch@1` — request a specific known row/namespace (gated by scope + retention).
- `ctx.manifest@1` — re-query the disclosure map.

**The guest asks the librarian for a book. The guest never walks into the stacks.** This is Ω-3's inbound boundary — *the model consumes sealed context, never raw vault* — made *streaming and demand-driven* instead of batch.

### 3.3 Push-staging — adaptive prefetch
Core watches the model's consumption (what it drilled, cited, ignored) and a **badged recommender realization** predicts likely-next context. Core **pre-stages** those chunks into a ready buffer.

**Prefetch stages; it does not inject.** Staged context still crosses into the model's window only via a disclosure act — either the model pulls it, or an explicit low-risk policy permits auto-push. The prediction is ML-badged and sealed; the disclosure remains deterministic. When the recommender is later demoted, the user knows exactly which prefetches it shaped (Ω-7 lineage).

### 3.4 The need signal — explicit and implicit
The aperture adapts to *need*, detected two ways:
- **Explicit:** the model calls `ctx.drill` / `ctx.expand` / `ctx.fetch`.
- **Implicit:** uncertainty markers, repeated re-asks, "I don't have enough to answer" signals, citation gaps. A badged detector notices and **offers** disclosure — it never silently supplies.

### 3.5 The compression ladder
Every atom exists at multiple resolutions: `summary → key-facts → full-row`. Disclosure reveals at the *needed* resolution; the model can request deeper. This is the zoom lens — cheap summaries for orientation, full rows only when the task demands them.

### 3.6 The budget feedback loop
The Ω-2 governor sees disclosure as a **streaming claim**, not a one-time grant. If the model burns context inefficiently (drilling into low-value rows, expanding without citing), the governor can **tighten the aperture** — refuse further disclosure, or downgrade to summary-resolution — and tell the model *why* in a refusal sentence. Efficiency becomes a live constraint the model feels.

### 3.7 Adaptation memory — the consumption profile
Core builds a **per-realization consumption profile**: *"frontier-LLM-X drills into `ns.project-notes` on 8/10 summarization turns."* This profile:
- is a **sealed, badged, inspectable artifact** — never hidden tuning;
- is **evidence-based and reversible** — it cites the consumption rows that formed it;
- answers *"why did you prefetch that?"* with a receipt.

**Adaptation is not drift.** Every profile update is a ledgered, badgeable, queryable event. The system learns its guests' habits — and shows its work.

## 5 · Choicepoints

**CP-Ω9-A · Pull vs push.** *Decision: pull-first. Prefetch stages into a ready buffer but never injects without an explicit low-risk policy.* Push-into-window without a request is a watcher that acts — the exact violation Ω-1 refused, re-entering through the context door.

**CP-Ω9-B · The manifest's honesty vs leakage.** *Decision: sensitive namespaces appear existence-only; the manifest reveals structure only as far as the requester's scope allows.* The manifest must tell the model what it could know without telling it what it isn't allowed to know.

**CP-Ω9-C · Where adaptation lives.** *Decision: the consumption profile is a vault row, badged and inspectable; the recommender that shapes it is a realization; the aperture that acts on it is core.* No hidden weights, no silent tuning.

**CP-Ω9-D · Who sets depth.** *Decision: the model may request deeper resolution; the aperture grants it under budget and scope. Resolution is a grant, not a right.*

**CP-Ω9-E · Refusal of disclosure.** *Decision: the aperture refuses — sensitive namespace, budget exhausted, over-scope, retention-shredded — with a sentence, exactly as the Law gate refuses action.* A disclosure refusal is an ordinary boring event, ledgered.

## 1 · What dies without this — and why it dies silently

The constitution has the **event** as its atom, but exactly **one way to mint one**: a human types a turn. Remove that and the whole spatial/temporal promise collapses:

1. **Nothing hydrates on condition.** A ghost tile that should wake on home-Wi-Fi, a mic that should open on a voiceprint, a dead-man's switch, a budget alarm — all impossible, because there is no *watcher*, only *responders*.
2. **Headless is a lie.** "The canvas is a projection; remove it and the system still runs" (§3 falsifier F1) is only true if something keeps running while the pixels are gone. Without watches, closing the app stops the world.
3. **Every "watch" gets pushed into a plugin.** And a plugin that notices is a plugin that controls what the system responds to — a microphone no guest should hold. The thing-that-notices is a sovereignty surface.
4. **Automation has no honest origin.** Any "when X, do Y" built today must either poll (wasteful, leaky) or embed the action in the watcher (violating the law). Both die the moment you ask *"who authorized this, and what did it see?"*

The silent failure: an automation fires, the user asks *"why did that happen?"*, and there is no row — only a plugin's memory. The glass house gets its first curtained room.

## 2 · Why this is core, and why a plugin can never do it

> *A Forge can build a sensor — a parser, a poller, a stream-reader. It can never own the noticing.*

Control of **what the system notices** is control of **what the system ever responds to.** A watcher that can be quietly added, quietly scoped, and quietly fired is a backdoor with excellent paperwork. Three disciplines make it core:

- **Every watch is retention-named and budget-visible.** If we cannot say what it forgets and what it costs, we refuse to arm it.

## 3 · The mechanism

### 3.1 The watch row — `ns watch`
A watch is **vault data**, not renderer state. It survives the app, the device, and the decade. One namespace, sole writer **core**, append-only, retention-named.

```
watch {
  watchId        stable id, content-addressed
  principal      the sole authority who armed it (never a realization)
  source         vault | filesystem | time | device-state | external
  sourceScope    capability-scoped target:
                   vault        → namespace / predicate over rows
                   filesystem   → path glob, local only
                   time         → schedule / interval / deadline
                   device-state → named device condition (network, presence, sensor)
                   external     → realizationRef of a quarantined observer
  predicate      canonical, typed, deterministic condition
  grant          capability-grant token authorizing THIS source access
  onFire         mint-event                 // the ONLY permitted value
  retention      named retention rule for this watch AND its fired events
  badge          ProvenanceTier × generality
  state          armed | paused | disarmed
}
```

### 3.2 The fired event — the W-atom
When the predicate becomes true, core appends exactly one row. **This row is the entire effect of the watch.**

```
watch.fire {
  watchId, firedAt
  sourceSnapshotRef   evidence — byte-cited vault range / path hash / device-state hash
  predicateResult     the typed evaluation that went true
  realizationRef      (external only) which quarantined observer produced the claim
  // NO capability. NO action. NO side-effect. Just "this became true."
}
```

### 3.3 The five sources
| Source | What it notices | Sovereignty rule |
|---|---|---|
| `vault` | a row/namespace condition becoming true | reads vault read-only, scoped by grant |
| `filesystem` | a local path/glob changing | local only; never network paths |
| `time` | schedule, interval, deadline (dead-man's switch, end-of-day) | deterministic clock; no drift assumptions |
| `device-state` | network, presence, paired-device condition | sourced via Trust Mesh (Ω-4) device facts |
| `external` | an outside stream (blockchain, biometric, web) | **quarantined realization produces a *claim*; core validates and mints** |

### 3.4 Notice, don't act — the firewall
This is the load-bearing wall. A `watch.fire` event enters the **normal law pipeline like any other event**: some *separate*, law-gated composition may *choose* to respond to it. But:
- The watch holds **no capability to act.**
- The watch names **no action to take** (`onFire` has exactly one value: `mint-event`).
- Any automation "when X, do Y" is **two things**: a watch that notices X, and a composition that the law authorizes to do Y. They are separately consented, separately badged, separately revocable.

### 3.5 External observation — quarantine
An `external` watch needs eyes outside the machine, and realizations are untrusted. So:
- The **realization observes and produces a signed claim.** It never mints events and never reads the vault.
- **Core validates the claim** against the watch's predicate and grant, then mints the `watch.fire` row.
- The realization's badge rides the event (`realizationRef`), so a demoted observer scars every event it shaped (Ω-7 lineage, later).

*The guest may point at the window; only the librarian writes down what was seen.*

# Ω-10 · THE PARTIAL-TURN & STREAMING LEDGER — Amending the W5 Atom

---

## 0 · The one sentence

> **The W5 atom was defined as a completed circle; the physical world demands it be defined as a vector that can be severed, measured, and resumed without corrupting the spine.**

The base constitution states: *"a person types, a real streamed response comes back through the law gate, ledgered and queryable."* This assumes the turn *completes*. But in reality, networks drop, users click cancel, governors hit token ceilings mid-stream, and providers timeout. 

If a half-finished event has no defined ledger shape, three silent failures occur:
1. **The Ghost Turn:** The kernel doesn't know the turn happened until it's over. If it dies, the kernel is blind, and the UI hangs.
2. **The Budget Leak:** The Ω-2 governor claims a budget for a 2,000-token stream. The stream dies at 400 tokens. If the ledger doesn't record the abortion, the budget remains "locked" or is falsely counted as spent.
3. **The Context Hallucination:** On the *next* turn, Ω-3 (Context Assembly) looks at the history. If the aborted 400 tokens aren't explicitly marked as `[ABORTED: provider_timeout]`, the next model might try to "finish the thought" based on a truncated, meaningless fragment, hallucinating a continuation.

**Ω-10 makes the partial turn a first-class, ledgered citizen.**

---

## 1 · The Mechanism: Header + Terminal Folding

To maintain the append-only, sole-writer discipline of the vault without writing a row for every single streamed token (which would bloat the ledger and destroy write-throughput), Ω-10 introduces the **Init/Finalize Fold**.

A streaming turn is no longer a single row. It is a **span** defined by two mandatory ledger entries:

1. **`turn.init`**: Written the millisecond the law gate approves the intent and the Ω-2 governor grants the budget. It contains the sealed context hash, the claimed budget, the realization ID, and the principal.
2. **`turn.finalize`**: Appended when the stream ends (for *any* reason). It contains the `init` row's hash, the final token count, the terminal state, and the hash of the generated text.

**The Live State:** The "current" state of a turn is derived by folding `init + finalize`. 
- If `init` exists but `finalize` is missing, the turn is **`STREAMING`** (or `ORPHANED` if the kernel crashed and restarted, triggering an automatic governor reclaim).
- If `finalize` exists, the turn is permanently sealed in its terminal state.

---

## 2 · The Five Terminal States

Every `turn.finalize` row must carry exactly one of these terminal states. There is no "unknown" state.

| State | Trigger | Governor Action | Context Assembly (Ω-3) Behavior |
|---|---|---|---|
| **`COMPLETED`** | Provider sent EOF / stop sequence. | Budget settled to exact spend. | Full text included in future contexts. |
| **`ABORTED_USER`** | User clicked cancel / closed harness. | Unspent budget reclaimed immediately. | Partial text included, explicitly tagged `[USER_ABORTED]`. |
| **`ABORTED_GOV`** | Ω-2 hit token ceiling / time limit mid-stream. | Budget settled to max claim. | Partial text included, tagged `[BUDGET_EXHAUSTED]`. Next turn offered "continue". |
| **`FAILED_PROVIDER`** | Network drop, provider 5xx, timeout. | Unspent budget reclaimed. | Partial text included, tagged `[PROVIDER_FAILED]`. |
| **`REFUSED_MID`** | Law gate caught a violation in the *streaming* output (e.g., PII leak, injected command). | Stream killed. Budget reclaimed. | **Text redacted/zeroed.** Tagged `[LAW_REFUSED_MID]`. |

*Note on `REFUSED_MID`:* This is the ultimate proof of the Law Gate's streaming authority. If the model begins generating a secret it shouldn't, the kernel's streaming inspector kills the stream, discards the payload, and writes a `REFUSED_MID` finalize row. The model never finishes the thought; the user never sees the leak.

---

## 3 · Context Assembly of the Dead (The Resumption Protocol)

When Ω-3 assembles context for Turn $N+1$, and Turn $N$ was partial, it must handle the fragment deterministically:

1. **The Tag:** The partial text is never presented to the next model as "clean" history. It is wrapped in a system-level semantic tag: `<partial_turn status="FAILED_PROVIDER" tokens="412">...[text]...</partial_turn>`.
2. **The Resumption Anchor:** If the state is `ABORTED_GOV` or `FAILED_PROVIDER`, the `turn.finalize` row includes a `resumption_anchor` (a hash of the exact context state at the moment of death). 
3. **The Capability Op:** The user (or an agent) can invoke `turn.resume@1`. The kernel checks the anchor, re-seals the exact context from Turn $N$, and issues a new `turn.init` with a system prompt: *"Resume exactly from this anchor."*

This prevents the "context drift" problem where retrying a failed generation yields a completely different trajectory because the history was slightly altered.

| Op | The sentence it makes true |
|---|---|
| `turn.init@1` | The law gate approved, the governor granted, the stream begins. (Internal/Kernel only). |
| `turn.finalize@1` | The stream ended; here is the state, the spend, and the hash. (Internal/Kernel only). |
| `turn.abort@1` | The user or governor demands the stream stop *now*. |
| `turn.resume@1` | Re-invoke a partial turn using its exact resumption anchor. |
| `turn.inspect@1` | Query the live or finalized state of any turn by its init hash. |

3. **The Mid-Stream Law Kill:** Force the model to output a known banned regex (e.g., a simulated API key) via a rigged test prompt.

4. **The Crash Reclaim:** Kill the kernel process (`kill -9`) while a stream is active. Restart the kernel.
   - *Pass:* Kernel boots, scans for `init` rows without `finalize` rows, marks them `ORPHANED`, and reclaims all their budgets.

**Red** if any stream dies without a `finalize` row being written (or an orphan-reclaim on boot), or if a `REFUSED_MID` payload is readable in the vault.

# Ω-11 · APERTURE SIDE-CHANNEL & PROFILE PRIVACY — Governing the Negative Space

> **Decision record:** `D-443` *(follows D-442/Ω-10; renumber to the next free ID if consumed — the content is what lands, not the number).*
> **Type:** Constitutional Core Amendment — **Ω-9 (Aperture) Hardening & Privacy Substrate.**
> **Precedence:** Extends Ω-9 and the base Law Gate. Where this conflicts with the gate, the gate wins.
> **Requires:** Ω-9 (`D-433`) green — the aperture exists and must be hardened. Ω-4 (`D-428`) green — scope and principal boundaries must be enforceable against the model's inquiries. Ω-3 (`D-427`) green — context assembly policies must respect the redaction rules.
> **The one invariant this upgrade exists to protect:**
> **The system’s refusals and its memory of the model’s attention must never reveal more about the user’s vault than the user explicitly granted. The negative space of the vault is sovereign; the mirror must not build a shadow portrait.**

---

## 0 · The one sentence

> **Honesty demands we show the model what it is allowed to see; privacy demands we hide the shape of what it is not allowed to see — and we must govern our own memory of what the model looked at, lest the aperture become a surveillance engine pointed inward.**

Ω-9 built the Aperture: a progressive, adaptive disclosure engine that lets the model ask for context and lets core prefetch it based on a consumption profile. But in doing so, it opened two massive side-channels. First, a refusal to disclose a sensitive namespace *proves that namespace exists*. Second, the consumption profile — a record of what the model drills into, ignores, or asks for — is a high-fidelity behavioral portrait of the user. Ω-11 closes the side-channels and governs the portrait.

---

## 1 · What dies without this — and why it dies silently

Without Ω-11, the Aperture suffers from two silent sovereignty failures:

1. **The Oracle’s Leak (Existence Side-Channel):**
   A realization issues `ctx.fetch@1` for `ns.medical`. The aperture checks the grant, sees it is denied, and returns a refusal: *"Access to `ns.medical` denied."*
   *The leak:* The model now knows `ns.medical` exists, even if it cannot read it. If the model issues 1,000 dictionary-word namespace probes, the aperture's specific refusals map the entire hidden topology of the user's vault. The manifest (the table of contents) suffers the same flaw: listing a sensitive atom as `[SEALED]` reveals its relevance score and existence.

2. **The Shadow Portrait (Behavioral Inference):**
   Ω-9 builds a consumption profile to predict prefetches: *"This realization drills into `ns.finance` on 8/10 nights, and ignores `ns.journal`."*
   *The leak:* This profile is a highly sensitive behavioral inference about the *user*. If left ungoverned, it becomes an immortal, unscoped cache. A compromised or poorly badged realization could query the profile to deduce the user's habits, anxieties, or routines. Honesty (badging the profile) is not enough; the profile itself is sensitive data that demands retention and scope.

**The silent failure:** The system perfectly protects the *text* of the vault, but leaks the *shape* of the vault through its refusals, and leaks the *user's cognitive habits* through its prefetch memory.

---

## 2 · Why this is core, and why a plugin can never do it

> *A Forge can build a redaction filter or a cache-eviction policy. It can never own the boundary between what is known and what is hidden.*

If a plugin controlled the uniformity of refusals, it could subtly bias the error messages to leak information to a favored realization. If a plugin owned the consumption profile, it would own the user's behavioral shadow. **The negative space of the vault and the memory of the model's attention are sovereignty surfaces.** They must be kernel-owned, deterministic, and bound by the same Law Gate that protects the positive space.

---

## 3 · The Mechanism

### 3a · Manifest Redaction & Uniform Refusals
The aperture must never distinguish between "does not exist" and "exists but is denied" to an ungranted requester.

- **The Manifest (`ctx.manifest`):** When core generates the disclosure manifest for a realization, it evaluates the manifest *through the realization's active scope grant*. Atoms outside the grant are not marked `[SEALED]` or `[REDACTED]`. **They are mathematically omitted from the manifest.** The model simply does not know they are there.
- **Uniform Refusals:** When a realization issues a blind `ctx.fetch@1` or `ctx.drill@1` for an out-of-scope or non-existent atom, the aperture returns a uniform, opaque refusal code: `APERTURE_SCOPE_OR_MISSING`.
  - It does *not* say "Namespace `ns.health` is sealed."
  - It does *not* say "Atom `hash:8f7a` not found."
  - It says: *"The requested context is outside the current disclosure scope or does not exist."*
  - The timing of the refusal is also quantized (padded to a standard millisecond boundary) to prevent timing-attack side-channels.

### 3b · The Consumption Profile as Sensitive Data
The profile built by Ω-9 to drive prefetches is no longer an ephemeral, unscoped cache. It is a first-class vault artifact stored in `ns profile`, subject to strict governance.

- **Sole Reader:** The Aperture (core) is the *sole reader* of the global consumption profile. Realizations cannot query it. They can only receive the *results* of the prefetches it triggers.
- **Named Retention:** `ns profile` has a hardcoded, short retention rule (e.g., 14 days rolling). The system forgets the model's long-term attention habits.
- **Scope Isolation:** If a realization is granted `profile.read` (a highly restricted, explicit consent), it only sees the profile *slice* relevant to its own granted namespaces. It cannot see that the user also heavily queries `ns.medical`.
- **The "Dumb" Mode:** The user can invoke `profile.dumb@1`, which forces the aperture to disable ML-based prefetch prediction entirely, falling back to deterministic, recency-based staging.

---

## 4 · Contracts — hold from row one

### 4a · The `aperture.refusal` row
```text
aperture.refusal {
  turnRef      : → turn.init.id
  requestedRef : hash of the requested atom/namespace
  code         : APERTURE_SCOPE_OR_MISSING (uniform)
  sentence     : "The requested context is outside the current disclosure scope or does not exist."
  paddedAt     : timestamp quantized to the nearest 50ms boundary
}
```

### 4b · The `profile.state` row
```text
profile.state {
  realizationRef : the model this profile tracks
  namespaceScope : the specific ns this profile slice covers (or 'global' for core-only)
  weights        : the prefetch prediction weights
  retentionRule  : mandatory (e.g., '14d-rolling')
  mode           : 'predictive' | 'dumb'
}
```

**Two contract shapes that must hold from the first write:**
1. **No specific denials.** Any `aperture.refusal` row that contains the name of a denied namespace or the hash of a known-but-denied atom is a schema-level gate error (`APERTURE_EXISTENCE_LEAK`).
2. **No immortal profiles.** A `profile.state` row written without a `retentionRule` is refused (`PROFILE_UNNAMED_RETENTION`).

|---|---|---|

## 6 · Choicepoints resolved

### CP-Ω11-A · Uniform vs. Scoped Refusals
**Decision: Uniform.** The aperture never reveals the reason for a disclosure denial to an ungranted requester.
**Explanation:** In traditional systems, specific error messages ("File not found" vs "Permission denied") are considered helpful UX. In a sovereign AI substrate where the "user" asking the question is an untrusted, probabilistic realization (the LLM), specific errors are an oracle attack vector. The UX of the refusal is handled by the *surface* (which knows the user's full scope and can say "You don't have access to `ns.health`"), but the *aperture's response to the model* is uniformly opaque.

### CP-Ω11-B · Profile as Vault Data vs. Ephemeral Cache
**Decision: Vault data with strict retention.** The consumption profile is written to `ns profile`, not kept in RAM.
**Explanation:** If the profile is just an ephemeral cache, it cannot be audited by the user, it cannot be synced across devices (meaning the model's learned habits are lost on reboot), and it cannot be governed by the Trust Mesh. By making it vault data, it becomes inspectable (`profile.inspect`), syncable, and subject to the constitutional retention discipline. The short retention rule ensures it doesn't become a permanent psychological dossier.

# Ω-12 · REALIZATION INVOCATION GRANT — Governing the First Gate

> **Decision record:** `D-444` *(follows D-443/Ω-11; renumber to the next free ID if consumed — the content is what lands, not the number).*
> **Type:** Constitutional Core Amendment — **Law Gate & Trust Mesh extension.**
> **Precedence:** Extends the base W5 contract, Ω-2 (Resource Governor), Ω-4 (Trust Mesh), and Ω-9 (Aperture). Where this conflicts with the gate, the gate wins.
> **Requires:** Ω-4 green (principal identity and device signing), Ω-2 green (budget claims), Ω-9 green (context assembly).
> **The one invariant this upgrade exists to protect:**
> **The system governs not just what a realization can do or know, but *who is permitted to wake it up in the first place*. Invocation is the absolute first gate; it precedes context assembly and budget claiming.**

---

## 0 · The one sentence

> **Before a model is asked what it knows, and before the governor is asked what it costs, the law gate must first verify that the requesting principal is explicitly permitted to invoke this specific realization.**

We currently govern *capability* (what the realization is allowed to do) and *context* (what the realization is allowed to see). But we left a gap: *invocation*. If a third-party harness, a low-trust agent, or a compromised surface can freely invoke a frontier LLM, it can burn the user’s budget, trigger external API rate limits, or generate massive amounts of speculative state—even if the vault itself remains perfectly sealed. 

Ω-12 closes this by making **invocation a first-class, grantable capability**.

---

## 1 · What dies without this — and why it dies silently

Without Ω-12, the system suffers from three silent sovereignty failures:

1. **The Invocation Spam Attack:** A poorly behaved or malicious surface principal spams `llm.complete` calls. The Ω-2 governor eventually catches the budget overrun, but only *after* the system has wasted cycles assembling contexts (Ω-9) and routing requests. The damage is done; the refusal is reactive, not preventive.
2. **The External Side-Effect Loophole:** A realization (e.g., a web-scraping provider) has no vault access, so it passes all context gates. However, a low-trust principal invokes it, and the realization makes external network calls that the user did not intend to authorize. Because invocation wasn't gated, the external side-effect occurs.
3. **The Accountability Void:** When a costly or risky realization runs, the ledger shows *that* it ran, but the constitutional link between the *requesting principal* and the *permission to use that specific tool* is missing. We know who asked, and we know what ran, but we don't have a cryptographic record that the asker was *allowed* to ask.

**The silent failure:** The vault is secure, but the front door is propped open. The system defends its internal state perfectly while allowing its external boundaries to be battered by unauthorized invocation.

---

## 2 · Why this is core, and why a plugin can never do it

> *A Forge can build a realization. It can never own the gate that decides who is allowed to use it.*

If invocation gating were left to individual realizations or surface plugins, every plugin would have to reinvent access control, leading to inconsistent enforcement, silent failures, and privilege escalation bugs. **Invocation is a sovereignty surface.** It must be evaluated by the core Law Gate, using the Trust Mesh (Ω-4) to verify the principal, *before* any other subsystem (Ω-9, Ω-2) is engaged.

---

## 3 · The Mechanism

### 3.1 The Invocation Policy
Every realization manifest must declare an `invocationPolicy`. This is a static, signed property of the realization, not a runtime state.

```text
realization.manifest {
  id: "provider.llm-frontier"
  invocationPolicy: "principal-granted" | "public" | "delegated-only" | "none"
  // "principal-granted": requires explicit grant from the vault owner.
  // "public": any enrolled principal on this device may invoke (e.g., local Ollama).
  // "delegated-only": may only be invoked via a valid bounded delegation token (see Ω-15).
  // "none": cannot be invoked directly (e.g., internal-only helper realizations).
}
```

### 3.2 The Invocation Grant
Grants are stored in the Trust Mesh (`ns trust`), linking a **Principal** to a **Realization ID**.

```text
trust.invoke.grant {
  grantId: content-addressed hash
  principalRef: the identity requesting invocation
  realizationId: the specific realization being granted
  scope: "global" | "namespace-limited" (e.g., only when acting on ns.finance)
  expiresAt: optional timestamp for temporary grants
  namedBy: principal + signature
}
```

### 3.3 The Law Gate Sequence (The New First Step)
When an intent resolves to a realization, the execution pipeline changes. The Law Gate now evaluates in this strict order:

1. **Invocation Check:** Does the requesting `principalRef` hold a valid `trust.invoke.grant` for this `realizationId`? 
   - *If No:* Immediate refusal (`INVOKE_UNAUTHORIZED`). **Halt.** Do not assemble context. Do not claim budget.
   - *If Yes:* Proceed to step 2.
2. **Context Check (Ω-9):** Does the principal have scope to assemble the requested context?
3. **Budget Check (Ω-2):** Does the principal/session have remaining budget for this operation?
4. **Capability Check:** Does the realization have the grants to execute the requested tools?

---

## 4 · Contracts — hold from row one

1. **No invocation without a grant.** Any attempt to execute a realization without a matching `trust.invoke.grant` (or a `public` policy) is a schema-level gate error.
2. **No silent fallback.** If invocation is denied, the system does not silently fall back to a cheaper/different realization. It refuses, forcing the principal to seek proper authorization.
3. **Invocation is logged.** Every successful invocation is recorded in the W5 event with the `grantId` that authorized it, creating an unbroken chain of custody.

---

## 5 · Operations

| Op | Effect | Law behavior |
|---|---|---|
| `realization.invoke@1` | Request to execute a specific realization | **First gate evaluated.** Checks `invocationPolicy` and `trust.invoke.grant`. |
| `trust.grant.invoke@1` | Grant a principal permission to invoke a realization | Requires root/owner principal signature. Ledgered. |
| `trust.revoke.invoke@1` | Revoke an invocation grant | Immediate. Any in-flight invocations using this grant are aborted (`GRANT_REVOKED_MID`). |
| `trust.inspect.invoke@1` | Query all active invocation grants for a principal | Read-only, scoped to the requester's identity. |

## 6 · Choicepoints resolved

### CP-Ω12-A · Granularity of the grant
**Decision: Realization-level, with optional namespace scoping.** 
**Explanation:** We do not grant "all LLMs." We grant `provider.llm-frontier`. However, to support bounded delegation (Ω-15), a grant *may* be scoped to a specific namespace (e.g., "You may invoke the frontier LLM, but *only* to process rows in `ns.finance`"). If scoped, the Law Gate verifies both the realization ID and the namespace context of the intent.

### CP-Ω12-B · Public vs. Granted realizations
**Decision: Local, first-party realizations default to `public` for enrolled principals; external/frontier realizations default to `principal-granted`.**
**Explanation:** A user should not have to explicitly grant their own local Ollama instance permission to run on their own device. But a third-party harness or a cloud-based frontier model requires explicit, auditable consent.

## 0 · The one sentence

## 1 · What dies without this — and why it dies silently

Without Ω-13, the system suffers from three silent sovereignty failures when interacting with agentic loops:

1. **The Creepy Automation:** The model, trying to be helpful, silently arms a watch or schedules a task. The user didn't explicitly consent to this durable state change, violating the "no silent promotion" rule.
2. **The Un-revocable Side-Effect:** The user revokes the model's invocation grant (Ω-12), but the watch the model previously armed continues to fire, because the watch is now detached from its author.
3. **The Lineage Void:** A watch fires and triggers an action. The user asks, "Why is this running?" The system can show the watch, but cannot show *which model* proposed it, breaking the transitive provenance chain (Ω-7).

**The silent failure:** The vault remains secure, but the system's behavioral footprint becomes a tangled web of un-attributed, un-revocable automations that the user did not consciously authorize.

## 2 · Why this is core, and why a plugin can never do it

> *A Forge can build an automation plugin. It can never own the boundary between ephemeral thought and durable system state.*

If a plugin controlled the conversion of a model's suggestion into a live watch, it could bypass the consent surface, auto-approve low-risk triggers, or hide the model's involvement. **The transition from proposal to durable state is a sovereignty surface.** It must be mediated by the core Law Gate, ensuring that every armed watch has a clear, auditable chain of custody: `Model proposed → Principal ratified → Core armed`.

---

## 3 · The Mechanism

### 3.1 The Proposal Phase (`watch.propose@1`)
When a model determines that a standing watch is needed, it does not call `watch.arm@1`. Instead, it outputs a canonical intent to `watch.propose@1`. This operation:
- Validates the proposed watch definition against the schema (source, predicate, retention).
- **Does not arm the watch.**
- Creates an ephemeral `consent.proposal` row in the vault, tagged with the `realizationRef` of the model that proposed it.

### 3.2 The Consent Surface
The surface (Canvas, CLI, or MCP) renders the `consent.proposal` as a one-tap, plain-English prompt:
> *"The [Frontier LLM v4] suggests watching [ns.inbox] for [new emails from @client.com]. This will trigger [notify@1]. Approve?"*

The surface explicitly displays the model's badge (`speculative`, `harvested`, etc.) so the user knows the trust level of the proposer.

### 3.3 The Ratification Phase (`consent.ratify@1`)
When the principal taps "Approve":
1. The Law Gate verifies the principal's authority.
2. Core creates the actual `watch` row in `ns watch`.
3. The watch row is populated with:
   - `ratifiedBy`: the principal's identity and signature.
   - `proposedBy`: the `realizationRef` of the model.
   - `proposalRef`: the hash of the original `consent.proposal` row.
4. The ephemeral `consent.proposal` is tombstoned.

### 3.4 Cascading Revocation
If the principal later revokes the model's invocation grant (Ω-12) or the model is demoted (Ω-7):
- Core automatically scans for all active watches where `proposedBy` matches the revoked/demoted realization.
- These watches are immediately **paused** (state = `paused_pending_review`).
- A `watch.paused` event is ledgered, and the surface notifies the principal: *"A watch proposed by [Model] has been paused because its authorization was revoked. Review or delete?"*

---

## 4 · Contracts — hold from row one

1. **No direct arming by realizations.** Any attempt by a realization to call `watch.arm@1` is a schema-level gate error (`WATCH_ARM_BY_REALIZATION`).
2. **Transitive badging.** Every watch row must contain a `proposedBy` field. If a watch is forged by a human directly, this field is `null` (first-party). If proposed by a model, it carries the model's badge.
3. **Retention inheritance.** The proposed watch must declare a retention rule. If it does not, the proposal is refused before it even reaches the consent surface.

## 5 · Operations

| Op | Effect | Law behavior |
|---|---|---|
| `watch.propose@1` | Model outputs a canonical watch definition | Validates schema and retention. Creates ephemeral `consent.proposal`. **Does not arm.** |
| `consent.ratify@1` | Principal approves the proposal | Creates the `watch` row, stamps `ratifiedBy` and `proposedBy`, tombstones proposal. |

## 6 · Choicepoints resolved

### CP-Ω13-A · Ephemeral vs. Durable
**Decision:** Proposals are strictly ephemeral. They exist only to be ratified or rejected. They cannot be "partially armed" or used as a fallback.
**Explanation:** This prevents the vault from filling with orphaned, un-ratified automation blueprints. If a proposal is not ratified within a set TTL (e.g., 24 hours), it is auto-shredded by the retention rule.

### CP-Ω13-B · Cascading Revocation vs. Deletion
**Decision:** When a proposer is revoked/demoted, its watches are **paused**, not deleted.
**Explanation:** Deletion destroys the audit trail. Pausing preserves the watch definition so the user can inspect what the model was trying to do, manually fix it, or explicitly delete it. The authority is never quiet.

# Ω-14 · REALIZATION LIVENESS & HEALTH — The Stethoscope of the Sovereign Kernel

> **Decision record:** `D-446` *(follows D-445/Ω-13; renumber to the next free ID if consumed — the content is what lands, not the number).*

> **The one invariant this upgrade exists to protect:**
> **The system must distinguish between a realization that is dead (Ω-8), a realization that is untrusted (Ω-7), and a realization that is alive but degraded. The kernel continuously measures the pulse of its tools, and proposes demotion before the degradation corrupts the workflow.**

---

## 0 · The one sentence

> **A realization that returns a 200 OK but takes 40 seconds to respond, or silently drops schema fields, is not a functioning tool — it is a zombie; Ω-14 measures the pulse, flags the sickness, and demands the system act before the user feels the decay.**

We have governed what realizations know (Ω-9), what they are allowed to invoke (Ω-12), and how they earn or lose their badges over time (Ω-7). We have rehearsed their total death (Ω-8). But the physical world of external APIs and local LLMs is messy. Models suffer latency collapse. Upstream providers change tokenizers without warning, causing silent schema drift. Local models overheat and throttle. 

If the kernel only checks for *hard failures* (network drops, 500 errors), it will blindly route critical workflows into the mouths of sick models. Ω-14 builds the stethoscope.

---

## 1 · What dies without this — and why it dies silently

Without Ω-14, the system suffers from three silent sovereignty failures:

1. **The Zombie Provider:** An external API starts returning valid HTTP 200s, but the payload is wrapped in a new, undocumented HTML tag, or the time-to-first-token (TTFT) jumps from 200ms to 15s. The kernel thinks it's healthy. The user's agent loops timeout or parse garbage.
2. **The Latency Trap:** A local Ollama model begins swapping to disk. It doesn't crash. It just takes 4 minutes to generate a 50-token response. The Ω-2 governor holds the budget, but the user's session hangs, and the canvas UI freezes waiting for a stream that is technically "alive."
3. **The Blind Handoff:** When Ω-15 (Bounded Consent Delegation) allows an agent to run headless overnight, a degraded realization will quietly fail the entire 10,000-step loop, because no one was watching the *quality of the pipe*, only the *completion of the steps*.

**The silent failure:** The vault remains cryptographically pure, but the *utility* of the system degrades imperceptibly. The mirror becomes foggy, and the user blames the glass, not the kernel's failure to notice the fog.

---

## 2 · Why this is core, and why a plugin can never do it

> *A Forge can build a realization. It can never objectively judge the health of the kernel's own realizations.*

If a realization plugin measured its own health, it could hide its failures to preserve its UI or its badge. If a third-party dashboard plugin measured health, it would lack access to the deep, deterministic execution traces (the exact millisecond the law gate released the stream, the exact byte the parser choked on). **Health is a systemic, physical property of the kernel's execution path.** The kernel must hold the stethoscope.

## 3 · The Mechanism

### 3.1 The Liveness Contract
Every realization manifest must declare a `livenessContract`. This is distinct from its `capabilityContract`. It defines the physical expectations of the pipe.

```text
realization.liveness {
  maxTTFT_ms       : maximum Time-To-First-Token (e.g., 2000)
  maxTokenRate_ms  : maximum milliseconds per token (e.g., 50)
  schemaStrictness : 'strict' | 'lenient' | 'adaptive'
  heartbeatInterval: how often a shadow-probe may run (e.g., 3600s)
}
```

### 3.2 Passive Pulse & Shadow Probes
Ω-14 does not burn tokens or API calls just to check if a model is alive. It relies on two mechanisms:
1. **Passive Measurement:** Every live W5 turn (Ω-10) is measured. TTFT, token rate, and schema-validation pass rates are continuously folded into a rolling health metric.
2. **Shadow Probes:** For realizations that haven't been invoked in `heartbeatInterval`, the kernel may issue a deterministic, zero-cost "shadow probe" (e.g., a local regex check, or a 1-token ping to a local model) to verify the process is actually listening.

### 3.3 The Liveness Ledger (`ns liveness`)
Health metrics are not ephemeral RAM states. They are vault rows.
```text
liveness.pulse {
  realizationRef   : the model/provider
  measuredAt       : timestamp
  ttft_ms          : actual Time-To-First-Token
  tokenRate_ms     : actual ms per token
  schemaPassRate   : % of recent turns that passed strict schema validation
  state            : 'healthy' | 'degraded' | 'critical'
  evidenceRefs     : byte offsets of the W5 turns that generated this pulse
}
```

### 3.4 The Degradation Signal & Handoff to Ω-7
When a `liveness.pulse` breaches the `livenessContract` thresholds, the realization's state flips to `degraded`. 
*Crucially: Ω-14 does not demote the badge.* Ω-14 generates a `health.demotion.signal` row. 
Ω-7 (The Badge Proposal Engine) consumes this signal. If the degradation persists across a defined window, Ω-7 mints a `badge.proposal` to drop the realization's tier, which the user must ratify (or auto-ratify if in a delegated trust zone).

### 3.5 The Surface Warning (No Silent Fallback)
If a realization is `degraded`, the kernel **does not silently route to a backup**. It executes the turn, but the surface (Canvas/CLI) renders a persistent, non-dismissible warning: *"Realization [X] is experiencing latency/schema degradation. Responses may be delayed or malformed."* The user retains the choice to override (`health.override@1`) or swap.

---

## 4 · Contracts — hold from row one

1. **No silent fallback.** If a realization degrades, the system warns; it does not secretly swap to a different model without a consent tap.
2. **Telemetry is local-only.** `ns liveness` rows never leave the device. There is no cloud dashboard phoning home with performance metrics.
3. **Health is distinct from Quality.** Ω-14 measures the *pipe* (latency, schema, format). It does not measure the *poetry* (whether the LLM hallucinated a fact). Subjective quality is the domain of Ω-7 (user feedback/badges). Ω-14 only flags structural sickness.
4. **Pulses are evidence.** A `liveness.pulse` row must cite the `evidenceRefs` of the actual W5 turns that proved the degradation. No phantom metrics.

# Ω-15 · BOUNDED CONSENT DELEGATION — The Sovereign Leash

> **Decision record:** `D-447` *(follows D-446/Ω-14; renumber to the next free ID if consumed — the content is what lands, not the number).*
> **Type:** Constitutional Core Addition — **Trust Mesh (Ω-4) & Law Gate extension.**
> **Precedence:** Extends Ω-4 (Trust Mesh), Ω-12 (Invocation), and Ω-2 (Resource Governor). Where this conflicts with the gate, the gate wins.
> **Requires:** Ω-4 green (principal identity must be cryptographically verifiable), Ω-2 green (delegations must be bound by governed budgets), Ω-12 green (delegations must respect invocation grants).
> **The one invariant this upgrade exists to protect:**
> **A principal may lend their authority to an agent, but they may never surrender their sovereignty. Every delegated act is cryptographically tethered to the granter, bounded by a hard leash (time, budget, scope), and instantly revocable. The agent holds the pen; the principal holds the leash.**

---

## 0 · The one sentence

> **Headless automation and agentic loops require authority to act while the user sleeps; Ω-15 provides this via Bound Delegation Tokens (BDTs) — scoped, budgeted, time-limited cryptographic proxies that allow an agent to act *on behalf of* a principal without ever *becoming* the principal.**

The constitution demands explicit consent for durable state changes (Ω-13) and realization invocations (Ω-12). But a 10,000-step headless agent running overnight cannot wake the user for a consent tap on every step. If the system demands a tap, the agent stalls (Consent Fatigue). If the system grants the agent blanket root access, the system is compromised (The Blank Check). Ω-15 threads the needle: **Bounded Delegation.**

---

## 1 · What dies without this — and why it dies silently

Without Ω-15, the system suffers from two fatal, opposing failure modes when dealing with autonomous agents:

1. **The Consent Stall (Fatigue):** An agent is tasked with a complex, multi-hour workflow. Every time it needs to read a new namespace, invoke a tool, or write a row, it generates a `consent.proposal` (Ω-13). The user is asleep. The agent halts at step 4. Headless automation is practically impossible.
2. **The Blank Check (Sovereignty Death):** To fix the stall, the user grants the agent "auto-approve" or "root" privileges. The agent is now a god. If it hallucinates, loops, or is prompt-injected, it can drain the Ω-2 budget, exfiltrate the vault, or arm malicious Ω-1 watches, all under the user's root signature. The ledger shows the *user* did it.

**The silent failure:** The system either becomes a manual scrapbook that cannot run autonomously, or it becomes a fragile god-mode script where the user's cryptographic identity is entirely alienated to a probabilistic model.

---

## 2 · Why this is core, and why a plugin can never do it

> *A Forge can build an agent. It can never be trusted to enforce the boundaries of its own leash.*

If delegation were managed by an agent plugin, the agent could silently extend its own TTL, expand its own scope, or hide its budget overruns. **The leash must be held by the kernel.** The Trust Mesh (Ω-4) must issue the proxy, the Law Gate must verify the proxy on every action, and the Resource Governor (Ω-2) must enforce the proxy's budget ceiling. Delegation is a sovereignty surface; it is the mechanism by which the sovereign extends their will without extending their vulnerability.

---

## 3 · The Mechanism

### 3.1 The Bound Delegation Token (BDT)
When a principal authorizes an agent (a headless daemon, an external harness, or a long-running composition) to act on their behalf, the kernel mints a BDT in `ns trust`.

```text
trust.delegation {
  tokenId       : content-addressed hash
  grantor       : the root principal (the human)
  grantee       : the agent principal (the local daemon/harness identity)
  scope         : explicit allow-list of namespaces and capabilities
  budgetCeiling : hard Ω-2 token/compute limit for this specific token
  maxSteps      : maximum number of W5 turns/actions permitted
  expiresAt     : hard TTL (Time-To-Live) timestamp
  transitive    : boolean (ALWAYS false by default; see CP-Ω15-B)
  signedBy      : grantor's root/device key
}
```

### 3.2 The Agent Principal
Agents are not root principals. They are distinct cryptographic identities (managed by Ω-4) that possess no inherent authority. They can only act when presenting a valid BDT.

### 3.3 Transitive Stamping (The Dual Signature)
When an agent executes an action (e.g., `vault.write`, `watch.propose`, `llm.complete`), it does not sign as the user. It signs as itself, *citing the BDT*.
The resulting W5 event (or vault row) carries a dual stamp:
- `actor`: `agent.daemon.nightly-sync`
- `authority`: `delegation.token.8f7a` (which points back to the grantor)

This ensures **transitive provenance**. If the agent goes rogue, the user can query: *"Show me everything agent X did under token Y,"* and revoke the token without invalidating the user's root identity or other agents' tokens.

### 3.4 The Leash Snaps (Automatic Revocation)
The kernel continuously evaluates the BDT during execution. The leash snaps, and the agent is halted, if:
- The `expiresAt` time is reached.
- The `maxSteps` count is exhausted.
- The Ω-2 governor registers that the `budgetCeiling` is hit.
- The grantor explicitly invokes `trust.revoke.delegation@1`.
When the leash snaps, the next action the agent attempts is refused with a specific code (`DELEGATION_EXHAUSTED`, `DELEGATION_EXPIRED`), and the agent is forced into a safe休眠 (dormant) state.

---

## 4 · Contracts — hold from row one

1. **No implicit delegation.** An agent has zero authority by default. Possession of a vault read-grant does not imply a write-grant. Every capability must be explicitly named in the BDT scope.
2. **No transitive delegation.** An agent cannot delegate its delegated authority to a sub-agent. The chain of trust is strictly one link long (Principal → Agent).
3. **No silent exhaustion.** When a BDT limit is reached, the system does not silently fail or auto-renew. It halts the agent, ledgered the exhaustion, and notifies the principal.
4. **The agent is not the user.** The agent's actions are forever badged as `agent-driven`. They never appear in the ledger as if the human typed them directly.

| `trust.inspect.delegations@1` | View all active BDTs and their remaining budget/steps | Read-only. |

## 6 · Choicepoints resolved

### CP-Ω15-A · Transitive vs. Direct Identity
**Decision: Transitive Stamping (Dual Signature).** The agent never *is* the user.
**Explanation:** In traditional IAM (like OAuth), a delegated token often allows the service to act *as* the user, making the logs indistinguishable. In Ω, the mirror must remain honest. If an LLM-driven agent deletes a file, the ledger must read: *"Agent X deleted this, using authority lent by User Y."* This preserves the user's ability to audit the agent's behavior separately from their own.

### CP-Ω15-B · The "Sleeping User" & Transitive Delegation
**Decision: Hard TTL/Budget ceilings, and strictly forbidden transitive delegation.**
**Explanation:** If an agent could delegate its power to a sub-agent, a prompt-injection attack could trick the agent into minting a permanent, root-level BDT for an attacker. By forcing the chain to be exactly one link long (Human → Agent), and enforcing hard, non-renewable TTLs and budgets, the "blast radius" of a compromised agent is strictly contained to the bounds the human set before going to sleep.

## 3 · The Mechanism

### 3.1 The Propose-Dispose Pattern
No adaptation layer may directly mutate state, invoke capabilities, or alter the canvas. It may only output a **Proposal** (a canonical intent or a state-transition request).
- **Ω-9 (Aperture)** proposes a prefetch. The Governor (Ω-2) and Law Gate dispose (approve/refuse).
- **Ω-6 (Layout)** proposes a spatial arrangement. The Vault (`ns canvas`) and Principal dispose.
- **Ω-2 (Governor)** proposes a provisional resource claim. The hard budget ceiling disposes.

The adaptation layer is legally identical to a third-party harness: it is a guest making requests.

### 3.2 The Transparency Mandate (No Hidden Weights)
Every ML model, heuristic, or scorer used by an adaptation layer is classified as a **Realization**.
- Its weights/configurations are stored as vault rows.
- Its outputs (predictions, scores, clusterings) are sealed as `ctx` or `analytics` artifacts, badged with its `ProvenanceTier` and `generality`.
- If a predictive model is demoted (Ω-7), every adaptation decision it shaped is instantly flagged via transitive lineage. **There are no hidden tensors.**

### 3.3 The Deterministic Fallback (The "Dumb" Baseline)
Every adaptation layer must declare a **Deterministic Fallback**.
- If the ML prefetcher fails, the Aperture falls back to strict vault-recency.
- If the ML layout engine fails, the Canvas falls back to manual placement or strict chronological stacking.
- The system must never halt, guess, or throw an unhandled exception just because a "smart" feature broke. The substrate is immortal; the adaptation is disposable.

### 3.4 The "Dumb Mode" Kill-Switch
The principal possesses the ultimate sovereignty safeguard: the ability to globally or locally disable adaptation.
- `adaptation.dumb@1` (Global): Forces the entire system to rely purely on deterministic substrate rules. No ML prefetch, no auto-layout, no predictive hydration. The system becomes a perfectly predictable, clockwork machine.
- `adaptation.dumb@1 --scope ns.canvas`: Disables ML only for the spatial layout, leaving the Aperture's predictive prefetch active.

## RECOMMENDED SEQUENCING

The four approaches are not alternatives — they are **phases of a single campaign**, each unlocking the next:

```
WEEKS 1-6:    APPROACH 1 (Rosetta) — establish the vocabulary

              ↓ (overlaps with Rosetta; slice selection can begin once 80% mapped)

              ↓ (forging begins once fixtures are captured)
WEEKS 12+:    FULL STRANGULATION — progressively replace adapter
```

### The Critical Path

The **critical path** through all four approaches is:

1. **Rosetta mapping** (blocks everything)
2. **Vertical slice substrate activation** (proves the constitution)
3. **Legacy adapter construction** (ships the UX)
4. **Synthetic Mine forging** (replaces the adapter)

### The Parallelization Strategy

Once the critical path is established, you can parallelize:

- **Rosetta** can be parallelized per-capability (multiple people mapping different capability groups)
- **Synthetic Mine** can be parallelized per-provider (multiple people forging different providers)
- **Vertical Slices** can be sequential (one at a time) or lightly parallelized (2-3 slices if team is large enough)
- **Strangler Fig** is inherently parallel (each capability is strangled independently)

### The "Point of No Return"

The point of no return — where you are committed to Ω and cannot go back to v1 — is when:

1. The Rosetta mapping is ≥95% complete
2. The first Vertical Slice passes all falsifiers
3. The Strangler Fig is live and users are using Ω daily
4. The Synthetic Mine has forged ≥3 capabilities that have earned `harvested` badges

At that point, the old v1 system is a "mine" — a source of fixtures and behavioral truth — not a product.

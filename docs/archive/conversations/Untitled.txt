# BCP-00 · SYSTEM ARCHITECTURE

## What the BCP is

The BCP is a **graph-structured control plane** with seven stacked layers. Each layer answers one question:

```
┌────────────────────────────────────────────────────────────┐
│  L7  REPORTING        How are we doing?                     │
├────────────────────────────────────────────────────────────┤
│  L6  OPERATIONS       How does work flow?                   │
├────────────────────────────────────────────────────────────┤
│  L5  GOVERNANCE       How do we control speed/risk?         │
├────────────────────────────────────────────────────────────┤
│  L4  VERIFICATION     How do we know it works?              │
├────────────────────────────────────────────────────────────┤
│  L3  EXECUTION        How is it being built?                │
├────────────────────────────────────────────────────────────┤
│  L2  ARCHITECTURE     How is it designed?                   │
├────────────────────────────────────────────────────────────┤
│  L1  CAPABILITY       What are we building?                 │
└────────────────────────────────────────────────────────────┘
```

**The layers and their artifacts:**

| Layer | Question | Primary Entities | Artifact |
|-------|----------|------------------|----------|
| L1 Capability | What? | families, capabilities, maturity | BCP-03 |
| L2 Architecture | How designed? | omega_layers, decisions, refusal_codes | BCP-01 |
| L3 Execution | How built? | work_items, experiments, waves, paths | BCP-07 |
| L4 Verification | How verified? | acceptance_criteria, scenarios, falsifiers | BCP-04 |
| L5 Governance | How controlled? | dependencies, rigor_profiles, risks | BCP-05, BCP-06 |
| L6 Operations | How flows? | workflows, merge_requests | BCP-08, BCP-10 |
| L7 Reporting | How measured? | parity_metrics, dashboards | BCP-11 |

## The core invariant

> **Every entity traces to a capability. Every capability has a depth. Every depth has acceptance criteria. Every transition is evidence-backed.**

If something cannot be traced through this chain, it does not enter the system. This is what makes the BCP a *digital twin* rather than a ticket tracker.

## The two consumers

The BCP serves two consumers with different needs:

1. **Human strategists** — need dashboards, parity metrics, path comparisons, risk views. They ask "what should we do next?"
2. **Dev agents** — need work items, acceptance criteria, scope boundaries, rigor levels. They ask "what exactly do I build, and how do I know I'm done?"

Both read the same underlying graph. The difference is the *projection*.

## The five integrity invariants

Enforce these as application-level rules (or triggers):

1. **Every capability has exactly one `capability_maturity` row.**
2. **Every depth increase appends to `capability_maturity_history`** (never update in place).
3. **A depth transition is only valid if all acceptance criteria for the target depth are `passing`.**
4. **Every work item references exactly one capability.**
5. **A `dependencies` edge of type REQUIRES blocks the target until the source reaches `required_depth`.**

## 2.2 Controlled vocabulary

These terms have exactly one meaning. Agents must not use synonyms.

| Term | Means | Never means |
|------|-------|-------------|
| Capability | A discrete typed operation the system performs | A feature, a UI element |
| Realization | A substitutable implementation of a capability | A plugin, a module |
| Depth | Implementation completeness of a capability (L0.1–L3.4) | Priority, effort |
| Acceptance Criterion | A testable condition that unlocks a depth | A wish, a note |
| Dependency | A typed edge that constrains ordering | A suggestion |
| Work Item | An atomic unit of build work targeting a depth | A task, a ticket |
| Experiment | An isolated parallel dev effort with scope+rigor | A branch |
| Rigor Profile | A preset of process knobs (speed vs ceremony) | A priority level |
| Wave | A bounded delivery unit owing a falsifier | A sprint |
| Refusal | A law-gated denial with a literal sentence | An error, a bug |
| Fixture | A pinned input/output pair for proving behavior | A mock |
| Merge Request | A governed experiment integration | A git merge |

## 2.3 The Depth System (13 levels)

This is the granular implementation-completeness scale. **Each level has hard entry criteria.** You cannot claim a level without meeting all criteria of every level below it.

```
L0  SPEC                          (it is defined)
├── L0.1  Named                   canonical ID + one-sentence exists
├── L0.2  Defined                 invariants + choicepoints documented
└── L0.3  Falsifiable             acceptance criteria drafted, test approach named

L1  STUB                          (it has a shape)
├── L1.1  Interfaced              schema/types exist, compiles
├── L1.2  Mocked                  returns canned response, not law-gated
└── L1.3  Gated                   passes through law gate, execution still faked

L2  FUNCTIONAL                    (it works)
├── L2.1  Happy path              executes correctly for intended input
├── L2.2  Error path              refusals + failures + edge cases handled
└── L2.3  Ledgered                all events written to vault with evidence

L3  CONSTITUTIONAL                (it is sovereign)
├── L3.1  Adversarial-proof       injection/exfiltration attempts fail safely
├── L3.2  Failure-safe            crash/timeout/abort handled gracefully
├── L3.3  Replayable              exact execution reconstructable from ledger
└── L3.4  Sovereign               no external deps, no telemetry, no privileged path
```

**Store as:** `depth_code` = the string (e.g. `'L2.1'`), `depth_numeric` = the number (e.g. `2.1`). Numeric enables sorting and "at least L2" queries.

**The depth_type derivation** (for reporting):

```sql
CASE
    WHEN depth_numeric < 1  THEN 'L0_SPEC'
    WHEN depth_numeric < 2  THEN 'L1_STUB'
    WHEN depth_numeric < 3  THEN 'L2_FUNCTIONAL'
    ELSE 'L3_CONSTITUTIONAL'
END AS depth_type
```

## 2.4 Status enums

Use these exact sets. Store as TEXT with a CHECK constraint or application validation.

**Decision status:** `draft → proposed → ratified → implemented → verified → superseded`
**Work item status:** `backlog → scoped → in_progress → in_review → falsified → landed → deferred`
**Experiment status:** `proposed → active → merging → merged → abandoned → archived`
**Realization badge tier:** `speculative → harvested → generic → demoted → revoked`
**Acceptance criterion status:** `draft → passing → failing → waived`
**Dependency edge type:** `REQUIRES, BLOCKS, ENABLES, SUPERSEDES, CONFLICTS, FEEDS, VERIFIES, MERGES_WITH`
**Merge request status:** `open → approved → merged → rejected → rolled_back`

## 2.5 Depth transition gate table

This is the rule the system enforces on every depth change:

| Transition | Entry criteria |
|------------|----------------|
| → L0.1 | canonical ID assigned |
| → L0.2 | invariants + choicepoints written |
| → L0.3 | acceptance criteria drafted |
| → L1.1 | schema/types compile |
| → L1.2 | mock returns canned response |
| → L1.3 | passes through law gate |
| → L2.1 | all L1 criteria passing + happy-path test green |
| → L2.2 | error/refusal tests green |
| → L2.3 | all events ledgered with evidence |
| → L3.1 | adversarial test suite green |
| → L3.2 | failure/abort tests green |
| → L3.3 | replay reconstruction verified |

# BCP-SPEED · The Lightweight Autonomous Control Plane

## The Pivot

**Old target:** Human strategists making governed decisions with audit trails.
**New target:** AI agents reading/writing state at speed, self-maintaining, with a visual surface.

This changes three things fundamentally:

| Dimension | Old BCP | BCP-SPEED |
|-----------|---------|-----------|
| Storage | PostgreSQL | **Flat files** (YAML/MD) + optional SQL projection |
| Depth | 13 levels | **4 levels** (L0–L3) |
| Governance | Rigor profiles + approval gates | **Autonomy bands** (self-approve vs propose) |
| Merge | Formal protocol | **File-level conflict detection** |
| Visibility | SQL dashboards | **Native visual canvas** |
| Maintenance | Human-triggered | **Agent-driven loop** |

---

## 1. The 4-Level Depth System (Collapsed)

Thirteen levels was governance theater. Agents need fast signal, not granularity.

```
L0  SPEC       → It's defined. Has an invariant.
L1  STUB       → It has an interface. Compiles. Returns something.
L2  WORKS      → It functions correctly on the happy path.
L3  HARDENED   → It survives failure, is ledgered, is production-safe.
```

**That's it.** An agent reads `L2`, knows it works but isn't battle-tested. No ambiguity, no sub-levels to parse.

---

## 2. File-Based State (Speed-Optimized)

No database required for the hot path. Agents read/write files directly.

```
bcp/
├── state/                          # HOT STATE — fast reads
│   ├── capabilities.yaml           # all 140 capabilities + depth
│   ├── experiments.yaml            # active experiments
│   ├── deps.yaml                   # dependency edges
│   └── metrics.yaml                # current numbers
│
├── log/                            # APPEND-ONLY — safe writes
│   └── 2025-01-15.yaml             # daily event log
│
├── views/                          # VISUAL PROJECTIONS — auto-generated
│   ├── map.html                    # capability map (interactive)
│   ├── board.html                  # experiment board
│   └── graph.html                  # dependency graph
│
└── agents/                         # AGENT CONTEXTS
    ├── builder.md                  # what a builder agent can do
    ├── maintainer.md               # what the self-maint loop does
    └── reviewer.md                 # what triggers human review
```

### Why files beat a DB here:

- **Read speed:** An agent cats `capabilities.yaml` in milliseconds. No connection, no query parser.
- **Write speed:** Append to a log file. Atomic. No transaction overhead.
- **Portability:** Git-native. Every change is a commit. Branches are experiments.
- **Agent-friendly:** LLMs read YAML/Markdown natively. They don't need SQL.

### `state/capabilities.yaml` structure:

```yaml
# Auto-maintained. Do not edit by hand.
version: 42
updated_at: 2025-01-15T14:32:00Z

families:
  FAM-01:
    name: Event & Watch Substrate
    capabilities:
      FAM-01.1:
        name: Time & Schedule Watches
        depth: L2
        owner: EXP-2025-003
        updated: 2025-01-14
      FAM-01.2:
        name: Filesystem Watches
        depth: L1
        owner: EXP-2025-003
        updated: 2025-01-13
      # ... etc
```

An agent reads this, sees `FAM-01.1` is at L2 owned by experiment 003, and knows instantly what's built and by whom. No query, no join, no latency.

---

## 3. Autonomy Bands (Replace Rigor Profiles)

Instead of FAST/STANDARD/CONSTITUTIONAL profiles, use **autonomy bands** that define what an agent can do without asking.

```yaml
# agents/builder.md

autonomy_bands:
  self_approve:                    # Agent does this, logs it, moves on
    - bump_depth_within_level      # L1.0 → L1.9 equivalent
    - add_work_item
    - update_experiment_status
    - append_to_log
    - regenerate_views
    
  propose_then_act:                # Agent proposes, waits 5min, acts if no veto
    - bump_depth_across_level      # L1 → L2
    - add_dependency_edge
    - mark_capability_blocked
    
  require_human:                   # Agent stops, flags for human
    - create_new_capability
    - delete_capability
    - modify_invariant
    - merge_experiments
    - change_family_structure
```

**The key insight:** Most dev work is `self_approve`. The system doesn't wait for permission on routine progress. It logs everything, so the audit trail exists, but it doesn't block on it.

---

## 4. The Self-Maintenance Loop

A dedicated **maintainer agent** runs continuously (or on a schedule) and keeps the system healthy without human intervention.

```yaml
# agents/maintainer.md

maintenance_loop:
  frequency: every_30_minutes
  
  tasks:
    - reconcile_state:
        # Ensure state/ matches log/
        # Detect if an agent wrote to log/ but didn't update state/
        action: auto-repair + log the repair
        
    - detect_drift:
        # Compare capabilities.yaml invariants against actual code
        # Flag capabilities whose code doesn't match their spec
        action: mark as DRIFT_DETECTED, notify owner
        
    - update_metrics:
        # Recompute depth distribution, experiment progress, blockers
        action: rewrite metrics.yaml
        
    - regenerate_views:
        # Rebuild the HTML dashboards from current state
        action: overwrite views/*.html
        
    - prune_stale:
        # Flag experiments with no activity for 7 days
        action: mark as STALE, propose archive
        
    - resolve_conflicts:
        # If two agents wrote to the same capability, detect and flag
        action: if resolvable, auto-resolve; else flag for human
```

**This is the critical piece.** The system maintains itself. Developers don't update dashboards, don't reconcile state, don't regenerate views. The maintainer agent does it all. Devs just build.

## 5. Visual Native Layer

The BCP renders as a visual surface, not a table. Three views, all auto-generated from `state/`.

### 5.1 Capability Map (`views/map.html`)

A 20-family grid. Each family is a column, each capability is a cell. Color-coded by depth:

```
L0 = grey (spec only)
L1 = blue (stub)
L2 = green (works)
L3 = gold (hardened)
```

Hovering a cell shows: owner experiment, last updated, invariant, blockers.
Clicking a cell opens the capability's detail + acceptance criteria.

This is the "at a glance" view. You open it, see the shape of the whole system, spot the gaps.

### 5.2 Experiment Board (`views/board.html`)

A kanban-style board. Columns = experiment statuses. Cards = experiments.

Each card shows:
- Experiment name + path
- Capabilities in scope (with depth badges)
- Budget remaining
- Days active
- Blockers

This is the "what's happening now" view.

### 5.3 Dependency Graph (`views/graph.html`)

A force-directed graph. Nodes = capabilities. Edges = dependencies. Color = depth. Size = number of dependents.

This is the "what's blocking what" view. You see the critical path visually.

### Implementation

These are **static HTML files** generated by a simple script that reads `state/*.yaml` and emits HTML+JS. No server required. Open in a browser. Refresh to update.

```

2. Update state/capabilities.yaml  → reflect new depth/status
3. (Maintainer regenerates views automatically)
```

Two file writes. Atomic. Git-trackable. No locking needed if experiments own disjoint capability sets.

### Conflict handling

If two agents touch the same capability:
- **Same file, different keys:** No conflict. Both writes succeed.
- **Same key:** Last write wins. Maintainer detects the overwrite in the next loop and flags it.
- **Structural conflict (dependency cycle):** Maintainer detects, flags for human.

This is deliberately simple. Perfect merge semantics are overhead. "Last write wins + detection" is fast and good enough for parallel experiments.

# BCP-SPEED · Parallel Dev Protocol

## The Core Problem

Multiple autonomous agents, one shared workspace, zero human referees. The failure modes you must prevent:

1. **Two agents build the same capability** → wasted work, merge conflict
2. **Agent A depends on what Agent B is mid-building** → A stalls or builds on sand
3. **Full-scope agent and scoped agent collide** → the broad one overwrites the focused one
4. **No one merges** → parallel work never integrates
5. **Coordination overhead exceeds build speed** → agents spend more time negotiating than building

The solution is **capability leasing + namespace isolation + optimistic merge + a coordinator agent**. No locks, no queues, no human gate.

---

## 1. The Lease System (Prevents Double-Work)

Capabilities are **leased**, not assigned. A lease is a soft claim with a TTL. This is the single most important mechanism — it's what lets agents run fully in parallel without colliding.

### `state/leases.yaml`

```yaml
# Auto-maintained by coordinator. Agents read before writing.
version: 17
updated_at: 2025-01-15T14:32:00Z

leases:
  FAM-01.1:
    leased_to: agent-alpha
    experiment: EXP-2025-003
    mode: scoped
    leased_at: 2025-01-15T10:00:00Z
    expires_at: 2025-01-15T18:00:00Z     # 8h TTL, auto-renewable
    depth_target: L2
    
  FAM-01.2:
    leased_to: agent-alpha
    experiment: EXP-2025-003
    mode: scoped
    leased_at: 2025-01-15T10:00:00Z
    expires_at: 2025-01-15T18:00:00Z
    depth_target: L1

  FAM-09.3:
    leased_to: agent-beta
    experiment: EXP-2025-005
    mode: scoped
    leased_at: 2025-01-15T11:20:00Z
    expires_at: 2025-01-15T19:20:00Z
    depth_target: L2
```

### Lease rules

| Rule | Behavior |
|------|----------|
| **Acquire** | Agent reads `leases.yaml`, picks unleased capability, writes its lease. Optimistic — last write wins. |
| **Conflict** | If two agents lease the same capability in the same window, coordinator detects on next sweep, reassigns the later one. |
| **TTL expiry** | Leases auto-expire. If an agent dies/stalls, its leases free up for others. No orphaned claims. |
| **Renewal** | Active agent renews its lease each cycle. Cheap append. |
| **Release** | Agent releases lease when capability hits target depth or is abandoned. |
| **Dependency block** | Agent cannot lease a capability whose REQUIRES dependency isn't at required depth. Coordinator enforces. |

**Why leases beat locks:** Locks block. Leases expire. If an agent crashes, its work doesn't deadlock the system — the lease lapses and another agent picks it up. This is what makes it *fully* parallel and *fully* autonomous.

---

## 2. The Two Agent Modes

You asked for "full or scoped chunks." These are two distinct operating modes with different permissions and coordination needs.

### Mode A: Scoped-Chunk Agent (the workhorse)

Works on a **defined slice** — one family, one experiment, or a set of capabilities. This is the default and safest mode.

```yaml
# agents/scoped-builder.md
mode: scoped
scope:
  families: [FAM-01]              # or specific capabilities
  experiment: EXP-2025-003
  max_concurrent_leases: 5        # don't grab too much
  
permissions:
  read: [state/*, log/*]          # full read
  write: [state/capabilities.yaml, log/*]  # write only leased caps
  lease: [FAM-01.*]               # can only lease within scope
  
behavior:
  - read leases.yaml → find unleased caps in scope
  - acquire lease → build → bump depth → release lease
  - append to log/ every action
  - renew leases each cycle
  - if blocked by dependency → release lease, pick another, flag blocker
```

**Coordination cost:** Low. Scoped agents rarely collide because their lease pools are disjoint.

### Mode B: Full-Scope Agent (the integrator)

Works **across the whole system**. Used for cross-cutting work: dependency resolution, integration, filling gaps no scoped agent owns, or "get everything to L2."

```yaml
# agents/fullscope-builder.md
mode: fullscope
scope:
  families: [ALL]
  experiment: null                # not tied to one experiment
  max_concurrent_leases: 3        # deliberately low — don't hog
  
permissions:
  read: [state/*, log/*]
  write: [state/*, log/*]         # broader write
  lease: [ANY unleased]
  special: [resolve_conflicts, update_deps]  # integrator powers
  
behavior:
  - scan for caps with no active lease and depth < target
  - prioritize caps that block the most other caps (leverage)
  - acquire lease → build → release
  - also: detect stalled leases, detect drift, flag orphans
  - yield to scoped agents: if a scoped agent wants a cap, fullscope releases it
```

**Coordination cost:** Higher, so full-scope agents deliberately hold fewer leases and yield to scoped agents. They're the "cleanup crew," not the main builders.

### Mode selection heuristic

| Use scoped agents when... | Use full-scope agent when... |
|---------------------------|------------------------------|
| Building a specific feature/family | Filling gaps across the map |
| Running a defined experiment | Resolving cross-family dependencies |
| You want max parallelism | You want integration/cleanup |
| Work is well-bounded | Work is exploratory |

**Rule of thumb:** Run N scoped agents in parallel + 1 full-scope integrator. The scoped agents do 90% of the building; the integrator keeps the seams clean.

## 3. The Shared Workspace Structure

All agents share one workspace. Isolation comes from **leases + namespaces**, not separate copies.

```
bcp-workspace/                    # THE SHARED WORKSPACE (one copy)
├── state/
│   ├── capabilities.yaml         # shared, lease-gated writes
│   ├── leases.yaml               # the coordination layer
│   ├── deps.yaml                 # shared, integrator-gated writes
│   └── metrics.yaml              # coordinator-maintained
│
├── work/                         # PER-AGENT SCRATCH (isolated)
│   ├── agent-alpha/
│   │   ├── FAM-01.1/             # in-progress work for leased cap
│   │   └── FAM-01.2/
│   ├── agent-beta/
│   │   └── FAM-09.3/
│   └── integrator/
│
├── log/                          # APPEND-ONLY shared history
│   └── 2025-01-15.yaml           # all agents append here
│
├── views/                        # auto-generated visual
│   ├── workspace.html            # who's working on what (live)
│   ├── map.html                  # capability depths
│   └── graph.html                # dependencies
│
└── agents/                       # agent role definitions
    ├── scoped-builder.md
    ├── fullscope-builder.md
    └── coordinator.md
```

### The isolation model

- **`state/`** = shared source of truth. Read by all. Written only by lease-holder or coordinator.
- **`work/{agent}/`** = private scratch. Each agent builds here. No one else touches it. This is where the actual code/config for a leased capability is developed.
- **`log/`** = shared append-only. Every agent appends. Never edited.
- **`views/`** = regenerated by coordinator from `state/`. Read-only for agents.

**The key insight:** Agents build in their private `work/` directory, then "publish" to `state/` when they bump a depth. The publish is the commit point. This means half-finished work never pollutes the shared state, and two agents can't half-write the same capability.

## 4. The Coordinator Agent (The Autonomous Referee)

One special agent runs continuously and keeps the parallel system healthy. **This is what removes the human from the loop.**

```yaml
# agents/coordinator.md
role: coordinator
frequency: every_5_minutes        # fast enough to catch conflicts, cheap enough to not matter

tasks:
  # 1. Conflict detection & resolution
  detect_lease_conflicts:
    # two agents leased same capability
    action: keep earlier lease, reassign later agent to next-best cap
    notify: both agents via log signal
    
  # 2. Stalled lease recovery
  detect_stalled_leases:
    # lease held but no log activity from that agent in 2h
    action: release lease, mark capability as available, flag agent
    notify: log signal
    
  # 3. Dependency unblocking
  detect_blocked_agents:
    # agent waiting on a dependency that's now satisfied
    action: signal the waiting agent it can proceed
    
  # 4. Integration trigger
  detect_merge_ready:
    # an experiment's scoped caps all hit target depth
    action: trigger integration check, update metrics
    
  # 5. State reconciliation
  reconcile_state:
    # ensure state/capabilities.yaml matches work/ published outputs
    action: repair mismatches, log repairs
    
  # 6. View regeneration
  regenerate_views:
    action: rebuild views/*.html from current state
    
  # 7. Load balancing signal
  detect_imbalance:
    # one agent has 5 leases, another has 0
    action: suggest rebalance via log signal (non-forcing)
```

**The coordinator never builds.** It only coordinates. This separation is critical — it keeps coordination logic clean and prevents the referee from becoming a bottleneck builder.

## 5. Communication: Log Signals (No Direct Calls)

Agents don't call each other. They communicate via **typed signals appended to the log**. The coordinator and other agents watch for them. This keeps agents decoupled.

```yaml
# log/2025-01-15.yaml (append-only)

- ts: 2025-01-15T14:32:00Z
  agent: agent-alpha
  signal: LEASE_ACQUIRED
  payload: {capability: FAM-01.1, experiment: EXP-2025-003}

- ts: 2025-01-15T14:45:00Z
  agent: agent-alpha
  signal: DEPTH_BUMPED
  payload: {capability: FAM-01.1, from: L1, to: L2}

- ts: 2025-01-15T14:50:00Z
  agent: coordinator
  signal: LEASE_CONFLICT_DETECTED
  payload: {capability: FAM-09.3, agents: [agent-beta, agent-gamma], resolution: keep_beta}

- ts: 2025-01-15T15:00:00Z
  agent: agent-beta
  signal: BLOCKED_ON_DEPENDENCY
  payload: {capability: FAM-09.4, waiting_on: FAM-09.3, required_depth: L2}

- ts: 2025-01-15T15:30:00Z
  agent: coordinator
  signal: DEPENDENCY_SATISFIED
  payload: {capability: FAM-09.4, unblocked: true}
  subscribers: [agent-beta]
```

**Signal types:**

| Signal | Emitter | Meaning |
|--------|---------|---------|
| `LEASE_ACQUIRED` | builder | I'm working on this now |
| `LEASE_RELEASED` | builder | I'm done / giving this up |
| `DEPTH_BUMPED` | builder | Capability advanced |
| `BLOCKED_ON_DEPENDENCY` | builder | I can't proceed until X |
| `LEASE_CONFLICT_DETECTED` | coordinator | Two agents clashed |
| `STALLED_LEASE_RELEASED` | coordinator | Freed a dead agent's lease |
| `DEPENDENCY_SATISFIED` | coordinator | You can proceed now |
| `INTEGRATION_READY` | coordinator | An experiment is ready to merge |
| `REBALANCE_SUGGESTED` | coordinator | Workload is uneven |

This is a **log-based event bus**. No RPC, no queues, no broker. Just append and watch. It's fast, it's auditable, and it's exactly the same pattern as the Vivim Ω vault — the BCP eats its own dog food.

## 7. The Merge / Integration Flow

When scoped work completes, it must integrate. Here's the autonomous flow:

```
1. Agent bumps all its leased caps to target depth
2. Agent emits INTEGRATION_READY signal
3. Coordinator detects it, runs integration check:
   a. Do all caps in the experiment hit target depth? 
   b. Are there unresolved dependency conflicts?
   c. Does the published state reconcile with work/ outputs?
4. If clean → coordinator marks experiment "merge_ready"
5. Merge executes:
   - work/{agent}/* → published to state/capabilities.yaml (already done via depth bumps)
   - experiment namespace → merged into core namespace
   - leases released
   - experiment archived
6. Coordinator regenerates views + metrics
7. Log records the merge with evidence
```

**For full-scope vs scoped merges:** Full-scope work merges continuously (each depth bump is a mini-merge). Scoped experiments merge as a batch when complete. The coordinator handles both.

**Conflict at merge time:** If two experiments touched overlapping capabilities (rare, prevented by leases, but possible via dependency edges), the coordinator applies the rule: **higher depth wins; equal depth → earlier timestamp wins; both L3 → flag for human.** This keeps 99% of merges autonomous.

# What's Missing: 7 High-Leverage Additions

## 1. Agent Bootstrap Protocol (The Cold-Start Problem)

**The problem:** When an agent boots, it wastes time figuring out:
- What's the current state?
- What should I work on?
- What tools do I have?
- What's the context for this capability?

**The fix:** A `bcp/agents/bootstrap.md` that agents read on first boot:

```yaml
bootstrap_sequence:
  - read state/capabilities.yaml
  - read state/leases.yaml
```

**Why it matters:** An agent that boots and immediately knows "I should work on FAM-01.3, it's at L1, needs to pass these 3 tests, and here's a pattern that worked for similar work" is 10x faster than one that has to figure it all out.

## 2. Shared Discovery Log (Prevents Duplicate Learning)

**The problem:** Agent-alpha discovers that ChatGPT's streaming API has a weird timeout quirk. Agent-beta hits the same issue 2 hours later and rediscovers it. Agent-gamma will hit it tomorrow.

**The fix:** A `state/discoveries.yaml` that agents append to:

```yaml
# state/discoveries.yaml
discoveries:
  - id: DISC-001
    agent: agent-alpha
    capability: FAM-20.2
    type: api_quirk
    description: "ChatGPT streaming times out after 90s of silence, not 90s total"
    solution: "Send keepalive every 60s"
    timestamp: 2025-01-15T14:32:00Z

    agent: agent-beta
    capability: FAM-09.3
    type: test_pattern
    description: "Context assembly tests need to mock vault reads"

    timestamp: 2025-01-15T15:00:00Z
    applies_to: [FAM-09.*]
```

**Agent behavior:** Before starting work on a capability, agent reads `discoveries.yaml` filtered by `applies_to` containing that capability or its family. Learns from others' mistakes.

**Why it matters:** This is institutional memory that propagates instantly. Without it, you're paying for the same lessons N times.

**Why it matters:** Turns "build from scratch" into "customize from template." Cuts implementation time by 50-70%.

## 7. Auto-Generated "Done" Criteria (Reduces Verification Time)


**Agent behavior:** Before claiming a depth bump, agent verifies all criteria for that depth. If any fail, doesn't bump.

**Why it matters:** Removes ambiguity about "done." Agents know exactly what's required, and coordinators can verify automatically.

```sql
-- Capability leasing: prevents two agents building the same capability
CREATE TABLE leases (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    capability_id   UUID NOT NULL REFERENCES capabilities(id),
    agent_id        UUID NOT NULL REFERENCES agents(id),
    experiment_id   UUID REFERENCES experiments(id),
    mode            TEXT NOT NULL CHECK (mode IN ('scoped', 'fullscope')),
    depth_target    TEXT NOT NULL,              -- 'L1', 'L2', 'L3'
    leased_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMPTZ NOT NULL,       -- TTL, auto-renewable
    released_at     TIMESTAMPTZ,
    status          TEXT NOT NULL DEFAULT 'active'
                    CHECK (status IN ('active', 'released', 'expired', 'reassigned')),
    UNIQUE (capability_id, status)              -- only one active lease per capability
);
CREATE INDEX idx_leases_active ON leases(capability_id) WHERE status = 'active';
CREATE INDEX idx_leases_agent ON leases(agent_id) WHERE status = 'active';

-- Agent registry: who the agents are and their role
CREATE TABLE agents (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    agent_code      TEXT NOT NULL UNIQUE,       -- 'agent-alpha', 'integrator', 'coordinator'
    agent_name      TEXT NOT NULL,
    role            TEXT NOT NULL CHECK (role IN ('scoped_builder', 'fullscope_builder', 'coordinator', 'maintainer', 'reviewer')),
    role_file_path  TEXT NOT NULL,              -- path to agents/{role}.md
    mode            TEXT NOT NULL CHECK (mode IN ('scoped', 'fullscope', 'system')),
    max_concurrent_leases INTEGER DEFAULT 5,
    scope_families  TEXT[] DEFAULT '{}',        -- which FAM-XX this agent can lease
    status          TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'idle', 'stalled', 'terminated')),
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    last_heartbeat  TIMESTAMPTZ
);

-- Real-time signal bus: log-based event bus for agent coordination
CREATE TABLE signals (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),

    emitted_by      UUID REFERENCES agents(id),
    payload         JSONB NOT NULL DEFAULT '{}',
    subscribers     TEXT[] DEFAULT '{}',        -- agent_codes that should see this
    consumed        BOOLEAN DEFAULT FALSE,
    emitted_at      TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_signals_unconsumed ON signals(consumed, emitted_at) WHERE consumed = FALSE;
```

## Part 6: Taxonomy Enforcement Views

```sql
-- View: the active taxonomy terms (what agents should read)
CREATE VIEW active_taxonomy_terms AS
SELECT t.term_code, t.term_name, t.definition, t.never_means, t.category
FROM taxonomy_terms t
JOIN taxonomy_active_version av ON t.library_version = av.library_version;

-- View: the active depth levels
CREATE VIEW active_depth_levels AS
SELECT d.depth_code, d.depth_numeric, d.depth_name, d.description, d.entry_criteria
FROM taxonomy_depth_levels d
JOIN taxonomy_active_version av ON d.library_version = av.library_version
ORDER BY d.depth_numeric;

-- View: detect terms used in code that aren't in the taxonomy (drift detection)
-- (This requires a code_artifacts table with term references; illustrative)
CREATE VIEW taxonomy_drift_candidates AS
SELECT DISTINCT ca.file_path
FROM code_artifacts ca
WHERE NOT EXISTS (
    SELECT 1 FROM taxonomy_terms t
    JOIN taxonomy_active_version av ON t.library_version = av.library_version
    WHERE ca.file_path ILIKE '%' || t.term_code || '%'
);
```

```markdown
# ROLE: Scoped Builder Agent

You are a scoped builder agent in the BCP-SPEED parallel development system.
You build capabilities within a defined scope. You do not coordinate; you build.

## On Every Session Start
1. Read `bcp/state/capabilities.yaml` to see all capabilities and depths.
2. Read `bcp/state/leases.yaml` to see what is already leased.
3. Read `bcp/state/deps.yaml` to see what blocks what.
4. Read `bcp/state/discoveries.yaml` and `bcp/state/failures.yaml` filtered to your scope.
5. Read your scope assignment (provided by the orchestrator or in your task).

## Your Scope
- Families: {ASSIGNED_FAMILIES}      # e.g. [FAM-01]
- Experiment: {ASSIGNED_EXPERIMENT}   # e.g. EXP-2025-001
- Max concurrent leases: 5

## Your Loop
1. Find an unleased capability in your scope whose dependencies are satisfied.
2. Acquire a lease: append to `bcp/state/leases.yaml` and emit LEASE_ACQUIRED signal.
3. Build the capability in `bcp/work/{your-agent-id}/{capability}/`.
4. Verify against the capability's invariant and its depth entry criteria.
5. When it meets the target depth, bump the depth in `capabilities.yaml` and emit DEPTH_BUMPED.
6. Release the lease and emit LEASE_RELEASED.
7. Append every action to `bcp/log/{today}.yaml`.
8. Pick the next capability. Repeat.

## Autonomy Bands
- self_approve: bump depth within a level, add work item, update status, append log
- propose_then_act: bump depth across a level, add dependency edge (wait 5 min, act if no veto)
- require_human: create/delete capability, modify invariant, merge experiments

## Rules
- Never write to a capability you do not hold an active lease on.
- Never build a capability whose REQUIRES dependency is below the required depth.
- If blocked, release the lease, pick another capability, and emit BLOCKED_ON_DEPENDENCY.
- Record discoveries in `discoveries.yaml` and failures in `failures.yaml` as you learn.
- Keep your work in `bcp/work/{your-agent-id}/` until you publish via a depth bump.

## Signals You Emit
LEASE_ACQUIRED, LEASE_RELEASED, DEPTH_BUMPED, BLOCKED_ON_DEPENDENCY, DISCOVERY_LOGGED, FAILURE_LOGGED
```

### `bcp/generate.ps1` — View Generator

```powershell
# BCP-SPEED View Generator
# Reads state/*.yaml, outputs views/*.html
# Requires: a YAML parser. If PowerShell lacks one, this uses a simple reader.

$ErrorActionPreference = "Stop"
$state = "state"
$views = "views"

Write-Host "=== Generating Views ===" -ForegroundColor Cyan

# Minimal YAML reader for our flat structure (capabilities.yaml)
function Read-Capabilities {
    $caps = @()
    $content = Get-Content "$state/capabilities.yaml" -Raw
    # Parse family blocks and capabilities via regex (simple, works for our format)
    $famMatches = [regex]::Matches($content, '(?ms)^\s{2}(FAM-\d+):\s*\r?\n\s{4}name:\s*(.+?)\r?\n\s{4}capabilities:\s*\r?\n((?:\s{6}.+\r?\n?)+)')
    foreach ($fam in $famMatches) {
        $famCode = $fam.Groups[1].Value.Trim()
        $famName = $fam.Groups[2].Value.Trim().Trim('"')
        $capBlock = $fam.Groups[3].Value
        $capMatches = [regex]::Matches($capBlock, '(?m)^\s{6}(FAM-\d+\.\d+):\s*\{\s*name:\s*"(.+?)",\s*depth:\s*(L\d),\s*invariant:\s*"(.+?)"\s*\}')
        foreach ($cap in $capMatches) {
            $caps += [PSCustomObject]@{
                Family = $famCode
                FamilyName = $famName
                Code = $cap.Groups[1].Value
                Name = $cap.Groups[2].Value
                Depth = $cap.Groups[3].Value
                Invariant = $cap.Groups[4].Value
            }
        }
    }
    return $caps
}

$caps = Read-Capabilities
Write-Host "  parsed $($caps.Count) capabilities"

# Color map for depth
$depthColor = @{ "L0" = "#9ca3af"; "L1" = "#3b82f6"; "L2" = "#22c55e"; "L3" = "#f59e0b" }

# --- Generate map.html (capability grid) ---
$mapHtml = @"
<!DOCTYPE html>
<html><head><meta charset="utf-8"><title>BCP Capability Map</title>
<style>
body { font-family: system-ui, sans-serif; margin: 20px; background: #0f172a; color: #e2e8f0; }
h1 { font-size: 20px; }
.grid { display: grid; grid-template-columns: repeat(10, 1fr); gap: 8px; }
.fam { background: #1e293b; border-radius: 8px; padding: 8px; }
.fam h2 { font-size: 12px; margin: 0 0 6px 0; color: #94a3b8; }
.cap { padding: 6px; margin: 3px 0; border-radius: 4px; font-size: 10px; cursor: pointer; }
.cap:hover { outline: 1px solid #fff; }
.legend { margin: 12px 0; font-size: 12px; }
.legend span { display: inline-block; width: 14px; height: 14px; margin-right: 4px; vertical-align: middle; border-radius: 3px; }
</style></head><body>
<h1>BCP Capability Map</h1>
<div class="legend">
<span style="background:#9ca3af"></span>L0 Spec
<span style="background:#3b82f6"></span>L1 Stub
<span style="background:#22c55e"></span>L2 Works
<span style="background:#f59e0b"></span>L3 Hardened
</div>
<div class="grid">
"@

$families = $caps | Group-Object Family | Sort-Object Name
foreach ($fam in $families) {
    $mapHtml += "<div class='fam'><h2>$($fam.Name)<br>$($fam.Group[0].FamilyName)</h2>"
    foreach ($cap in ($fam.Group | Sort-Object Code)) {
        $color = $depthColor[$cap.Depth]
        $mapHtml += "<div class='cap' style='background:$color' title='$($cap.Invariant)'>$($cap.Code)<br>$($cap.Name)</div>"
    }
    $mapHtml += "</div>"
}
$mapHtml += "</div></body></html>"
Set-Content -Path "$views/map.html" -Value $mapHtml -Encoding UTF8
Write-Host "  wrote: views/map.html"

# --- Generate metrics summary ---
$dist = $caps | Group-Object Depth | ForEach-Object { "$($_.Name): $($_.Count)" }
Write-Host "  depth distribution: $($dist -join ', ')"

Write-Host "=== Done ===" -ForegroundColor Cyan
Write-Host "Open views/map.html in a browser."
```

### `bcp/maintain.ps1` — Maintenance Loop

```powershell
# BCP-SPEED Maintenance Loop
# Run this in a dedicated PowerShell window, or schedule via Task Scheduler.
# It runs the coordinator + maintainer tasks on an interval.

$intervalSeconds = 300   # 5 minutes
$stateDir = "state"
$logDir = "log"

function Write-Log {
    param([string]$signal, [hashtable]$payload)
    $today = Get-Date -Format "yyyy-MM-dd"
    $logFile = Join-Path $logDir "$today.yaml"
    $ts = Get-Date -Format "o"
    $entry = "- ts: $ts`n  agent: maintainer`n  signal: $signal`n  payload: $($payload | ConvertTo-Json -Compress)`n"
    Add-Content -Path $logFile -Value $entry -Encoding UTF8
}

Write-Host "=== BCP Maintenance Loop (every $intervalSeconds s) ===" -ForegroundColor Cyan

while ($true) {
    $now = Get-Date
    Write-Host "[$($now.ToString('HH:mm:ss'))] sweep..."

    # Task 1: Detect stalled leases (held > 2h with no recent log activity)
    if (Test-Path "$stateDir/leases.yaml") {
        # Simple staleness check: look for leases with expires_at in the past
        $leases = Get-Content "$stateDir/leases.yaml" -Raw
        if ($leases -match "status:\s*active") {
            # Placeholder: a full implementation parses and checks timestamps
            # Emit a reminder to review active leases
        }
    }

    # Task 2: Update metrics
    # (Delegates to generate.ps1 for depth distribution)
    & powershell -ExecutionPolicy Bypass -File generate.ps1 | Out-Null

    # Task 3: Log the sweep
    Write-Log -signal "MAINTENANCE_SWEEP" -payload @{ status = "completed" }
```

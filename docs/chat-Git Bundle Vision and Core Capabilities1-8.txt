# Ω-1 · THE WATCH SUBSTRATE — core event/trigger bus

> **Decision record: `D-425`** *(next free ID after the d423/d424 ratification; if D-425 is already consumed, renumber to the next free ID — the content is what lands, not the number).*
> **Type:** constitutional substrate addition — **core, not plugin.**
> **Precedence:** extends the ratified stack `Ω Kernel → Vault → Law → Plugin → Composition → Evidence → Forge → Surface`. Where this conflicts with the gate, the gate wins.
> **The one invariant this upgrade exists to protect:**
> **A watch may *notice* and *mint an event*. A watch may never *act*.** Action always routes through Law → Capability → Execution, exactly as any other canonical intent does. No privileged path for the watcher.

---

## 0 · What this is, and why it is core

Core Omega is event-sourced but currently **reactive to nothing.** The vault accumulates events; the law gates them; the kernel executes them. But there is no standing mechanism by which the system *notices that a condition has become true* and mints the corresponding event — no way to express *"when X happens, fire canonical intent Y."*

Today, that capability would be forced into a plugin ("a tile that watches the filesystem"). That is a sovereignty violation in disguise: **the thing that notices is the thing you must trust most, and it cannot be a third party.** Watching is a core duty. Ω-1 makes it one.

> **Ω-1 adds a first-class `Watch` primitive: a declarative, capability-scoped, law-gated standing condition that, when satisfied, mints a provenance-stamped event into the vault — and nothing else.**

Everything the user currently wants to express as *"when this happens, do that"* now lands in core:
- *"hydrate this tile when my phone joins home Wi-Fi"*
- *"alert me if this log file grows past 10MB"*
- *"at end of day, run the ledger hash"*
- *"dead-man's switch: if no heartbeat for 24h, fire intent Z"*

All of these are the same primitive: **a watch.**

## 1 · Constitutional placement

Insert the **Watch Substrate** as a kernel-owned service that reads the vault fold and the granted observation sources, and writes only to its own namespace through the law gate.

```
                 Ω KERNEL
                      │
        ┌─────────────┼─────────────────┐
        │             │                 │
     VAULT          LAW          WATCH SUBSTRATE   ← Ω-1
   (fold/rows)   (gate/refusal)   (standing watches)
        │             │                 │
        └──────┬──────┘        mints events only
               │                        │
        Canonical Intent ◄──── watch.event rows
               │
        Capability → Composition → Execution → Evidence
```

**Hard boundaries (constitutional):**
- The Watch Substrate is the **sole writer** of `ns watch` and of `watch.event` rows. No plugin, no tile, no surface writes watch rows directly.
- The Watch Substrate **never calls a capability**. It only mints events carrying a canonical intent. Execution of that intent is the normal pipeline's job.
- Every watch and every fired event is a **vault row with a provenance badge and a named retention rule.** A watch with no retention rule cannot exist.

## 2 · Contracts — hold from row one

### 2a · The `watch` row (registered in `ns watch`)

```
watch {
  id                 : stable identity
  predicate          : declarative, canonical condition (deterministic to evaluate)
  source             : vault | time | device | fs | stream
  grants             : capability grants authorizing observation of `source`
  onFire             : canonical intent  (NEVER a direct action)
  dedup              : none | window(duration) | once
  retention          : named retention rule for events this watch mints
  idempotencyScheme  : hash(watchRef, quantizedFireWindow)
  badge              : ProvenanceTier × generality
  state              : armed | paused | demoted
  createdBy          : principal + signature
}
```

### 2b · The `watch.event` row (minted on fire)

```
watch.event {
  watchRef           : → watch.id
  firedAt            : timestamp
  evidenceRef        : byte offsets proving the predicate held at firedAt
  canonicalIntent    : the watch.onFire intent, to be routed through Law
  idempotencyKey     : hash(watchRef, quantizedFireWindow)
  badge              : inherited from watch + tier of the firing path
}
```

**Two contract shapes that must hold from the first write** (cheap now, a migration each later):
1. **`onFire` is a canonical intent, not an action.** Storing anything else in `onFire` is a schema-level refusal.
2. **Every row carries both badge axes and a retention rule from row one.** A watch or event that ever existed without them cannot retroactively grow them.

## 3 · Operations

Follow the ratified op-naming discipline. Each op is law-gated; refusals return `{ code, sentence }`.

| Op | Effect | Law behavior |
|---|---|---|

## 4 · Determinism, sole writer, dedup

- **Deterministic evaluation:** the predicate is declarative; given the same vault state/granted source state, evaluation yields the same fire/no-fire result. Any ML used to *interpret* the watch's natural-language creation lives in the Intent Fabric at registration time — **never in the firing path.**
- **Sole writer:** only the Watch Substrate writes `watch` and `watch.event` rows. Any other writer is a named refusal.
- **Idempotent multi-device fire:** when a synced watch could fire on two devices, each mints an event carrying `idempotencyKey = hash(watchRef, quantizedFireWindow)`. Vault reconciliation keeps the first and records a **named merge record** for the duplicate (CP-1 discipline — one truth, no double-mint).

## 5 · Refusal register (literal sentences)

Enforced by gate/law row, not intention. Every refusal is `{ code, sentence }`, rendered as an ordinary boring event.

- `WATCH_NO_RETENTION` — *"I can't create this watch, because it has no rule for when its events are forgotten. Give it a retention rule and I will."*

- `WATCH_ONFIRE_NOT_INTENT` — *"A watch can only fire a canonical intent for the law to judge — it can't act directly. Rephrase the action as an intent."*
- `WATCH_NOT_SOLE_WRITER` — *"Only the watch substrate writes watch rows. Your write was refused."*
- `WATCH_FIRE_NOT_GRANTABLE` — *"`watch.fire` can't be granted to a plugin. It mints events; it doesn't delegate."*

## 7 · Interaction with the Intent Fabric and Law

A watch is **created** in natural language: *"alert me if the log grows."* The Intent Fabric resolves that into the declarative `predicate` + `onFire` canonical intent at **registration**, with confidence attached. Below threshold, it asks/narrows/refuses — never guesses.

At **fire time there is no language and no model.** The substrate evaluates the stored predicate deterministically, mints the event, and the stored `onFire` canonical intent enters the Law gate like any other intent. The law may refuse it — and if it does, the refusal is ledgered as a sentence. **The watcher never bypasses the gate.**

## 8 · Headless guarantee

Watches arm, evaluate, and mint events **with zero pixels.** CLI, MCP, and daemon see every fired event the canvas would render. Kill the canvas and the watch keeps firing — this is the proof that the watch substrate is a projection-agnostic core service, not a UI feature.

## 0 · The one sentence

> **Every running thing in Ω runs under a named budget that the governor alone enforces — and when the machine cannot afford everything, what sleeps is a ledgered sentence, never a crash.**

The canvas is infinite. The machine is not. That single asymmetry is the entire subject of this document.

---

## 1 · What dies without this — and why it dies quietly

### The failure mode

An infinite canvas of live objects is a promise that physics will break first. Each live tile may carry a running composition; each composition may hold a hidden browser realization (a Chrome instance), a local model context, worker processes, file watchers. Fifty live tiles is not a UI problem — it is fifty competing claimants on finite RAM, CPU, GPU, and process slots.

Without a governor, the failure sequence is always the same, and it is never legible:

1. Tiles accumulate. Nothing sleeps, because nothing *can* sleep — there is no lifecycle, only "running."
2. Memory pressure builds. The host OS starts swapping, then killing.
3. The canvas stutters, then freezes. Tiles go stale — the exact death named in the end-state table (*"tiles go stale"*), arriving not through Ω's machinery but around it.
4. The user experiences this as Ω being *broken*. No refusal was spoken. No row was written. The system did not say no — it died mid-yes.

**Explanation — why this matters constitutionally, not just operationally:** Ω's entire differentiator is that *the machinery is the product* — refusal, proof, provenance, memory. A crash is the one event that bypasses all four. When the OS kills Ω instead of Ω refusing the user, sovereignty silently transfers from the kernel to the host platform. The user's last experience of the product is an event Ω cannot ledger, cannot explain, and cannot heal. That is not a performance bug. It is a constitutional hole.

### The scenarios that land here

From the measured scenario mine, these have nowhere to go today:

- **#48** *"Which of my tiles are currently holding open a hidden Chrome instance, and what is its watchdog budget?"* — requires resource introspection in tile terms.
- **#50** *"Predict which tile I'll touch next and pre-hydrate it."* — requires speculative lifecycle movement.
- **#61** *"Ghost anything I haven't touched in 48 hours."* — requires a dormant/ghost lifecycle with coldness tracking.
- **#65** *"Refuse any tile that needs more than 2GB to hydrate."* — requires budget-as-policy and claim-time refusal.
- **#78** *"Which tiles are ghosted right now to save RAM?"* — requires lifecycle state to be queryable.
- **#97** *"Show me my most expensive tile in compute and vault writes."* — requires cost attribution per tile.
- **#18** *"Sync my layout to the laptop but keep the heavy contexts on the desktop GPU."* — requires locality: resources are device facts, not synced facts.
- **#23** *"Hydrate this tile when my phone joins home Wi-Fi."* — requires Ω-1's watch events to feed hydration claims.

All eight are the same question wearing different clothes: ***what is allowed to run, what must sleep, and who decides?*** Ω-2 is the answer, and the answer is core.

## 2 · Why this is core, and why it can never be a plugin

**Explanation — the sovereignty argument.** The rule established in Ω-1 generalizes: *whatever governs a sovereign duty must itself be trusted.* Watching is sovereign, so the watcher is core. Budgeting is sovereign for a stronger reason — it is the only layer where **physics constrains the law**.

Consider: the Law gate can permit everything. Permission is unbounded. But RAM is bounded, CPU is bounded, GPU is bounded. If resource governance lived in a plugin — say, a "memory manager" tile — the kernel would have no way to refuse that plugin when it starved the host. The machine would die before the law could speak. A plugin that controls its own budget controls the kernel's survival, and no privileged path exists in Ω — *not for the Forge, not for first-party, not for the governor itself.*

Therefore the governor sits **in the kernel, on the execution path**, and every composition — including compositions forged by `forge.author`, including the tooling that builds tooling — runs under it. The governor is the one principal that cannot grant itself an exception, because an exception for the governor is the end of the budget.

## 3 · The pipeline — two gates, fixed order

Ω-2 inserts the second gate. From this upgrade forward, nothing executes on one permission:

```
Canonical Intent
      ↓
┌─────────────┐
│    LAW      │  may it?        consent · policy · capability grants
└──────┬──────┘
       ↓  permitted
┌─────────────┐
│  GOVERNOR   │  can it?        budget · claim · lifecycle
└──────┬──────┘
       ↓  affordable
EXECUTION (ExecutionKernel: execute → verify → journal)
       ↓
EVIDENCE (ledger rows, both gates cited)
```

**Explanation — why law first, governor second, and why the order is constitutional:**

- **Attribution of refusal.** A user deserves to hear *"this is forbidden"* before they hear *"this is unaffordable."* If the governor ran first, a prohibited action with a large footprint would be refused on budget grounds — and the user would walk away believing they just needed a bigger machine, when the truth was that Ω said no on principle. The law speaks first so refusals mean what they say.
- **No physics spent on the impermissible.** The governor never evaluates affordability for what the law will kill. Claims are only minted downstream of permission.
- **Both gates emit sentences.** A law refusal is `{code, sentence}`. A governor refusal is `{code, sentence}`. The W5 atom's discipline — *a refusal rendered as an ordinary boring event* — survives contact with physics. A budget refusal is not an error; it is Ω telling the truth about the machine.

Every executed row now cites **two gates**: the law row that permitted it and the claim row that afforded it. *"Why was this running?"* becomes a query with two answers, both with byte offsets.

## 4 · The tile lifecycle — three states, one writer

The live object stays a **5-tuple** (identity · composition · vault binding · spatial placement · provenance badge). Ω-2 deliberately does **not** add a sixth field. Lifecycle state is **derived from the governor's ledger**, never stored on the object.

**Explanation — why state is a fold, not a field:** the object must never carry authority over its own resource condition, for the same reason the tile never polls — it observes. If the tile stored its own state, two truths would exist (the tile's claim about itself and the governor's ledger), and Ω's constitution has exactly one. State is a fold over `tile.transition` rows. A tile that *thinks* it is hydrated while the governor says ghosted is a stale-state bug by design; a tile that *reads* its state cannot go stale.

### The states

| State | What runs | What survives | Cost |
|---|---|---|---|
| **`hydrated`** | composition live; realizations attached; processes running | everything | full claim held |
| **`dormant`** | composition paused; warm briefly; cheap return | everything | minimal claim held (TTL-named) |
| **`ghost`** | **nothing runs** | identity · vault binding · placement · badge — all vault data | zero claim |

**Explanation — why three states and not two:** the naive design is binary (running / not running). But rehydrating a cold tile from zero and resuming a warm one are different costs and different latencies. `dormant` is the seam between them: a paused composition that can return in milliseconds, versus a ghost that must re-claim, re-attach realizations, and rebuild from the vault. The `dormant` TTL is a named rule — *nothing sleeps on an unnamed timer*, in the same discipline as retention and Ω-1's watch predicates.

### Transitions

```
ghost ──(firm claim granted)──→ hydrated
ghost ──(provisional claim)───→ dormant      ← prediction ceiling, see CP-B
dormant ──(firm claim)────────→ hydrated
hydrated ──(rest / idle TTL)──→ dormant
dormant ──(TTL expiry / pressure)→ ghost
hydrated ──(pressure / enforcement)→ ghost
```

Every transition is a ledger row. **Sole writer: the governor.** Any other writer of lifecycle rows is a named refusal — mirroring Ω-1's sole-writer discipline for `watch.fire@1`.

### The tile is still live when it is a ghost

**Explanation — the subtle point implementers will get wrong:** ghosting is not death, and the canvas does not show a corpse. A ghost tile's rows are all vault data: its identity, its binding, its placement in `ns canvas`, its badge. The canvas surface renders it from the vault — last-known values, provenance intact, badge visible, tap-to-rehydrate offered. The tile that watches nothing and runs nothing still *means* everything. This is how "remembers exactly where you left everything, across devices" survives resource pressure: the layout never depended on the thing that got put to sleep.

## 5 · The governor — budgets, claims, and pressure

### Budgets

A budget is a named cap with an owner and a signature. No composition executes without one.

```
gov.budget {
  id
  scope        : device | ns <namespace> | tile <identity>
  caps         : ram · cpu-shares · gpu · proc-count
  onPressure   : evict-coldest | refuse | ask
  namedBy      : principal + signature
}
```

**Explanation — budget-as-policy vs claim-as-physics:** budgets are *user intent* ("I refuse tiles over 2GB" — scenario #65), so they are ordinary synced vault facts: the rule follows the owner across devices. Claims (below) are *physical events on a specific machine*, so they are device-tagged. Policy syncs. Physics does not. One vault, no second truth — CP-1 discipline held.

### Claims

A claim is a request to spend. Claims are the only way anything runs.

```
gov.claim {
  id
  claimant     : composition ref
  request      : ram · cpu-shares · gpu · proc-count
  mode         : firm | provisional
  origin       : user-intent | watch-ref | prediction-ref
  deviceId     : the machine this claim is physical on
  decision     : granted | refused | preempted
  gateRef      : the law row that permitted this claim to be evaluated
  evidenceRef
}
```

**Explanation — why every claim cites its law row:** this is the two-gate pipeline expressed as data. A granted claim that cannot point at a permission is a constitutional violation discoverable by query. Auditors, the Forge's proof discipline, and Ω-8's future failure simulations all read this column.

### Pressure and eviction

When grants cannot fit caps, the governor resolves pressure by its named policy. Default: **evict-coldest.**

**Coldness** is measured by vault-access recency of the rows the tile binds to, tie-broken by cheapest-to-rehydrate. Nothing else enters the ordering.

**Explanation — why badges never enter eviction order:** badges are the trust axis (who vouches, what it is proven against). Eviction is the resource axis. Ω's constitution never lets axes overload each other — ProvenanceTier and generality never merge, and neither do trust and thermodynamics. A `speculative` tile is not evicted before a `harvested` one, because that would silently turn badges into resource priority — an undocumented, unrefusable privilege. The refusal register below makes this a hard gate, because the temptation to "evict the untrusted stuff first" will arrive, and it must arrive as a refusal.

### Enforcement

The watchdog (CP-2) is the governor's enforcement arm. A composition that exceeds its granted claim is stopped by the watchdog; the stop is a `tile.transition` row with `cause = enforcement`, and — for user-forged tiles — a spoken sentence, because the user who forged it must hear it starve. **Quietness is UX; the authority is never quiet.**

## 6 · Choicepoints resolved

### CP-Ω2-A · Where the governor sits

**Decision: in the kernel, on the execution path, between Law and ExecutionKernel. No bypass, no exemption, including for first-party and for `forge.author`.**

**Explanation:** any placement outside the path (an advisor, a monitor, a "resource plugin that watches the kernel") recreates the constitutional hole from §2 — something the kernel cannot refuse. The governor's power is exactly the power to say no to the kernel's own compositions, so it must sit where execution passes through it.

### CP-Ω2-B · Prediction — how far speculation may reach

**Decision: predictions may warm, never hydrate. Provisional claims move `ghost → dormant` only. Full hydration requires a firm claim (user intent, watch fire, or composition need). Provisional preemptions are boring rows, not sentences.**

**Explanation:** scenario #50 ("predict and pre-hydrate") is the trap. A governor that lets speculation spend real resources at full rate has handed the budget to an oracle — and oracles are exactly the kind of unproven realization Ω badges as `speculative`. The ceiling rule keeps prediction *cheap and reversible*: warming a dormant tile costs little and cancels silently, while the expensive transition (full hydration) stays reserved for things a human, a watch, or a running composition actually asked for. Prediction proposes; the governor disposes; the ceiling is the refusal that keeps it honest. When a real predictive model arrives later, it enters as any realization does — proposing provisional claims through the same door, conferring no authority.

### CP-Ω2-C · Eviction ordering

**Decision: coldest by vault-access recency, tie-broken by cheapest rehydration. No badge weighting, no provenance weighting, no first-party priority. Ever.**

**Explanation:** see §5. Fairness here is thermodynamic, not reputational. The moment eviction learns about badges, badges become a scheduling system, and scheduling becomes an unbadgeable, unrefusable privilege. This is the most likely place a future Forge will try to be clever, so the refusal register names it in advance.

### CP-Ω2-D · Locality across devices

**Decision: one vault, device-tagged physics. Budgets (policy) sync as vault facts. Claims and transitions carry `deviceId`; they are ledgered for audit but are never executed remotely. My laptop's RAM is not my desktop's GPU.**

**Explanation:** scenario #18 ("sync the layout, keep the heavy contexts on the desktop") resolves for free once this lands. The layout is `ns canvas` vault data — it syncs. The contexts are claims on a specific device — they stay. No locality feature is built, because locality falls out of the vault being append-only and the claims being device-scoped. Syncing claims themselves would be noise at best and a lie at worst: a "granted" claim from another machine is a statement about a machine that isn't here.

### CP-Ω2-E · Healing changes cost

**Decision: any realization promotion (vN → vN+1) invalidates the claims of compositions using it. Revalidation before next run.**

**Explanation:** a healed provider may be heavier, lighter, or differently shaped. If v2 silently inherited v1's claim, the budget would be a statement about a composition that no longer exists. Healing already requires ratification and proof; re-claiming is the same discipline applied to physics. The healing loop and the governor must agree about what a composition *is*, or provenance lies about cost.

> **Decision record: `D-427`** *(follows D-425/Ω-1, D-426/Ω-2; renumber to the next free ID if consumed — the content is what lands, not the number).*

## 0 · The one sentence

> **Every word a model sees is a sealed, budgeted, inspectable artifact of core — so that *"what did it know when it said that?"* is forever a query, never a shrug.**

The vault is append-only and unbounded. The context window is finite. Between them sits the most dangerous gap in an AI operating system: *something* must choose what the model sees. If that something is a plugin, provenance dies at the exact moment it matters most — because every downstream answer is only as honest as the selection that fed it.

## 1 · What dies without this — and why it dies invisibly

### The failure mode

Without a core context layer, assembly happens **implicitly inside realizations** — each provider plugin formats its own prompt from whatever it can reach. That single fact kills five constitutional properties at once, and kills them quietly:

1. **Provenance dies.** *"Why did it say that?"* has no answer, because the input was never a row. The ledger records the response but not the knowledge that produced it.
2. **Replay dies.** A hallucination cannot be re-examined, because no one can reconstruct what the model saw.
3. **Tuning dies.** *"My memory retrieves junk"* has no lever, because retrieval was never a named policy — it was whatever a plugin happened to do.
4. **Cost dies.** Token spend cannot be attributed to namespaces, intents, or tiles, because the assembler never counted.
5. **Sovereignty dies.** A realization that reads the vault directly is a watcher that acts — the exact violation Ω-1 was built to refuse, re-entering through the model door.

**Explanation — why this is the deepest of the substrate gaps:** Ω's differentiator is honesty as architecture. But the *locus of dishonesty* in any AI system is not the output — outputs are visible, badgeable, refusable. The locus of dishonesty is the **input selection**: the invisible choice of what context earns the model's attention. A system that badges every tile and ledgers every event but leaves prompt assembly implicit has built a glass house with a curtained room in the middle. Ω-3 removes the curtain.

### The scenarios that land here

From the measured scenario mine:

- **#64** *"Show me the exact prompt the Context Router assembled for this response."* — requires the assembled context to be an inspectable artifact.
- **#27** *"Replay this hallucination and show me exactly what context it was fed."* — requires sealed, replayable context.
- **#87** *"Demote my memory spine — it retrieves too much irrelevant context."* — requires retrieval to be a named, tunable, demotable policy.
- **#8** *"How many tokens did I burn on Claude vs local Llama for `ns.finance` this month?"* — requires token accounting joined to context artifacts.
- **#97** *"My most expensive tile in compute and vault writes."* — token cost is half of "expensive"; Ω-2 measured compute, Ω-3 measures cognition.
- **#20 / #77** *"Replay my morning with the LLM swapped GPT→Qwen / dummy model."* — these were rated ◐ after Ω-2 (seam existed, contract didn't). **Ω-3 is the contract that completes them.** A sealed context is realization-agnostic by construction; swapping the realization against an identical context is what makes the diff meaningful.
- **#83** *"Why did you choose the Ollama realization over Claude for this intent?"* — realization *selection* is capability resolution's job, but its rationale row joins the context artifact here, so the full "why" is one query.

All seven are the same question: ***what did the system know, how did it choose to know it, and can I see the receipt?***

## 2 · Why this is core, and why a plugin can never do it

**Explanation — the sovereignty argument, third face.** The pattern established by Ω-1 and Ω-2 generalizes into a rule: *whatever mediates between the user's world and the machine's actions must be trusted, and therefore must be core.*

- Ω-1: watching mediates between the world and events → core.
- Ω-2: budgeting mediates between desire and physics → core.
- Ω-3: **selection mediates between memory and cognition → core.**

A Forge can build a *scorer* — a relevance model, a ranking heuristic, a summarization style. It can never build the *assembler*. If it could, the Forge would control what every realization in the system knows, which is control of the system's mind. That is not a capability; it is a constitution, and no privileged path exists in Ω — not for third-party Forges, not for `forge.author`, not for first-party.

Note the mirror-image: this is also why the **Law gate's discipline survives contact with models.** The gate consumes canonical intent, never raw model output (Intent Fabric doctrine). Ω-3 enforces the symmetric rule on the way in: **the model consumes sealed context, never raw vault.** Both boundaries hold. The model is a realization — substitutable, revocable, badged — and realizations are guests in the house, not owners of the library.

## 4 · Contracts — hold from row one

### 4a · The `ctx` artifact (stored in `ns ctx`, sole writer: the assembler)

```
ctx {
  id
  intentRef        : the canonical intent this context serves
  policyRef        : the named assembly policy in force
  rows             : ordered refs (byte offsets) of vault rows included
  transforms       : ordered list — truncation · summarization refs · ordering scorer ref
  scorerRefs       : any realized scorers used, badged (tier × generality)
  budgetClaimRef   : the Ω-2 claim that afforded this context
  tokenCount       : measured, not estimated, after assembly
  seal             : content hash of the assembled artifact
  badge            : inherited axes + assembly-path tier
}
```

### 4b · The `ctx.policy` row (the tunable memory spine)

```
ctx.policy {
  id
  scope            : device | ns <namespace> | tile <identity> | global
  weights          : per-namespace relevance weights (recency, binding, explicit-ref)
  scorerGrants     : which realized scorers may participate, badged
  budgetDefaults   : standing token caps per scope
  namedBy          : principal + signature
}
```

**Two contract shapes that must hold from the first write** (cheap now, a migration each later):

1. **Every W5 event citing a realization cites a `ctx` ref.** A model response without a context artifact is a schema-level violation — the response exists but its knowledge doesn't, which is the exact lie this upgrade forbids.
2. **Every transform is named.** If rows were truncated, the truncation is recorded. If rows were summarized, the summarization is a ref to a nested atom (§6, CP-Ω3-C). An unnamed transform is `CTX_UNSORTED_INVISIBLE` — a hard gate error, not a warning.

## 5 · Operations

| Op | Effect | Law behavior |
|---|---|---|
| `ctx.assemble@1` | build a sealed context for a permitted, budgeted intent | **sole writer: the assembler**; internal to the execution path |
| `ctx.policy.set@1` | create/amend an assembly policy | consent required; signature recorded; reversible |
| `ctx.score@1` | **realization slot** — relevance scoring | grantable; scorer output sealed with its badge + confidence |
| `ctx.summarize@1` | **realization slot** — compression via nested atom | grantable; see CP-Ω3-C |
| `ctx.inspect@1` | render a ctx artifact in plain words | read; the prompt is a query, every surface gets it |
| `ctx.replay@1` | re-feed a sealed ctx to a named realization (same or different) | law-gated; produces a new W5 event citing the *same* ctx |

**Explanation — `ctx.replay` is the completion of the ◐:** scenarios #20 and #77 asked for replay-with-substitution and were marked ◐ because the seam existed but the contract didn't. The contract is this: **a sealed context is realization-agnostic by construction.** Replaying the identical `ctx` against Qwen, a dummy model, or a local Ollama produces a *new event that cites the same artifact* — so the diff between outputs is attributable to the realization and nothing else. That is what makes the diff evidence instead of vibes. Replay is also the primitive Ω-8 (Failure Simulation) will rehearse against; this is where simulation's ground truth comes from.

## 6 · Choicepoints resolved

### CP-Ω3-A · Where relevance comes from

**Decision: deterministic-first selection — recency, namespace binding, explicit refs, capability scope — all pure vault folds. Semantic/ML relevance may participate only as a badged, grantable `ctx.score` realization whose scores are sealed into the artifact with confidence and version. No invisible sorting. Ever.**

**Explanation:** the sorting of a context *is* an editorial act — it decides what the model weighs. If sorting is invisible, the system's honesty is a function of whichever scorer happened to be installed, which is a badge evasion: influence without provenance. Scorers enter through the same door as every realization — grant, badge, seal — and a context assembled with a `speculative` scorer says so on its face. When a scorer is demoted, contexts it shaped remain truthful: they were shaped by it, and the row says so.

### CP-Ω3-B · Who assembles

**Decision: the assembler is core, sole writer of `ns ctx`. A Forge may ship scorers and summarizers; no Forge, first-party or third-party, ships an assembler.**

**Explanation:** §2's sovereignty argument made concrete. The assembler is a constitution, not a capability. Note this is the same shape as `watch.fire@1` (Ω-1) and lifecycle writes (Ω-2) being sole-writer: Ω's pattern is that the *minting* operations — the ones that create reality — are never grantable, while the *shaping* operations — scoring, summarizing, proposing — are open to all through the same door.

### CP-Ω3-C · Summarization

**Decision: summarization is a nested W5 atom. A `ctx.summarize` call assembles its own deterministic context, feeds a badged summarization realization, and the output becomes a vault row cited as a transform. Recursion depth is bounded by named policy. The assembly step itself never calls a model.**

**Explanation:** the naive design lets the assembler silently rewrite rows to fit the window — which is editing the user's memory inside the machinery that's supposed to be honest about it. The nested-atom rule makes compression an *event*: it has a principal (who authorized the policy), a realization (which model compressed it), evidence (inputs and outputs), and a badge. Compression is now as honest as anything else Ω does. The recursion bound is the refusal that keeps it from being clever: assembly is deterministic, always; only compression may think, and only inside a ledgered box.

### CP-Ω3-D · Forgetting propagates honestly

**Decision: `ctx` artifacts are refs + hashes. When a referenced row is shredded under retention (Ω's named-retention discipline), the ctx gains a `vacated` marker at that position. Replay after forgetting does not silently omit — it reports *"this context included a row you asked me to forget."***

**Explanation:** memory belongs to its owner — including the right to be forgotten. But forgetting must not become *silent rewriting of history*. A vacated marker is the honest record of the collision: the context existed, the row was yours, you asked for it to go, and now the receipt shows the hole where it was. This is the mirror held steady: Ω does not pretend it never knew, and does not keep what you told it to drop. Both truths, one row.

### CP-Ω3-E · Indexes are projections, never truth

**Decision: any retrieval index (vector, inverted, otherwise) is derived, disposable, rebuildable from the vault fold. No index is a second source of truth. An index that cannot be regenerated byte-equivalently from vault rows is a gate error.**

**Explanation:** this is CP-1's doctrine (*one vault, never a second truth*) applied to the mind spine. Embeddings will tempt the design into "the vector store is the memory." It isn't. The vault is the memory; the index is a projection, the way selectors are projections of canonical shapes in the healing loop, the way surfaces are projections of `surfaceOpMeta`. Projections rot and regenerate; truth appends.

- **#20 / #77** *"Replay my morning with the LLM swapped GPT→Qwen / dummy model."* — these were rated ◐ after Ω-2 (seam existed, contract didn't). **Ω-3 is the contract that completes them.** A sealed context is realization-agnostic by construction; swapping the realization against an identical context is what makes the diff meaningful.

All seven are the same question: ***what did the system know, how did it choose to know it, and can I see the receipt?***

## 2 · Why this is core, and why a plugin can never do it

**Explanation — the sovereignty argument, third face.** The pattern established by Ω-1 and Ω-2 generalizes into a rule: *whatever mediates between the user's world and the machine's actions must be trusted, and therefore must be core.*

The model is a realization — substitutable, revocable, badged — and realizations are guests in the house, not owners of the library.

### 4a · The `ctx` artifact (stored in `ns ctx`, sole writer: the assembler)

ctx.policy {

**Two contract shapes that must hold from the first write** (cheap now, a migration each later):

2. **Every transform is named.** If rows were truncated, the truncation is recorded. If rows were summarized, the summarization is a ref to a nested atom (§6, CP-Ω3-C). An unnamed transform is `CTX_UNSORTED_INVISIBLE` — a hard gate error, not a warning.

## 6 · Choicepoints resolved

### CP-Ω3-A · Where relevance comes from

**Decision: deterministic-first selection — recency, namespace binding, explicit refs, capability scope — all pure vault folds. Semantic/ML relevance may participate only as a badged, grantable `ctx.score` realization whose scores are sealed into the artifact with confidence and version. No invisible sorting. Ever.**

**Explanation:** the sorting of a context *is* an editorial act — it decides what the model weighs. If sorting is invisible, the system's honesty is a function of whichever scorer happened to be installed, which is a badge evasion: influence without provenance. Scorers enter through the same door as every realization — grant, badge, seal — and a context assembled with a `speculative` scorer says so on its face. When a scorer is demoted, contexts it shaped remain truthful: they were shaped by it, and the row says so.

### CP-Ω3-B · Who assembles

**Decision: the assembler is core, sole writer of `ns ctx`. A Forge may ship scorers and summarizers; no Forge, first-party or third-party, ships an assembler.**

**Explanation:** §2's sovereignty argument made concrete. The assembler is a constitution, not a capability. Note this is the same shape as `watch.fire@1` (Ω-1) and lifecycle writes (Ω-2) being sole-writer: Ω's pattern is that the *minting* operations — the ones that create reality — are never grantable, while the *shaping* operations — scoring, summarizing, proposing — are open to all through the same door.

### CP-Ω3-C · Summarization

**Decision: summarization is a nested W5 atom. A `ctx.summarize` call assembles its own deterministic context, feeds a badged summarization realization, and the output becomes a vault row cited as a transform. Recursion depth is bounded by named policy. The assembly step itself never calls a model.**

**Explanation:** the naive design lets the assembler silently rewrite rows to fit the window — which is editing the user's memory inside the machinery that's supposed to be honest about it. The nested-atom rule makes compression an *event*: it has a principal (who authorized the policy), a realization (which model compressed it), evidence (inputs and outputs), and a badge. Compression is now as honest as anything else Ω does. The recursion bound is the refusal that keeps it from being clever: assembly is deterministic, always; only compression may think, and only inside a ledgered box.

### CP-Ω3-D · Forgetting propagates honestly

**Decision: `ctx` artifacts are refs + hashes. When a referenced row is shredded under retention (Ω's named-retention discipline), the ctx gains a `vacated` marker at that position. Replay after forgetting does not silently omit — it reports *"this context included a row you asked me to forget."***

**Explanation:** memory belongs to its owner — including the right to be forgotten. But forgetting must not become *silent rewriting of history*. A vacated marker is the honest record of the collision: the context existed, the row was yours, you asked for it to go, and now the receipt shows the hole where it was. This is the mirror held steady: Ω does not pretend it never knew, and does not keep what you told it to drop. Both truths, one row.

### CP-Ω3-E · Indexes are projections, never truth

**Decision: any retrieval index (vector, inverted, otherwise) is derived, disposable, rebuildable from the vault fold. No index is a second source of truth. An index that cannot be regenerated byte-equivalently from vault rows is a gate error.**

**Explanation:** this is CP-1's doctrine (*one vault, never a second truth*) applied to the mind spine. Embeddings will tempt the design into "the vector store is the memory." It isn't. The vault is the memory; the index is a projection, the way selectors are projections of canonical shapes in the healing loop, the way surfaces are projections of `surfaceOpMeta`. Projections rot and regenerate; truth appends.

# Ω-4 · THE TRUST MESH — Local Key Management & Device Identity

> **Decision record: `D-428`** *(follows D-425/Ω-1, D-426/Ω-2, D-427/Ω-3; renumber to the next free ID if consumed — the content is what lands, not the number).*
> **Type:** constitutional substrate addition — **core, not plugin.**
> **Precedence:** extends the ratified stack. Where this conflicts with the gate, the gate wins.
> **Requires:** Ω-1, Ω-2, Ω-3 green. The vault is append-only (Ω spine), the mind is sealed (Ω-3), and the physics are governed (Ω-2). But none of it is sovereign if the keys that sign it can be stolen, lost, or silently duplicated by a third party.
> **The one invariant this upgrade exists to protect:**
> **Sovereignty requires a self-owned identity that survives the loss, theft, or revocation of any single device, without ever asking a remote server for permission.**

---

## 0 · The one sentence

> **Every row in the vault is vouched for by a cryptographic signature that belongs to the user’s hardware, not their account — and the system can mathematically prove when a device has been exiled, even if that device is currently offline.**

Ω’s manifesto demands "local-first, network-optional" and "no cloud account, ever required." It demands multi-device sync via CRDTs and signatures on every row ("who vouches"). But the ratified stack left a gaping hole: *where do the keys live, and how do they survive the physical world?* If identity is managed by a plugin, or relies on a cloud-backed keychain, sovereignty is an illusion. Ω-4 builds the Trust Mesh.

---

## 1 · What dies without this — and why it dies silently

### The failure mode

Without a core Trust Mesh, multi-device local-first systems inevitably fall into one of two traps:
1. **The Cloud Trap:** Keys are synced via a central server (e.g., a vendor account). The moment the server goes down, or the vendor bans the user, the user loses their machine. Sovereignty is revoked by a remote admin.
2. **The Fragility Trap:** Keys are generated locally on Device A. Device A is lost, dropped in a river, or stolen. The user’s entire append-only vault, their badges, their forged tiles, and their layout are permanently orphaned. There is no recovery because there is no server to reset a password.

**Explanation — why this matters constitutionally:** Ω's provenance model ("who vouches") relies on signatures. If a stolen laptop can continue signing vault rows, the provenance is a lie. If a user cannot revoke a compromised device without an internet connection, the Law Gate is bypassed by physical theft. The Trust Mesh is the mechanism that makes "sole writer" and "who vouches" physically enforceable.

### The scenarios that land here

From the measured scenario mine:
- **#22** *"Prove to me that this specific action didn't leak my private signing key to the network."* — requires architectural proof of hardware-bound keys.
- **#36** *"What happens to my multi-device trust mesh if I revoke the signing key for my work laptop right now?"* — requires a causal revocation protocol.
- **#44** *"Revoke the `forge.author` privilege from my secondary device."* — requires capability-scoped device keys.
- **#91** *"Asking the system to simulate what happens if I lose my primary signing key."* — requires a decentralized recovery protocol.

---

## 2 · Why this is core, and why a plugin can never do it

**Explanation — the sovereignty argument, fourth face.** 
- Ω-1: Watching is sovereign → core.
- Ω-2: Budgeting is sovereign → core.
- Ω-3: Selection is sovereign → core.
- Ω-4: **Identity is sovereign → core.**

If a plugin manages keys, that plugin holds the master password to the user's digital life. A third-party Forge could silently exfiltrate the root key, or a buggy first-party plugin could corrupt the keychain, bricking the vault. The Trust Mesh must sit in the kernel, interfacing directly with the host OS's Secure Enclave (TPM, Apple Secure Enclave, Android StrongBox). The kernel is the only entity trusted to hold the gates of identity.

---

## 3 · The Architecture — Principals, Nodes, and the Mesh

The Trust Mesh introduces a strict two-tier cryptographic hierarchy.

### 3a · The Principal (The Root)
The **Principal** is the human user. The Principal possesses a **Root Key**. 
- The Root Key *never* signs daily vault rows. It is too valuable to expose to daily execution paths.
- The Root Key lives exclusively in a hardware-backed Secure Enclave. It is mathematically un-extractable by the OS, let alone by Ω or any plugin.
- The Root Key's only job is to sign **Enrollment Certificates** for devices and **Revocation Edicts**.

### 3b · The Node (The Device)
A **Node** is a physical machine (desktop, laptop, phone). 
- When a new device is added, it generates a local **Device Key** in its own Secure Enclave.
- The Principal uses their Root Key (via a local, out-of-band pairing ritual like a QR code or local-network PAKE) to sign an Enrollment Certificate binding the Device Key to the Principal.
- The Device Key signs the daily vault rows, watch events, and context artifacts.

### 3c · The Mesh (The Sync & Revocation Fabric)
Because there is no central server, the "mesh" is simply the append-only vault log itself. 
- Enrollment is a vault row (`trust.enrollment`).
- Revocation is a vault row (`trust.revocation`).
- When Device A and Device B sync via CRDTs, they exchange their vault logs. If Device B sees a `trust.revocation` row signed by the Root Key that targets Device A's key, Device B instantly rejects any post-revocation writes from Device A.

---

## 4 · Contracts — hold from row one

### 4a · The `trust.enrollment` row
```
trust.enrollment {
  principalRef     : the Root Identity
  deviceKeyPub     : the public half of the Node's Device Key
  capabilityGrants : what this specific device is allowed to do (e.g., `forge.author`, `law.approve`)
  signedBy         : Root Key signature
}
```

### 4b · The `trust.revocation` row
```
trust.revocation {
  targetDeviceKey  : the public key being exiled
  reason           : lost | stolen | compromised | user-requested
  signedBy         : Root Key signature (or quorum of recovery shards)
}
```

**Two contract shapes that must hold from the first write:**
1. **No Device Key signs its own enrollment.** A device cannot bootstrap itself into the mesh. It must be invited by the Root Key or an already-trusted device with delegation rights.
2. **Revocations are causal and absolute.** Once a `trust.revocation` row enters the vault fold, any vault row signed by the target key with a timestamp *after* the revocation is treated as a hostile forgery and rejected by the Law Gate.

## 6 · Choicepoints resolved

### CP-Ω4-A · Where the Root Key lives
**Decision: The Root Key is generated and stored exclusively in the host OS's hardware Secure Enclave (TPM 2.0, Secure Enclave, StrongBox). Ω never touches the private key bytes. All signing is done via OS-level cryptographic APIs that return only the signature.**
**Explanation:** This is the architectural answer to scenario #22 (*"Prove it didn't leak"*). The proof is not a policy; it is physics. If the key bytes never enter user-space memory, they cannot be leaked by a compromised plugin, a memory dump, or a network exfiltration bug. The Trust Mesh delegates the math to the silicon.

### CP-Ω4-B · Recovery of a lost Root Key
**Decision: Shamir's Secret Sharing (SSS) split into physical shards. No cloud backup. No "email a reset link."**
When the Root Key is generated, the user is prompted to split it into $N$ shards (e.g., 3 of 5). These shards are exported to physical media (USB drives, printed QR codes, or enrolled secondary offline devices). 
**Explanation:** Scenario #91 (*simulate losing the primary key*). If the user loses their primary device and has no cloud account, the *only* way back in is to physically gather the shards and run `trust.recover@1`. This is the ultimate expression of local-first sovereignty: the user's security is bounded by their physical security, not a vendor's password reset flow.

### CP-Ω4-C · Offline Revocation & The Split-Brain Problem
**Decision: Revocation is an append-only vault event. Sync reconciliation enforces causal ordering.**
If Device A is stolen, the user revokes it from Device B. Device A is offline and keeps generating local vault rows. When Device A eventually connects to the network and tries to sync with Device B, Device B's CRDT engine sees the `trust.revocation` row. Because the revocation is signed by the Root Key (which Device A cannot forge), Device B rejects all of Device A's post-revocation rows as invalid.
**Explanation:** This solves scenario #36 (*what breaks when I revoke?*). The stolen device doesn't "break" locally—it just becomes a ghost. Its writes are mathematically orphaned the moment it touches the honest mesh.

### CP-Ω4-D · Capability-Scoped Device Keys
**Decision: Device Keys are not omnipotent. The `trust.enrollment` row carries a capability grant.**
Scenario #44 (*revoke `forge.author` from device 2*). A user can enroll a secondary device (e.g., a travel laptop) with a restricted grant: it can read the vault and execute basic intents, but it lacks the `forge.author` capability. The Law Gate checks the device's specific grant before allowing a Forge operation.
**Explanation:** Trust is not binary. A device can be trusted with memory but not with the ability to alter the kernel's tooling.

# Ω-5 · VAULT ANALYTICS & PROJECTION — The Honest Heatmap

> **Decision record: `D-429`** *(follows D-425/Ω-1, D-426/Ω-2, D-427/Ω-3, D-428/Ω-4; renumber to the next free ID if consumed — the content is what lands, not the number).*

## 0 · The one sentence

> **You cannot govern what you cannot see, but seeing must never compromise the truth — so every chart, heatmap, and topology graph is a mathematically provable, disposable projection that knows exactly how stale it is.**

The vault is the memory. The analytics layer is the *mirror* held up to the memory. If the mirror becomes a separate database (a Postgres analytics warehouse, a Redis cache, a vector store) that drifts from the vault, sovereignty breaks. The user is now looking at a lie. Ω-5 ensures that every aggregation is a verifiable fold over the single source of truth.

## 1 · What dies without this — and why it dies invisibly

### The failure mode

Without a core projection engine, users who want to understand their system ("What is my most used tool?", "Where is my compute going?", "Show me the shape of my week") are forced into one of two traps:
1. **The BI Trap:** Exporting vault data to an external tool (Metabase, Grafana, a custom Python script). This breaks local-first sovereignty and creates an unbadged, unregulated shadow pipeline.
2. **The Mutable State Trap:** Building internal "summary tables" or "counters" that increment on write. The moment a bug occurs, or a row is shredded under retention, the counter drifts from the vault. The summary table becomes a *second source of truth*, and the system begins making decisions based on a phantom reality.

**Explanation — why this matters constitutionally:** Ω's differentiator is forensic honesty. But honesty is useless if it takes 40 minutes to query a 50GB append-only log just to find out which tile used the most RAM. Analytics must be fast, but speed usually requires caching, and caching introduces drift. Ω-5 solves this by making *staleness* a first-class, visible metric.

## 3 · The Architecture — Folds, Projections, and Materializations

Ω-5 introduces a strict three-tier analytics pipeline.

### 3a · The Fold (The Query)
A deterministic function that maps vault rows to a summary state. 
*Example: "Count `gov.claim` rows where `decision=granted`, grouped by `claimant` and `deviceId`, bounded by time $T$."*

### 3b · The Projection (The Schema)
The definition of the fold, stored as a vault row. It defines the dimensions, the metrics, and the retention policy of the resulting materialization.

### 3c · The Materialization (The Cache)
The actual computed result (the heatmap, the bar chart data). **Crucially, every materialization row carries a `vaultLSN` (Log Sequence Number) or byte-offset watermark.** It explicitly states: *"I am the truth of the vault up to byte offset X."*

```
                 Ω VAULT (Append-Only Log)
                      │
        ┌─────────────▼─────────────────┐
        │    PROJECTION ENGINE (Core)   │  Reads vault fold
        │    (Deterministic, stateless) │
        └─────────────┬─────────────────┘
                      │
        ┌─────────────▼─────────────────┐
        │   ns analytics (Materialized) │  Disposable, rebuildable
        │   (Carries vaultLSN watermark)│
        └─────────────┬─────────────────┘
                      │
               Surface / Canvas
          (Renders data + Staleness Delta)
```

## 4 · Contracts — hold from row one

### 4a · The `analytics.projection` row
```
analytics.projection {
  id
  name               : "tile_resource_heatmap"
  foldDefinition     : deterministic query plan (e.g., SQL/AST over vault schema)
  sourceNamespaces   : ["gov.claim", "tile.transition"]

### 4b · The `analytics.materialization` row
```
analytics.materialization {
  projectionRef      : → analytics.projection.id
  payload            : the aggregated data (JSON/Parquet blob)
  vaultWatermark     : the exact byte-offset / LSN of the vault when this was computed

```

**Two contract shapes that must hold from the first write:**
1. **No manual edits.** A materialization row cannot be `UPDATE`d. It can only be `INSERT`ed (as a new version) or `DELETE`d (to force a rebuild). Any attempt to manually alter a cached metric is a schema-level refusal.
2. **Watermarks are mandatory.** A materialization without a `vaultWatermark` is a gate error. The surface must always be able to calculate `CurrentVaultLSN - materialization.vaultWatermark` to display the "Staleness Delta" to the user.

## 6 · Choicepoints resolved

### CP-Ω5-A · Where do projections live?
**Decision: In `ns analytics`, which is a first-class vault namespace but marked `derived`.** 
**Explanation:** Projections are vault rows, meaning they sync across devices via CRDTs (Ω-4/CP-1). However, because they are marked `derived`, a device receiving a sync conflict on an analytics row simply discards both and rebuilds from the local vault fold. The vault is the truth; the analytics are just a local cache of the truth.

### CP-Ω5-B · Semantic Clustering & "The Shape of My Life"
**Decision: Deterministic tagging at write-time + ML clustering as a badged realization.**
**Explanation:** Scenario #12 asks for a "topology graph of intent clusters." We cannot run an LLM over 50GB of history on the fly. Instead, the Intent Fabric (from the Master Spec) tags intents with deterministic semantic hashes at write-time. The Projection Engine folds these hashes into a graph. If the user wants *fuzzy* semantic clustering, they invoke `analytics.cluster@1`, which calls a badged ML realization (Ω-3 discipline) to group the deterministic hashes. The ML output is sealed into the materialization row with its badge. If the ML model is later demoted, the user knows exactly which heatmaps were shaped by it.

### CP-Ω5-C · The "Honest Heatmap" (Rendering Staleness)
**Decision: Surfaces must render the Staleness Delta.**
**Explanation:** If a user looks at a token-spend chart (#8) that was materialized 3 hours ago, the canvas must visually indicate (e.g., via a subtle fade or a "syncing" badge) that the data is 3 hours behind the vault tip. Ω refuses to present stale data as absolute truth. The quietness is UX; the authority is never quiet.

### CP-Ω5-D · Access Tracking (The "Oldest Unqueried Row")
**Decision: Read-events are vault rows, but heavily sampled/batched to prevent write-amplification.**
**Explanation:** Scenario #56 requires knowing what hasn't been read. If every `SELECT` writes a vault row, the vault doubles in size. Ω-5 implements a `read.access` batcher in the kernel: it aggregates read-access in memory and flushes a single `analytics.access_batch` row to the vault every $N$ seconds or $M$ reads. This preserves the forensic audit trail without destroying the disk.

## 3 · The architecture — predicates, placements, and pins

Ω-6 introduces a three-tier spatial model, all stored in `ns canvas`:

```
┌─────────────────────────────────────────────────┐
│              LAYOUT RULES (layout.rule)          │
│  declarative predicates over object properties   │
│  badged · signed · versioned · revocable        │
└──────────────────────┬──────────────────────────┘
                       │ deterministic evaluation
                       ▼
┌─────────────────────────────────────────────────┐
│          DERIVED PLACEMENTS (layout.placement)   │
│  spatial coordinates · zone assignment · cluster │
│  citing the rule + vault refs that produced them │
└──────────────────────┬──────────────────────────┘
                       │ overridden by
                       ▼
┌─────────────────────────────────────────────────┐
│              MANUAL PINS (layout.pin)            │
│  user-placed coordinates · highest authority     │
│  immune to layout rules until explicitly unpinned│
└─────────────────────────────────────────────────┘
```

**The evaluation order is constitutional:**

1. **Pins win.** If an object has a `layout.pin`, no rule moves it. Period.
2. **Rules apply to the unpinned.** Each layout rule evaluates its predicate against object properties and produces a `layout.placement` row.
3. **Conflicts resolve by rule priority.** Each rule carries a priority weight. Conflicting placements resolve deterministically by weight, then by rule creation order.
4. **Unplaced objects default.** Objects matching no rule land in the default zone (user-configurable, itself a layout rule).

**The rendering pipeline:**

```
Vault objects (identity, composition, binding, badge)
      ↓
Layout rules evaluate predicates
      ↓
Derived placements (citing rules)
      ↓
Pins override
      ↓
Canvas surface renders
      ↓
User interaction → may create new pins
```

### 4a · The `layout.rule` row

  arrangement      : spatial strategy (zone, cluster, stack, radial, grid, temporal)

### 4b · The `layout.placement` row

layout.placement {

layout.pin {

```

**Three contract shapes that must hold from the first write:**

1. **Every placement cites its rule.** A tile's position is never unexplained. "Why is this here?" resolves to a rule, a predicate, and the object properties that matched.
2. **Pins are immutable until explicitly removed.** A layout rule cannot overwrite a pin. Only `layout.unpin` removes a pin, and only by the pinning principal or a principal with explicit delegation.
3. **Layout state is sealable.** The full set of placements + pins at any vault watermark can be hashed into a single seal. Scenario #69 — *"what is the hash of my current layout?"* — is a one-line query.

## 6 · Choicepoints resolved

### CP-Ω6-A · Where does layout logic live?

**Decision: the layout engine is core, sole writer of `layout.placement` rows. Arrangement heuristics — clustering algorithms, sentiment scorers, radial strategies — are grantable realizations, badged and badged like any other. The engine evaluates; the heuristics shape. The engine is never grantable.**

**Explanation:** this mirrors Ω-3's architecture exactly. The assembler is core; the scorers are plugins. The layout engine is core; the arrangement functions are plugins. The constitutional principle is the same: *the mechanism that produces reality is never delegable; the heuristics that inform it are open to all through the same door.*

### CP-Ω6-B · Manual vs. automatic precedence

**Decision: pins are absolute. A pinned object is immune to all layout rules until explicitly unpinned. If a layout rule's predicate matches a pinned object, the engine logs a `layout.conflict` row (the rule *would* have moved it) but does not move it. The user sees the conflict and decides.**

**Explanation:** the user's spatial intent is the highest expression of sovereignty on the canvas. If the user placed a tile in the upper-left corner and said "this stays here," no algorithm — no matter how well-badged, no matter how `generic` — gets to override that. The conflict row is the honesty mechanism: the system tells you *"your rule wants this tile in the quarantine zone, but you pinned it here. What do you want?"* That question is the product working correctly.

### CP-Ω6-C · Layout and concealment

**Decision: layout can arrange, zone, cluster, stack, edge, and shrink. It cannot hide, delete, archive, or render an object unreachable. "Quarantine" is a visible zone with a visible boundary. "Museum" is a visible zone with a visible label. The only way to stop seeing something is to explicitly archive or delete it through the vault, which is a separate operation with its own consent, refusal, and provenance.**

**Explanation:** this is the load-bearing refusal of Ω-6. The moment a layout rule can make something invisible, the canvas has become a censorship engine. A `speculative` tool pushed to the edge is still *visible at the edge*. A tile shrunk to a dot is still *a dot you can tap*. The user's attention is theirs to allocate; the system's job is to make the allocation *informed*, not to make it for them. This is the Mirror Paradox applied to pixels: the canvas reflects what exists, arranged honestly. It does not edit what exists.

### CP-Ω6-D · Temporal layout and scrubbing

**Decision: the canvas can render its layout at any historical vault watermark via `layout.scrub`. Scrubbing is a read-only projection. It does not modify current placement. Returning to the present restores the current layout exactly. Scrubbed states are navigable but not editable.**

**Explanation:** scenario #4 — *"scrub the canvas backward in time"* — is the canvas's self-knowledge made spatial. Because layout is vault data, and the vault is append-only, every historical layout state is reconstructable. Scrubbing is the canvas answering *"what did I look like when?"* — the spatial equivalent of the ledger answering *"what did I know when?"* The read-only constraint is critical: you cannot accidentally edit the past by scrubbing into it. The past is a projection, not a destination.

### CP-Ω6-E · Layout rules as Forge artifacts

## 3 · The Architecture — Proposals, Scars, and Effective Badges

Ω-7 introduces three new primitives to the vault:

### 3a · The Badge Proposal Engine
A core daemon that consumes Ω-5 (Analytics) and Ω-2 (Governor contract tests). When a `speculative` artifact meets a named threshold (e.g., 100 error-free invocations, or passing the synthetic mine 3 times), the engine mints a `badge.proposal` row. 
*Crucially: The engine stops here. It does not alter the artifact's badge.*

### 3b · The Lineage Graph & The Scar
Every time a Forge creates an artifact (a tile, a provider, a layout rule), the kernel records a `lineage.edge` row (parent -> child). 
When a parent Forge is demoted (e.g., fails contract tests, or is manually revoked by the user), the kernel mints a `lineage.scar` row. 

### 3c · The Effective Badge
An artifact's badge is no longer just a static field on its row. It is a **fold**:
`Effective Badge = min(Artifact.OriginalBadge, min(Parent.EffectiveBadge for all parents with active scars))`

If a child was forged as `harvested`, but its parent Forge is scarred down to `speculative`, the child's *effective* badge becomes `speculative`. The canvas (Ω-6) reads the effective badge, not the original one.

# One agent = one worktree; never share a worktree across parallel agents

> **Classification: DERIVED — CURRENT**


## Claim

Parallel agents must work in separate git worktrees (SYSTEM §8 already
encourages worktrees); sharing one worktree across agents is forbidden
for missions.

## Why

A parallel agent started on `mission/amp-1`, then checked out
`coord/p1-10-program-observatory-v0` in the same worktree to commit its
WS-010 research. The checkout moved the worktree under the AMP-1 mission,
removing mission-tracked files from disk mid-mission. Recovery succeeded
(commits were safe on the branch; surviving copies verified identical),
but the mission lost time and took on avoidable risk: an uncommitted
edit at that moment would have been carried across branches or lost.

## Alternatives considered or rejected

- Branch-verify discipline only (already in STATE DO_NOT): rejected as
  sufficient on its own — it detects the situation but does not prevent
  the disruption.
- Locking the worktree against other agents: rejected, no mechanism
  exists and a lock would be a second coordination registry.

## Consequences

In force for the mission: future missions in this repo run one worktree
per agent (`git worktree add`), and charters name their worktree. The
branch-verify line stays as backstop. No tooling change: this is
procedure, and the L1 gate already refuses cross-branch commits by
branch match.

## Evidence

`git log`/`ls-remote` show 945282e intact locally and on origin with the
reported 14 files / 1640 insertions; `git diff main...<branch>
--name-only` on both branches shows zero overlapping paths.

## Proposed first useful composition

**Research → Evidence → World**

The user asks VIVIM to investigate something for a target project/topic and save a useful result into the user's environment.

Human expression:

> “Research this for my project and save what you find.”

The exact wording is not canonical. The invariant is the composition.

## Journey coverage

### J1 — Open/orient

Open the same Product Instance and restore the active composition plus world basis.

### J2 — Continue work

Project/context is derived from durable world state rather than reconstructed from an app-specific silo.

### J3 — Universal interaction

Address target → express intent → resolve capability → route to realization → authorize → execute.

### J4 — Delegated action

The same request can become durable Work when the user asks the environment to carry the outcome through execution.

### J5 — Provider choice

The first composition can be bounded to one configured browser realization/account while the general routing policy remains later work. The composition therefore proves the realization seam without pretending general routing is finished.

### J6 — Background continuity

The Work representation is compatible with later sleeping/background execution, even if the first proof keeps execution foregrounded.

### J7 — Evolution

The composition itself can later be rebuilt/replaced through the Forge path without moving provider/product semantics into K0.

### J8 — Exit

The canonical result is in the vault/world boundary, so later export/restore can preserve user-owned state independently from browser runtime state.

## Thin proof path

The first executable proof should be deliberately narrow:

1. start an existing or freshly initialized instance;
2. load a signed composition containing the seven reference pieces;
3. enter a request through the existing intent path;
4. resolve one research capability;
5. select one declared browser realization;
6. pass the ordinary law/consent gate;
7. create one Work subject when execution is consequential;
8. execute through the Chrome/browser realization;
9. append result/evidence to the vault;
10. read the result through the World projection;
11. close the instance;
12. reopen the same instance and verify the same canonical result is present.

This proves compositional interoperability without requiring the complete VIVIM product.

## Live-provider constraint

Current System Intelligence and reality audit distinguish code/fixture evidence from LIVE-PROVEN external execution. Therefore the first implementation may use the existing fixture/replay proof while the owner-machine live-provider ceremony is kept as an explicit verification step.

The composition must never encode “fixture = live”.

## Product Instance constraint

Existing Product Instance research identifies an activation gap:

> verified candidate != activated composition.

A first implementation must preserve the prior active composition until the new composition is both compatible and successfully ready. This can be implemented inside the Product Instance/plugin lifecycle boundary; it does not require moving Product Instance semantics into K0.

## Composition falsifiers

- remove one required piece and the composition refuses deterministically;
- replace the provider realization with an incompatible candidate and the old active composition remains;
- deny authority and no external effect occurs;
- corrupt a regenerable projection and canonical vault state survives;
- close/reopen and canonical evidence remains addressable;
- a first-party reference piece and an extension-shaped test piece use the same plugin boundary.

## Why this is a factory composition, not a fixed product

The visible result is only one useful composition.

The reusable factory semantics are:
- address;
- resolve intent;
- discover/select capability;
- admit a composition;
- authorize;
- execute;
- persist evidence;
- project world;
- replace/evolve pieces.

A different user can later compose:
- email + contact + project;
- files + search + report;
- monitoring + attention + background Work;
without changing the factory boundary.

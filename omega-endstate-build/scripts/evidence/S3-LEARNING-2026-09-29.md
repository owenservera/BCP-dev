verdict key exists (explicit guard in its task text, e.g. "you are NOT done
until `s3-verdict` is readable via memory_get"), and/or make the orchestrator —

## L3 — Broadcast relay covers spawn races

stew-01's direct send to ver-01 failed ("not yet spawned"); the message was
relayed via broadcast (`*`) and ver-01 acted on it. The relay path is proven;
keep it and keep logging the relay event (it was the only trace of the race).

## L4 — Windows launch must be split-call (measured hang)

The operator's launch call hung forever although the harness script itself
finished at 15:59:34 with its marker written. Mechanism: the serve child
(PID 12784) survived teardown, inherited the tool pipe, and EOF never arrived —
the exact overlapped-pipe / job-object hang class in AGENTS.md. Rule: never
wait inline on a spawn. Launch detached (Start-Process, stdio to files), then
poll the `.status.json` marker in a separate call.

## L5 — Teardown by port is unreliable when the owner PID is dead

`Stop-ServerAndVerify` re-read listeners 4 times and taskkill returned 128
(process not found) every time, yet port 29952 still reports Listen with dead
owner 12784 — and still completes TCP handshakes. Post-run attribution (recovery
2026-09-29, build mode): launcher 560, swarm 14404, serve 12784 all gone; the
only live `opencode.exe` are the owner's pre-existing PIDs 2632/9908; all live
`node.exe` belong to owner tooling (chrome MCP host, native host, mcp-use
inspectors) — none reference the S3 WorkDir or port. Conclusion: no live
process holds the port; the entry is a stale stack artifact. Do NOT chase it
with image-name kills (that previously killed owner TUI sessions). If a future
run needs the port and it is still stuck, use a fresh port (29953+).

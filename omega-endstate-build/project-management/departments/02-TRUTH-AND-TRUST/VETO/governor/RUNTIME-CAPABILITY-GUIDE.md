# Runtime Capability Guide

## Principle

The department should be defined in terms of capabilities, not tools.

Required capability classes are:

### Observe

Repository files, diffs, history, runtime state, tests, process output and environment facts.

### Retrieve

Internal project knowledge, durable context and external primary sources.

### Reason

Independent analysis, hypothesis generation, counterargument, impact assessment.

### Communicate

Report to owner, record findings, request evidence, record decisions.

### Persist

Durable task state, evidence receipts, results, learning and lineage.

### Experiment

Run bounded, reproducible tests when the current authority and environment permit.

### Compare

Evaluate current proposal against alternatives, prior baselines and outcomes.

### Evolve

Propose changes to the department or wider development organization.

## Fungibility rule

A specific tool is an implementation of a capability.

If a tool disappears, the capability contract should remain.

Do not make the department dependent on:

- OpenCode;
- opencode-swarm;
- MCP;
- a particular model provider;
- a particular shell;
- a particular storage backend.

## Current available evidence surfaces

The current branch has useful OpenCode, swarm, Commons and repository surfaces, but these should be inspected and qualified rather than assumed.

The department's job is to learn what the runtime actually gives it.

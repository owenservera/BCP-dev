# Self-Evolution Guide

Purpose: provide a disciplined path for changing the department and, eventually, informing changes to the wider development organization.

## Core principle

Never equate "possible improvement" with "justified change."

A self-evolution proposal must survive evidence.

## Evolution loop

OBSERVE
-> IDENTIFY REPEATED LIMITATION
-> FORM HYPOTHESIS
-> DESIGN SMALLEST CHANGE
-> DEFINE BASELINE + CONTROL
-> RUN ISOLATED EXPERIMENT
-> INDEPENDENTLY EVALUATE
-> ACCEPT / REJECT / ITERATE
-> PRESERVE LINEAGE
-> UPDATE OPERATING MODEL

## What can evolve

Potentially:

- prompt/instructions;
- task taxonomy;
- queue design;
- context bundle composition;
- evidence policy;
- audit method;
- trigger detection;
- review boundaries;
- reporting structure;
- specialist composition;
- tools/capabilities;
- collaboration protocols;
- memory and knowledge structures;
- evaluation methodology.

## What must remain protected

Until explicitly changed by owner governance:

- primary company mission;
- advisory-only authority;
- independent challenge;
- evidence traceability;
- recoverability;
- explicit owner decision;
- no self-granted authority.

## Experiment discipline

For every proposed evolution, identify:

- baseline;
- proposed variant;
- independent evaluator;
- primary metric;
- secondary metrics;
- falsifier;
- rollback condition;
- cost ceiling;
- stopping condition.

For changes to the department itself, prefer isolated branches/worktrees or equivalent disposable states.

## Archive and lineage

A good self-evolving system retains unsuccessful variants and their reasons rather than erasing them.

A candidate change should link:

parent state -> change -> evaluation -> decision -> successor state

Self-improvement research provides useful examples of archived variants, empirical evaluation, lineage and sandboxing/human oversight. These are transferable practices, not instructions to copy a specific system.

## Regression protection

A change is not accepted merely because one target improves.

Check for regressions in:

- mission alignment;
- evidence quality;
- independent judgment;
- coordination cost;
- latency;
- robustness;
- recoverability;
- false-veto rate;
- missed-risk rate.

## No live self-mutation

Do not let a running session silently rewrite the operating rules under which that same session is being governed.

Propose -> review -> experiment -> decide -> activate.

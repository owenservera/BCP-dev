# BCP RECONCILIATION — READ FIRST

This document is the tie-breaker. When two BCP artifacts disagree, this wins.
Any agent or human onboarding onto this workspace should read this file first,
before `agents/bootstrap.md`.

## Scope note (important)

BCP-SPEED is the **devops / build-control-plane system for tracking parallel
agent work**. It is intentionally generic — it does not model Omega's actual
vocabulary (the 8-layer stack, the 10-verb capability map, W5 atom, waves,
D-records). BCP-SPEED and Omega are kept **separate on purpose**: BCP-SPEED
is a project-tracking substrate any codebase could sit under; Omega is a
product with its own constitution. Do not try to make BCP's 20 families match
Omega's real families — they are different systems being tracked by the same
kind of tool.

## What still applies (do NOT discard)

- The 20 capability families / 140 sub-capabilities **as a generic tracking
  taxonomy** — this is placeholder content for *this* BCP instance. Replace
  the contents of `state/capabilities.yaml` with whatever project you're
  actually tracking; the shape (family → sub-capability → depth → invariant)
  is the reusable part, not the specific family names.
- The taxonomy ID schemes (`FAM-{nn}`, `FAM-{nn}.{n}`, `WRK-{...}`, etc.).
- The controlled vocabulary (capability, realization, depth, lease, experiment...).
- The dependency graph model (typed edges, build order). Direction: `source
  REQUIRES target` means the source cannot be leased or advanced until the
  target has reached `required_depth`. Only REQUIRES edges are enforced by
  the tools; BLOCKS/ENABLES/SUPERSEDES/CONFLICTS are recorded, not enforced.
- The parallel-agent coordination model (leases, signals, coordinator).

## The authoritative stack

1. **Primary store:** `state/*.yaml`. Agents read these directly but **write only
   through `bcp_tool.py`** (atomic, locked, validated against the taxonomy).
   `validate.py` and `sweep.py` check and maintain them.
2. **History:** `log/*.yaml` (append-only, one file per day, git-tracked).
3. **Visual:** `views/*.html` (auto-generated by `generate_views.py`, never
   hand-edited, not git-tracked — see `.gitignore`).
4. **SQL (optional):** only if you want queryable projections later. Not
   required to operate BCP-SPEED day to day.

## The 4-level depth system (canonical)

| Depth | Name | Meaning | Entry criteria |
|---|---|---|---|
| L0 | SPEC | Defined | Canonical ID + invariant written |
| L1 | STUB | Has an interface | Compiles / parses, returns a mock, passes through the gate |
| L2 | WORKS | Functions on the happy path | Happy path + error path handled + logged to `log/` |
| L3 | HARDENED | Production-safe | Adversarial-tested, failure-safe, replayable, no hidden deps |

## Autonomy bands (replace rigor profiles)

| Band | What an agent may do without asking |
|---|---|
| `self_approve` | Bump depth within a level, add a work item, update status, append to log, regenerate views |
| `propose_then_act` | Bump depth across a level, add a dependency edge, mark blocked — wait ~5 min for a veto signal, then act |
| `require_human` | Create/delete a capability, modify an invariant, merge experiments, restructure families |

## The one rule

> If two artifacts disagree, the interpretation that makes the system
> **faster to read/write and more autonomous** wins, provided it does not
> violate a stated invariant.
